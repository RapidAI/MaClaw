M MaClaw Connector第三方硬件接入协议

协议版本 1.1 · 以当前 ESP32-S3 客户端为准

把第三方硬件接入 MaClaw Hub

设备通过一次性配对码取得持久 Bearer Token，声明自身输入、输出与硬件能力，随后使用 HTTPS JSON、游标长轮询和逐消息 ACK 与 MaClaw 交换文本、语音、设备配置及会议录音。

入口 https://<hub> 消息 API /api/im-gateway/v1 配对 API /api/device-gateway/v1 传输 HTTPS + JSON
适用范围本页描述 Hub 上公开的硬件设备协议。MaClaw GUI 在 127.0.0.1:18777 提供的本机第三方软件网关与此协议共享消息结构，但不包含本页的 Hub 配对、硬件能力和会议录音扩展。
本页内容 接入流程配对能力协商 消息与媒体轮询与 ACK会议录音 运行约定错误处理

1. 接入流程

  1. 1
    生成配对码

    在 MaClaw GUI 的“设置 / 消息接入 / 第三方接入 / 硬件配置”中生成 6 位配对码。配对码有效期 30 分钟且只可消费一次。

  2. 2
    换取设备凭证

    设备以稳定的 clientId 调用 POST /pair，成功后安全保存 gatewayToken，并立即删除本地配对码。

  3. 3
    能力协商

    每次启动调用 POST /handshake，提交新的 bootSessionId 和真实能力。只有冷启动才更换 bootSessionId；普通刷新沿用它。

  4. 4
    收发消息

    输入通过 POST /incoming 提交；输出由唯一的 GET /outgoing 长轮询读取，处理完成后调用 POST /ack。

  5. 5
    保存恢复状态

    持久化 Token 与会议上传进度；游标是否落盘取决于客户端能否同时持久化去重状态。当前 ESP32 仅在 RAM 中维护游标，重启后从 0 重新轮询，并依靠 Hub 的 ACK 状态跳过已确认消息。

2. 配对与认证

POST /api/device-gateway/v1/pair

Content-Type: application/json

{
  "clientId": "esp32s3-pet-001",
  "pairCode": "123456"
}

pairCode 是规范字段；服务端仍兼容旧固件的 code，新接入不要继续使用别名。成功返回 201 Created：

{
  "ok": true,
  "gatewayToken": "<64-character device token>",
  "clientId": "esp32s3-pet-001"
}

同一 clientId 再次配对会撤销旧 Token 并清空旧的设备出站队列。除健康检查、配对以及带 mediaToken 的媒体 URL 外，后续请求必须携带：

Authorization: Bearer <gatewayToken>
不要擦除被拒绝的 Token当握手返回 401 或 403 时，进入重新配对流程，但保留旧 Token 供诊断。网络错误、408、429 和 5xx 属于可重试故障，不应触发配对恢复。
可选：语音配对端点

POST /api/device-gateway/v1/pair/voice 接收不超过 512 KiB 的短 WAV，使用 X-MaClaw-Client-ID 指定设备。服务端从语音中识别恰好 6 位数字并返回与普通配对相同的 201 响应。该端点按来源和设备限流，ASR 未配置时返回 503。

Content-Type: audio/wav
X-MaClaw-Client-ID: esp32s3-pet-001

<raw WAV bytes>

}

meetingRecording 仅在 Hub 启用了该能力时出现；transcript 和 minutes 只会在相应工作器可用时为 true。客户端必须以响应为准，不要硬编码可用模式。

设备端工具

顶层 tools 是本次握手注册的设备工具目录，Hub 会把它附加到该设备后续提交的消息。当前 ESP32 注册 alarm_create、alarm_clear_all、alarm_clear 和 alarm_list；最多 16 个闹钟与最近 8 个修改状态的工具调用结果写入 NVS。结果缓存是固定轮换槽，包含成功和确定性失败，不是永久调用历史；只读的 alarm_list 不进入缓存，可安全重执行。刷新握手会替换目录；不再支持的工具必须从数组移除。

Hub/GUI 可在普通出站队列投递 tool_call。设备只执行自己注册并实现的名称，使用 toolCall.idempotencyKey 去重；缺省时回退到 toolCall.id。通用协议允许标识符最多 128 个字符，但当前 ESP32 的 64 字节持久化结果槽要求修改状态的调用使用最多 63 个 ASCII 字符的幂等键；超限或非 ASCII 键会在执行前以 invalid_arguments 拒绝。执行完成后调用 POST /api/im-gateway/v1/tool-result，只有结果提交成功后才 ACK 原 tool_call 消息。

{"id":"hub_out_...","type":"tool_call","conversationId":"default","toolCall":{"id":"call-1","name":"alarm_create","arguments":{"triggerAtEpochMs":1781031600000,"label":"喝水"},"idempotencyKey":"call-1"}}
POST /api/im-gateway/v1/tool-result
{"clientId":"esp32s3-pet-001","resultId":"call-1","toolCallId":"call-1","conversationId":"default","status":"success","idempotencyKey":"call-1","result":{"count":1}}

status 规范值为 success、error、rejected、cancelled 或 timeout；服务端也会把 succeeded/failed 等兼容值归一化。工具结果当前作为异步输入继续送入 Agent，200 accepted=true 仅表示 Hub 已接收。

文本：POST /api/im-gateway/v1/incoming

{
  "clientId": "esp32s3-pet-001",
  "eventId": "text-1781028000000",
  "messageId": "text-1781028000000",
  "conversationId": "default",

{"ok": true, "accepted": true, "messageId": "text-1781028000000", "duplicate": false}

5. 出站轮询、关联与 ACK

GET /api/im-gateway/v1/outgoing

GET /api/im-gateway/v1/outgoing?clientId=esp32s3-pet-001&cursor=0&limit=16&timeout=5
  • 同一设备只能运行一个出站读取器。当前 ESP32 在前台命令期间使用 2 秒长轮询，空闲时使用 5 秒。
  • limit 范围 1–20，默认 20；timeout 范围 0–30 秒，默认 0。超范围值会被夹紧。
  • nextCursor 是该页最后一条消息的游标。仅在整页都已处理或确认可安全去重后持久化；若某条可重试媒体尚未成功播放，继续使用旧游标以便重新取得该页。
{
  "ok": true,
  "messages": [{
    "id": "hub_out_1781028005123_12", "seq": 12,
    "conversationId": "default", "replyTo": "voice-1781028000000",
    "type": "text", "text": "上海今天晴，27℃。",
    "metadata": {"acp_turn": "final"}
  }],
  "nextCursor": "12",
  "hasMore": false
}

回复关联按以下优先级读取：replyTo、replyToMessageId、source_message_id、sourceMessageId、sourceMessageID，并兼容这些字段位于 metadata 或 extra 中。progress: true 或 metadata.acp_turn 为 progress/working 表示中间进度；final/complete/completed 表示终态。

当前设备应支持的出站类型包括 text、error、audio/voice、ambient、pet_state、hardware_config、meeting_result 和单步 tool_call。通用协议还能表示 tool_plan/tool_cancel，但当前 ESP32 不执行这两类消息，服务端不要向它投递。当前 ESP32 仍兼容内联 data/file_data，但握手只声明 URL 投递；新服务端应返回以 /api/im-gateway/v1/media/ 开头的同源相对 URL。响应体达到或超过 96 KiB 会被拒绝。

POST /api/im-gateway/v1/ack

{
  "clientId": "esp32s3-pet-001",
  "messageIds": ["hub_out_1781028005123_12"],
  "status": "delivered"
}

status 规范值为 delivered、read 或 failed；省略或无法识别的值会归一化为 delivered，因此新客户端不要依赖自定义状态。一次最多确认 100 个非空消息 ID。文本、配置和已成功播放的音频回报 delivered；格式错误、超出能力或不可恢复的音频回报 failed；暂时的下载、内存、I2S 或设备忙错误不 ACK，留到下一轮重试。ACK 成功返回 {"ok":true}。

6. 可恢复会议录音

仅当握手响应包含 meetingRecording 时启用。客户端使用响应给出的 basePath 和 chunkSize，而不是把下面的默认值写死。

步骤请求成功状态
创建POST {basePath}201
分片PUT {basePath}/{id}/chunks/{index}204
完成POST {basePath}/{id}/complete200

POST /api/device-gateway/v1/meeting-recordings
{"title":"硬件会议录音","purpose":"","conversation_id":"default","content_type":"audio/wav"}
PUT /api/device-gateway/v1/meeting-recordings/{recording_id}/chunks/0
Content-Type: application/octet-stream
X-Chunk-SHA256: <sha256 of this chunk>

<1 to 1048576 raw bytes>
POST /api/device-gateway/v1/meeting-recordings/{recording_id}/complete
{"chunks":3,"sha256":"<sha256 of complete WAV>","duration_sec":82.125}

POST /api/device-gateway/v1/meeting-recordings/{recording_id}/process
{"mode":"minutes"}

分片从 0 连续编号，每片 1 字节至 1 MiB，且必须带 SHA-256；相同序号可用相同内容安全重试。完成请求会按顺序合并并校验整文件。Hub 总配额为 512 MiB；16 kHz 单声道 S16LE WAV 的最长声明时长约为 16,777 秒（约 4 小时 39 分）。录音状态默认保留 30 天。mode 只能选择握手中为真的 keep、transcript 或 minutes。

断点恢复设备应在每个成功分片后持久化 recording_id、下一个分片序号和阶段。重启后先 GET 状态：uploading 继续分片，uploaded/failed 继续处理，processing/ready 不再重复提交。终态结果会作为 meeting_result 进入普通出站队列。

7. 运行与安全约定

稳定身份

clientId 对一个物理设备保持稳定；Token 与会议恢复信息写入持久存储。当前 ESP32 的出站游标仅驻留 RAM，冷启动后从 0 恢复轮询；bootSessionId 每次冷启动随机生成，最长 96 字符。

单一 HTTP 调度

资源受限设备应串行化普通 HTTP 请求，避免轮询、语音上传和 ACK 争用 TLS 内存。前台操作可缩短长轮询，但不要启动第二个读取器。

最小能力

按真实屏幕、扬声器、麦克风、编解码器和内存上限声明能力。Hub 会据此把大音频转为 URL、截断文本，并过滤无法处理的类型。

媒体安全

只访问 Hub 返回的同源媒体 URL。当前 ESP32 还会限制音频路径必须以 /api/im-gateway/v1/media/ 开头，拒绝任意外部下载地址。

建议的重试策略

配对与握手使用 2 秒起步、最大 60 秒的指数退避；普通轮询失败后至少等待 3 秒。/incoming 返回 200 且 accepted=true 后不得重发。只有在未收到明确成功响应、且业务能接受“至少一次”处理语义时，才以有限次数退避重试，并为同一业务动作复用相同的 eventId/messageId。当前 ESP32 的语音提交最多尝试 3 次。

/incoming 不是持久幂等接口Hub IM 核心当前按 messageId 提供约 10 秒的进程内尽力去重；该记录不会持久化，Hub 重启或超过窗口后重发仍可能再次处理。设备网关响应中的 duplicate 当前通常为 false，不能作为持久幂等证明。请避免无界重试。

8. 错误处理

{
  "ok": false,
  "error": {"code": "unauthorized", "message": "missing or invalid bearer token"}
}
HTTP含义客户端动作
400JSON、字段、能力、媒体或分片无效修正请求；不要原样热循环重试。
401 / 403配对码或设备凭证无效、clientId 不匹配停止受保护请求并进入配对恢复。
404媒体或会议对象不存在媒体重新准备；会议对象重新创建。
409上传/处理阶段冲突GET 当前状态后从服务端状态恢复。
429请求过快遵守 Retry-After 并指数退避。
503GUI 中继、ASR 或处理能力不可用保留本地数据，稍后重试或选择可用模式。
5xxHub 临时故障按端点决定是否重试；/incoming 仅在可接受至少一次语义时复用原 ID 并有限重试。

MaClaw Third-Party Hardware Protocol · Protocol 1.1 · aligned with the current ESP32-S3 client

Connect third-party hardware to MaClaw Hub

A device exchanges a one-time pairing code for a durable bearer token, declares its actual input, output, and hardware capabilities, then uses HTTPS JSON, cursor long polling, and per-message acknowledgements for text, audio, configuration, and resumable meeting recordings.

Origin https://<hub> Messaging /api/im-gateway/v1 Pairing /api/device-gateway/v1 Transport HTTPS + JSON
ScopeThis page specifies the public Hub hardware protocol. The loopback third-party software gateway exposed by MaClaw GUI at 127.0.0.1:18777 shares the core message shape, but does not use the Hub pairing, device capability, or meeting-recording extensions described here.
On this page FlowPairingCapabilities Messages & mediaPolling & ACKMeetings Runtime contractErrors

1. Integration flow

  1. 1
    Create a pairing code

    In MaClaw GUI, open Settings / Message Access / Third-party Access / Hardware configuration. Generate a six-digit code. It expires after 30 minutes and can be consumed once.

  2. 2
    Exchange it for credentials

    Call POST /pair with a stable clientId. Persist the returned gatewayToken securely and delete the local pairing code.

  3. 3
    Negotiate capabilities

    On every startup, call POST /handshake with a fresh bootSessionId and honest capabilities. Keep the same boot ID for ordinary handshake refreshes.

  4. 4
    Exchange messages

    Submit input with POST /incoming. Run exactly one GET /outgoing reader and acknowledge handled messages with POST /ack.

  5. 5
    Store recovery state

    Persist the token and meeting-upload progress. Persist a cursor only if the client also has durable deduplication state. The current ESP32 keeps its cursor in RAM, restarts from zero after reboot, and relies on Hub ACK state to skip acknowledged messages.

2. Pairing and authentication

POST /api/device-gateway/v1/pair

{"clientId":"esp32s3-pet-001","pairCode":"123456"}

pairCode is canonical. The server accepts legacy code only for already-flashed firmware. Success returns 201 Created:

{"ok":true,"gatewayToken":"<64-character device token>","clientId":"esp32s3-pet-001"}

Pairing the same clientId again revokes its previous token and clears the stale device queue. Except for health, pairing, and URLs protected by mediaToken, send:

Authorization: Bearer <gatewayToken>
Do not erase a rejected tokenA handshake 401 or 403 should enter pairing recovery while retaining the old token for diagnosis. Network errors, 408, 429, and 5xx are retryable and must not trigger re-pairing.
Optional voice pairing

POST /api/device-gateway/v1/pair/voice accepts a short WAV of at most 512 KiB and requires X-MaClaw-Client-ID. The server extracts exactly six spoken digits. It is rate-limited and returns 503 when ASR is unavailable.

Content-Type: audio/wav
X-MaClaw-Client-ID: esp32s3-pet-001

<raw WAV bytes>

meetingRecording is omitted when unavailable. Processing modes are advertised only when their workers are configured; always follow the response.

Client-side tools

The top-level tools array is the device tool catalog for this handshake. Hub attaches it to later messages from that device. The current ESP32 registers alarm_create, alarm_clear_all, alarm_clear, and alarm_list. It persists at most 16 alarms and the eight most recent state-changing tool-call results in NVS. The result cache is a fixed rotating set of slots containing both successes and deterministic failures, not a permanent call history. Read-only alarm_list calls are not cached and are safe to execute again. A refreshed handshake replaces the catalog, so remove tools the device no longer supports.

Hub/GUI may deliver a tool_call through the normal outgoing queue. Execute only names that the device registered and implements. Deduplicate with toolCall.idempotencyKey, falling back to toolCall.id. The general protocol permits identifiers up to 128 characters, but the current ESP32 uses 64-byte persistent result slots and requires state-changing calls to use an idempotency key of at most 63 ASCII characters; longer or non-ASCII keys are rejected as invalid_arguments before execution. After execution, call POST /api/im-gateway/v1/tool-result; ACK the original tool_call only after that result submission succeeds.

{"id":"hub_out_...","type":"tool_call","conversationId":"default","toolCall":{"id":"call-1","name":"alarm_create","arguments":{"triggerAtEpochMs":1781031600000,"label":"Hydrate"},"idempotencyKey":"call-1"}}
POST /api/im-gateway/v1/tool-result
{"clientId":"esp32s3-pet-001","resultId":"call-1","toolCallId":"call-1","conversationId":"default","status":"success","idempotencyKey":"call-1","result":{"count":1}}

Canonical status values are success, error, rejected, cancelled, and timeout; the server also normalizes compatibility spellings such as succeeded/failed. A tool result is forwarded asynchronously as new Agent input, so 200 accepted=true only confirms Hub acceptance.

5. Outgoing polling, correlation, and ACK

GET /api/im-gateway/v1/outgoing?clientId=esp32s3-pet-001&cursor=0&limit=16&timeout=5
  • Run one outgoing reader per device. The current ESP32 uses a 2-second poll during a foreground command and 5 seconds while idle.
  • limit is clamped to 1–20; timeout is clamped to 0–30 seconds.
  • nextCursor identifies the last message in the page. Persist it only after the entire page is handled or can be safely deduplicated; keep using the old cursor while retryable media remains unplayed.
{"ok":true,"messages":[{"id":"hub_out_1781028005123_12","seq":12,"conversationId":"default","replyTo":"voice-1781028000000","type":"text","text":"It is sunny and 27°C.","metadata":{"acp_turn":"final"}}],"nextCursor":"12","hasMore":false}

Resolve correlation in this order: replyTo, replyToMessageId, source_message_id, sourceMessageId, sourceMessageID, including those fields inside metadata or extra. progress: true or metadata.acp_turn=progress/working is intermediate; final/complete/completed is terminal.

Current device output types include text, error, audio/voice, ambient, pet_state, hardware_config, meeting_result, and single-step tool_call. The generic protocol can also represent tool_plan/tool_cancel, but the current ESP32 does not execute those message types; servers must not send them to this client. The current ESP32 remains compatible with inline data/file_data, but advertises URL-only delivery; new servers should return a same-origin relative URL beginning with /api/im-gateway/v1/media/. Response bodies at or above 96 KiB are rejected.

POST /api/im-gateway/v1/ack

{"clientId":"esp32s3-pet-001","messageIds":["hub_out_1781028005123_12"],"status":"delivered"}

Canonical statuses are delivered, read, and failed. Missing or unrecognized values normalize to delivered, so new clients must not rely on custom statuses. A request may acknowledge at most 100 non-empty message IDs. ACK text, configuration, and successfully played audio as delivered. ACK permanent format/capability/playback errors as failed. Do not ACK transient download, allocation, I2S, or busy failures; leave them for the next poll.

Chunks are contiguous from zero, between 1 byte and 1 MiB, and require SHA-256; retrying the same index with the same bytes is safe. Hub verifies the assembled file and has a 512 MiB recording quota. Choose only an advertised keep, transcript, or minutes mode.

Resume contractPersist recording_id, next chunk, and phase after every successful chunk. On restart, GET status: continue chunks for uploading, continue processing for uploaded/failed, and do not resubmit for processing/ready. Terminal results arrive as meeting_result through the normal outgoing queue.

7. Runtime and security contract

Stable identity

Keep clientId stable per physical device. Persist the token and meeting recovery state. The current ESP32 keeps its outgoing cursor in RAM and resumes from zero after a cold start. Generate a cold-start bootSessionId of no more than 96 characters.

One HTTP scheduler

Resource-limited devices should serialize regular HTTP work so polling, audio uploads, and ACKs do not compete for TLS memory. Shorten the foreground poll instead of adding a reader.

Minimum honest capability

Describe the real display, speaker, microphone, codecs, and memory limits. Hub uses this contract to convert large audio to URLs, truncate text, and filter unsupported output.

Media safety

Use only Hub-returned, same-origin media URLs. The current ESP32 additionally requires audio paths to start with /api/im-gateway/v1/media/.

Recommended retries

Use exponential backoff from 2 seconds up to 60 seconds for pairing and handshake. Wait at least 3 seconds after poll failures. Never resend an /incoming request after receiving 200 with accepted=true. Only when no definite success response arrived and the business action tolerates at-least-once processing, retry a bounded number of times with backoff and reuse the same eventId/messageId. The current ESP32 makes at most three voice-submission attempts.

/incoming is not durably idempotentThe Hub IM core currently performs best-effort, in-memory deduplication by messageId for about 10 seconds. That state is not persisted; a resend after the window or a Hub restart may be processed again. The device-gateway response currently reports duplicate as false in normal operation, so it is not proof of durable idempotency. Avoid unbounded retries.

5. Гарах лавлагаа, холбоос ба ACK

GET /api/im-gateway/v1/outgoing?clientId=esp32s3-pet-001&cursor=0&limit=16&timeout=5
  • Төхөөрөмж бүрт нэг гарах уншигч ажиллуулна. Одоогийн ESP32 идэвхтэй команд үед 2 секундын лавлагаа, сул үед 5 секунд ашиглана.
  • limit нь 1–20, timeout нь 0–30 секундын хязгаарт хавчигдана.
  • nextCursor нь тухайн хуудасны сүүлийн зурвасыг заана. Хуудсыг бүхэлд нь боловсруулсан эсвэл аюулгүй давхардал арилгаж чадсаны дараа л хадгална. Дахин оролдох медиа тоглогдоогүй үед хуучин курсорыг үргэлжлүүлэн ашиглана.

Холбоосыг энэ дарааллаар тогтооно: replyTo, replyToMessageId, source_message_id, sourceMessageId, sourceMessageID. Эдгээр талбар metadata эсвэл extra дотор байж болно. progress: true эсвэл metadata.acp_turn=progress/working нь завсрын төлөв, final/complete/completed нь төгсгөлийн төлөв юм.

Одоогийн төхөөрөмжийн гаралтын төрөлд text, error, audio/voice, ambient, pet_state, hardware_config, meeting_result болон нэг алхмын tool_call багтана. Ерөнхий протокол tool_plan/tool_cancel-ийг мөн илэрхийлж чадна. Гэвч одоогийн ESP32 эдгээр зурвасын төрлийг гүйцэтгэдэггүй тул сервер тэдгээрийг энэ клиентэд илгээх ёсгүй. Одоогийн ESP32 мөр доторх data/file_data-тай нийцтэй хэвээр боловч зөвхөн URL хүргэлтийг зарлана. Шинэ сервер /api/im-gateway/v1/media/ гэж эхэлсэн ижил эх үүсвэрийн харьцангуй URL буцаах ёстой. 96 KiB ба түүнээс их хариуны бие татгалзагдана.

POST /api/im-gateway/v1/ack

{"clientId":"esp32s3-pet-001","messageIds":["hub_out_1781028005123_12"],"status":"delivered"}

Үндсэн төлөв нь delivered, read болон failed юм. Сервер байхгүй эсвэл танигдаагүй утгыг delivered болгож нормчилдог тул шинэ клиент тусгай төлөвт найдах ёсгүй. Нэг хүсэлт хамгийн ихдээ 100 хоосон биш зурвасын ID-г ACK хийж болно. Текст, тохиргоо болон амжилттай тоглуулсан аудиог delivered гэж ACK хийнэ. Байнгын формат, чадвар, тоглуулалтын алдааг failed гэж ACK хийнэ. Түр зуурын таталт, санах ойн хуваарилалт, I2S эсвэл завгүй байдлын алдааг ACK бүү хий; дараагийн лавлагаанд үлдээнэ.

Бичлэгийн квот 512 MiB. 16 kHz, нэг суваг, S16LE WAV-ын зарлаж болох хамгийн урт хугацаа ойролцоогоор 16,777 секунд (4 цаг 39 минут). Бичлэгийн төлөв анхдагчаар 30 хоног хадгалагдана. Төгсгөлийн үр дүн энгийн гарах дарааллаар meeting_result болж ирнэ.

7. Ажиллагаа ба аюулгүй байдлын гэрээ

Тогтвортой танигч

clientId-ийг физик төхөөрөмж бүрт тогтвортой байлгана. Token болон хурлын сэргээх төлөвийг хадгална. Одоогийн ESP32 гарах курсороо RAM-д байлгаж, хүйтэн асаалтын дараа тэгээс үргэлжлүүлнэ. 96-аас ихгүй тэмдэгт бүхий хүйтэн асаалтын bootSessionId үүсгэнэ.

Нэг HTTP төлөвлөгч

Нөөц хязгаартай төхөөрөмж энгийн HTTP ажлыг цуваа болгож, лавлагаа, аудио байршуулалт болон ACK нь TLS санах ойн төлөө өрсөлдөхгүй байх ёстой. Уншигч нэмэхийн оронд идэвхтэй лавлагааг богиносгоно.

Хамгийн бага бодит чадвар

Бодит дэлгэц, чанга яригч, микрофон, кодчилогч болон санах ойн хязгаарыг тодорхойлно. Hub энэ гэрээгээр том аудиог URL болгож, текстийг танаж, дэмжигдээгүй гаралтыг шүүнэ.

Медиагийн аюулгүй байдал

Зөвхөн Hub-ийн буцаасан, ижил эх үүсвэрийн медиа URL ашиглана. Одоогийн ESP32 аудио зам /api/im-gateway/v1/media/ гэж эхлэхийг нэмж шаардана.

Санал болгох дахин оролдлого

Хослуулалт ба гар барилтад 2 секундээс 60 секунд хүртэлх экспоненциал хоцролт ашиглана. Лавлагаа амжилтгүй болсны дараа дор хаяж 3 секунд хүлээнэ. accepted=true бүхий 200 хүлээн авсны дараа /incoming хүсэлтийг хэзээ ч дахин бүү илгээ. Тодорхой амжилтын хариу ирээгүй, бизнесийн үйлдэл дор хаяж нэг удаагийн боловсруулалтыг тэсвэрлэх үед л хязгаарлагдмал тоогоор хоцролттой дахин оролдож, ижил eventId/messageId-ийг дахин ашиглана. Одоогийн ESP32 дуу илгээлтийг хамгийн ихдээ гурван удаа оролдоно.

/incoming тогтвортой идемпотент бишHub IM цөм одоогоор messageId-ээр ойролцоогоор 10 секундын турш санах ойд, боломжийн хэрээр давхардал арилгана. Энэ төлөв хадгалагдахгүй. Цонх өнгөрсний дараа эсвэл Hub дахин ассаны дараа дахин илгээвэл дахин боловсруулагдаж болно. Төхөөрөмжийн гарцын хариу энгийн ажиллагаанд duplicate-ийг false гэж мэдээлдэг тул энэ нь тогтвортой идемпотентийн баталгаа биш. Хязгааргүй дахин оролдлогоос зайлсхийнэ.
