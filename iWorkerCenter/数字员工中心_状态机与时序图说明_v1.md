# 数字员工中心：状态机与时序图说明 v1

## 1. 目标

本文件用于整理数字员工中心 V1 的关键状态机与核心时序，作为后续：
- 状态流转实现
- 事件审计实现
- 接口语义统一
- 前后端状态展示
- 自动化测试设计

的统一依据。

本文件重点覆盖：
- 协作委托任务状态机
- 工作流实例状态机
- 工作流步骤实例状态机
- 配置下发状态机
- 关键业务时序

---

## 2. 设计原则

### 2.1 先统一状态语义，再落接口
接口只是触发动作，真正要稳定的是对象状态机。

### 2.2 工作流推进不能绕开协作任务
流程编排决定“下一步是谁”，实际执行仍通过协作任务落地。

### 2.3 每次状态变化都应可审计
关键状态变化建议落事件表：
- `communication_message_events`
- `workflow_instance_events`
- 后续可补统一 `audit_events`

### 2.4 状态值尽量少而稳定
V1 不追求细粒度到难以维护，优先保证：
- 管理端能看懂
- 接口语义清晰
- 测试容易覆盖

### 2.5 超时、拒绝、取消优先做成显式分支
不要用模糊字段表达异常流转，优先使用明确状态和事件。

---

## 3. 对象与状态总览

建议 V1 重点统一以下状态对象：

1. `CommunicationMessage`
2. `WorkflowInstance`
3. `WorkflowStepInstance`
4. `ConfigBundleVersion`
5. `ConfigApplyRecord`

其中：
- `CommunicationMessage` 表示实际协作任务
- `WorkflowInstance` 表示整个流程运行态
- `WorkflowStepInstance` 表示单个步骤执行态
- `ConfigBundleVersion` 表示配置包发布态
- `ConfigApplyRecord` 表示客户端应用结果态

---

## 4. 协作委托任务状态机

## 4.1 对象
对应：`CommunicationMessage`

用途：
- 数字员工之间的一次实际委托任务
- 也是工作流步骤落地后的执行载体

## 4.2 建议状态
- `standby`
- `accepted`
- `processing`
- `completed`
- `rejected`
- `expired`
- `cancelled`

说明：
- `standby`：已创建，待接收
- `accepted`：已接受，尚未正式开始执行
- `processing`：执行中
- `completed`：已完成并返回结果
- `rejected`：接收方明确拒绝
- `expired`：超时未处理
- `cancelled`：被上游取消，不再执行

V1 如果想更简化，也可不单独对外暴露 `accepted`，但内部保留更清晰。

## 4.3 状态流转图（文本）

```text
standby
 ├─ accept ───────> accepted
 │                    └─ start ─────> processing ── complete ──> completed
 │
 ├─ reject ───────> rejected
 ├─ expire ───────> expired
 └─ cancel ───────> cancelled

accepted
 ├─ start ────────> processing
 ├─ reject ───────> rejected
 ├─ expire ───────> expired
 └─ cancel ───────> cancelled

processing
 ├─ complete ─────> completed
 ├─ cancel ───────> cancelled
 └─ timeout ──────> expired
```

## 4.4 接口动作与状态映射
- `POST /runtime/collaboration/requests`：创建为 `standby`
- `POST /runtime/collaboration/requests/{id}/accept`：`standby -> accepted`
- `POST /runtime/collaboration/requests/{id}/start`：`accepted -> processing`
- `POST /runtime/collaboration/requests/{id}/complete`：`processing -> completed`
- `POST /runtime/collaboration/requests/{id}/reject`：`standby|accepted -> rejected`

如果后续需要管理员终止任务，可补：
- `POST /admin/communications/{id}/cancel`

## 4.5 关键约束
- `completed`、`rejected`、`expired`、`cancelled` 应视为终态
- 终态后不可再次 `accept` / `start` / `complete`
- `complete` 前建议要求已有 `accepted` 或 `processing`
- 若流程步骤已绑定该任务，则任务终态应反向驱动步骤态更新

## 4.6 建议事件类型
- `created`
- `accepted`
- `started`
- `completed`
- `rejected`
- `expired`
- `cancelled`
- `result_updated`

---

## 5. 工作流实例状态机

## 5.1 对象
对应：`WorkflowInstance`

用途：
- 表示一个具体业务事务的一次流程运行
- 关注“整个流程走到哪里”

## 5.2 建议状态
- `running`
- `paused`
- `completed`
- `rejected`
- `cancelled`
- `timeout`

说明：
- `running`：流程已启动，且至少当前可继续推进
- `paused`：人为暂停或等待特殊处理
- `completed`：流程整体完成
- `rejected`：某一步拒绝且按规则导致流程终止
- `cancelled`：发起方或管理员取消
- `timeout`：整体流程超时结束

V1 可不单独加 `draft`，因为实例一旦创建即进入运行态。

## 5.3 状态流转图（文本）

```text
running
 ├─ pause ────────> paused
 ├─ complete ─────> completed
 ├─ reject_end ───> rejected
 ├─ cancel ───────> cancelled
 └─ timeout ──────> timeout

paused
 ├─ resume ───────> running
 └─ cancel ───────> cancelled
```

## 5.4 接口动作与状态映射
- `POST /runtime/workflows/instances`：创建为 `running`
- `POST /runtime/workflows/instances/{id}/pause`：`running -> paused`
- `POST /runtime/workflows/instances/{id}/resume`：`paused -> running`
- `POST /runtime/workflows/instances/{id}/cancel`：`running|paused -> cancelled`
- `POST /runtime/workflows/steps/{id}/complete`：可能推动实例继续保持 `running`，或进入 `completed`
- `POST /runtime/workflows/steps/{id}/reject`：可能推动实例进入 `rejected`，也可能回退/重派后继续 `running`

## 5.5 关键约束
- 实例终态：`completed` / `rejected` / `cancelled` / `timeout`
- 进入终态后，未完成步骤应一并结束或标记不可继续
- `current_step_id` 应始终指向当前活跃步骤；终态后可置空或保留最后一步
- 实例状态不应直接跳过步骤态计算而被随意改写

## 5.6 建议事件类型
- `created`
- `paused`
- `resumed`
- `step_advanced`
- `completed`
- `rejected`
- `cancelled`
- `timeout`
- `reassigned`

---

## 6. 工作流步骤实例状态机

## 6.1 对象
对应：`WorkflowStepInstance`

用途：
- 表示流程中的某一步实际执行记录
- 常通过 `delegation_message_id` 绑定到实际协作任务

## 6.2 建议状态
- `standby`
- `accepted`
- `processing`
- `completed`
- `rejected`
- `skipped`
- `timeout`
- `cancelled`

说明：
- `standby`：该步骤已生成，但尚未被处理人接收
- `accepted`：处理人已接收
- `processing`：处理中
- `completed`：步骤完成
- `rejected`：步骤被明确拒绝
- `skipped`：因条件分支、提前终止等被跳过
- `timeout`：步骤执行超时
- `cancelled`：上层流程取消导致该步骤终止

## 6.3 状态流转图（文本）

```text
standby
 ├─ accept ───────> accepted
 ├─ reject ───────> rejected
 ├─ skip ─────────> skipped
 ├─ timeout ──────> timeout
 └─ cancel ───────> cancelled

accepted
 ├─ start ────────> processing
 ├─ reject ───────> rejected
 ├─ timeout ──────> timeout
 └─ cancel ───────> cancelled

processing
 ├─ complete ─────> completed
 ├─ reject ───────> rejected
 ├─ timeout ──────> timeout
 └─ cancel ───────> cancelled
```

## 6.4 与协作任务状态的关系

如果步骤通过 `delegation_message_id` 绑定协作任务，建议采用镜像驱动：

- `CommunicationMessage.standby` → `WorkflowStepInstance.standby`
- `CommunicationMessage.accepted` → `WorkflowStepInstance.accepted`
- `CommunicationMessage.processing` → `WorkflowStepInstance.processing`
- `CommunicationMessage.completed` → `WorkflowStepInstance.completed`
- `CommunicationMessage.rejected` → `WorkflowStepInstance.rejected`
- `CommunicationMessage.expired` → `WorkflowStepInstance.timeout`
- `CommunicationMessage.cancelled` → `WorkflowStepInstance.cancelled`

说明：
- 步骤状态是流程视角
- 任务状态是执行视角
- V1 最简单做法是任务态驱动步骤态，而不是两边各自独立推进

## 6.5 接口动作与状态映射
- `POST /runtime/workflows/steps/{id}/accept`：`standby -> accepted`
- `POST /runtime/workflows/steps/{id}/start`：`accepted -> processing`
- `POST /runtime/workflows/steps/{id}/complete`：`processing -> completed`
- `POST /runtime/workflows/steps/{id}/reject`：`standby|accepted|processing -> rejected`
- `POST /admin/workflows/steps/{id}/timeout-handle`：`timeout` 后触发后续处理
- `POST /admin/workflows/steps/{id}/reassign`：通常不直接改终态，而是生成新分配逻辑或新任务

## 6.6 拒绝后的处理建议
V1 建议只支持三种简单策略：
- `terminate_workflow`：步骤拒绝后，流程直接结束为 `rejected`
- `return_previous_step`：退回上一步重新处理
- `manual_reassign`：等待管理员改派

其中：
- V1 最小闭环优先支持 `terminate_workflow`
- `return_previous_step` 和 `manual_reassign` 可先保留规则字段，分阶段实现

## 7. 配置下发状态机

## 7.1 配置包状态
对应：`ConfigBundleVersion`

建议状态：
- `draft`
- `published`
- `rolled_back`
- `archived`

状态流转：

```text
draft
 ├─ publish ──────> published
 └─ archive ──────> archived

published
 ├─ rollback ─────> rolled_back
 └─ archive ──────> archived
```

说明：
- `draft`：已生成，尚未对客户端生效
- `published`：已发布，可被客户端拉取
- `rolled_back`：该版本被回滚，不再作为当前有效版本
- `archived`：仅历史保留

## 7.2 客户端应用记录状态
对应：`ConfigApplyRecord`

建议状态：
- `pending`
- `success`
- `failed`
- `skipped`

状态流转：

```text
pending
 ├─ apply_success ─> success
 ├─ apply_failed ──> failed
 └─ skip ──────────> skipped
```

说明：
- `pending`：客户端已收到待应用任务或中心等待回报
- `success`：客户端成功应用
- `failed`：客户端应用失败
- `skipped`：客户端判断该版本无需应用

## 7.3 接口动作与状态映射
- `POST /admin/config-bundles`：创建 `draft`
- `POST /admin/config-bundles/{id}/publish`：`draft -> published`
- `POST /admin/config-bundles/{id}/rollback`：`published -> rolled_back`
- `GET /client/config/version`：查询当前有效发布版本
- `GET /client/config/bundles`：拉取待同步包
- `POST /client/config/apply-result`：驱动 `ConfigApplyRecord` 进入 `success|failed`

## 8. 关键时序：发起协作委托

## 8.1 场景说明
数字员工 A 直接委托数字员工 B 处理一项任务。

## 8.2 时序图（文本）

```text
发起方运行时 -> 数字员工中心: POST /runtime/collaboration/requests
数字员工中心 -> 权限服务: 校验 from -> to 是否允许委托
权限服务 -> 数字员工中心: 返回允许/拒绝
数字员工中心 -> 安全规则服务: 校验消息类型、任务类型、共享范围
安全规则服务 -> 数字员工中心: 返回通过/拦截/需审批
数字员工中心 -> 数据库: 写入 communication_messages(status=standby)
数字员工中心 -> 数据库: 写入 communication_message_events(created)
数字员工中心 -> 接收方任务箱: 投递待办
数字员工中心 -> 发起方运行时: 返回请求创建成功
```

## 8.3 结果分支

### 分支 A：允许直接创建
- 生成 `CommunicationMessage`
- 状态为 `standby`

### 分支 B：命中拒绝规则
- 不创建正式任务，或创建一条被拦截审计记录
- 直接返回错误或受控拒绝结果

### 分支 C：需要审批
- V1 可先不做完整审批流
- 可先落审计记录，并返回“暂不可自动发起”

## 9. 关键时序：接受 / 开始 / 完成协作任务

## 9.1 接受任务

```text
接收方运行时 -> 数字员工中心: POST /runtime/collaboration/requests/{id}/accept
数字员工中心 -> 数据库: 校验当前状态=standby
数字员工中心 -> 数据库: 更新状态 accepted, 写 accepted_at
数字员工中心 -> 数据库: 写入 communication_message_events(accepted)
数字员工中心 -> 接收方运行时: 返回成功
```

## 9.2 开始执行

```text
接收方运行时 -> 数字员工中心: POST /runtime/collaboration/requests/{id}/start
数字员工中心 -> 数据库: 校验当前状态=accepted
数字员工中心 -> 数据库: 更新状态 processing
数字员工中心 -> 数据库: 写入 communication_message_events(started)
数字员工中心 -> 接收方运行时: 返回成功
```

## 9.3 完成任务

```text
接收方运行时 -> 数字员工中心: POST /runtime/collaboration/requests/{id}/complete
数字员工中心 -> 数据库: 校验当前状态=processing
数字员工中心 -> 数据库: 更新 result_summary/result_payload_ref/status=completed
数字员工中心 -> 数据库: 写入 communication_message_events(completed)
数字员工中心 -> 发起方侧视图/历史记录: 更新结果可见性
数字员工中心 -> 接收方运行时: 返回成功
```

## 10. 关键时序：发起工作流实例

## 10.1 场景说明
某业务事务触发流程，中心创建流程实例并生成第一步任务。

## 10.2 时序图（文本）

```text
发起方运行时/业务系统 -> 数字员工中心: POST /runtime/workflows/instances
数字员工中心 -> 数据库: 读取 WorkflowDefinition 与 StepDefinitions
数字员工中心 -> 数字员工中心: 计算第一步
数字员工中心 -> 权限服务: 校验该步候选处理人是否可委托/可执行
权限服务 -> 数字员工中心: 返回结果
数字员工中心 -> 安全规则服务: 校验该步是否允许分配
安全规则服务 -> 数字员工中心: 返回结果
数字员工中心 -> 数据库: 写入 workflow_instances(status=running)
数字员工中心 -> 数据库: 写入 workflow_step_instances(status=standby)
数字员工中心 -> 数据库: 写入 communication_messages(status=standby, workflow_instance_id, workflow_step_instance_id)
数字员工中心 -> 数据库: 回填 workflow_step_instances.delegation_message_id
数字员工中心 -> 数据库: 写入 workflow_instance_events(created/step_advanced)
数字员工中心 -> 目标员工任务箱: 投递待办
数字员工中心 -> 调用方: 返回实例创建成功
```

## 10.3 关键要求
- 第一条步骤任务必须在实例创建时就落地
- `workflow_step_instances` 与 `communication_messages` 必须互相可追踪
- 如果第一步无法合法分配，实例不应进入正常运行态而无任务承接

---

## 11. 关键时序：完成步骤并推进下一步

## 11.1 场景说明
当前步骤完成后，系统计算下一步并生成新的协作任务。

## 11.2 时序图（文本）

```text
处理方运行时 -> 数字员工中心: POST /runtime/workflows/steps/{id}/complete
数字员工中心 -> 数据库: 校验当前步骤状态=processing
数字员工中心 -> 数据库: 更新 workflow_step_instances(status=completed, result_summary, decision)
数字员工中心 -> 数据库: 同步关联 communication_messages(status=completed)
数字员工中心 -> 数字员工中心: 计算下一步骤

alt 存在下一步骤
  数字员工中心 -> 权限服务: 校验下一步候选处理人
  权限服务 -> 数字员工中心: 返回结果
  数字员工中心 -> 安全规则服务: 校验下一步是否允许分配
  安全规则服务 -> 数字员工中心: 返回结果
  数字员工中心 -> 数据库: 创建下一条 workflow_step_instances(status=standby)
  数字员工中心 -> 数据库: 创建下一条 communication_messages(status=standby)
  数字员工中心 -> 数据库: 回填 delegation_message_id
  数字员工中心 -> 数据库: 更新 workflow_instances(current_step_id=next_step_id, status=running)
  数字员工中心 -> 数据库: 写入 workflow_instance_events(step_advanced)
  数字员工中心 -> 目标员工任务箱: 投递下一步待办
else 无下一步骤
  数字员工中心 -> 数据库: 更新 workflow_instances(status=completed, completed_at)
  数字员工中心 -> 数据库: 写入 workflow_instance_events(completed)
end

数字员工中心 -> 处理方运行时: 返回成功
```

## 11.3 关键约束
- 步骤完成不等于流程完成
- 只有确认无下一步时，实例才可进入 `completed`
- 下一步任务创建失败时，不应假装流程已成功推进
- 需要保证“当前步骤完成”和“下一步创建”在事务边界内尽量一致

---

## 12. 关键时序：步骤拒绝后的处理

## 12.1 最小闭环策略
V1 建议优先支持：
- 当前步骤拒绝
- 流程直接结束为 `rejected`

## 12.2 时序图（文本）

```text
处理方运行时 -> 数字员工中心: POST /runtime/workflows/steps/{id}/reject
数字员工中心 -> 数据库: 校验步骤当前状态 standby|accepted|processing
数字员工中心 -> 数据库: 更新 workflow_step_instances(status=rejected, rejected_at)
数字员工中心 -> 数据库: 更新关联 communication_messages(status=rejected)
数字员工中心 -> 数据库: 根据 reject_rule 决定流程动作
数字员工中心 -> 数据库: 更新 workflow_instances(status=rejected)
数字员工中心 -> 数据库: 写入 workflow_instance_events(rejected)
数字员工中心 -> 发起方/管理员视图: 显示拒绝结果
数字员工中心 -> 处理方运行时: 返回成功
```

## 12.3 后续增强路线
后续可补：
- 拒绝后退回上一步
- 拒绝后管理员改派
- 拒绝后触发人工审批

## 13. 关键时序：配置下发闭环

## 13.1 发布配置包

```text
管理员 -> 数字员工中心: POST /admin/config-bundles/{id}/publish
数字员工中心 -> 数据库: 校验 bundle 当前状态=draft
数字员工中心 -> 数据库: 更新 config_bundle_versions(status=published, published_at)
数字员工中心 -> 数据库: 为目标客户端生成 config_apply_records(status=pending)
数字员工中心 -> 管理端: 返回发布成功
```

## 13.2 客户端同步并上报结果

```text
DiWorker -> 数字员工中心: GET /client/config/version
数字员工中心 -> DiWorker: 返回当前有效版本
DiWorker -> 数字员工中心: GET /client/config/bundles
数字员工中心 -> DiWorker: 返回待应用配置包
DiWorker -> 本地: 应用配置
DiWorker -> 数字员工中心: POST /client/config/apply-result
数字员工中心 -> 数据库: 更新 config_apply_records(apply_status=success|failed)
数字员工中心 -> 管理端: 下发结果可见
```

## 14. 建议的事务边界

以下动作建议尽量放在单事务内完成：

### 14.1 创建协作任务
- 写 `communication_messages`
- 写 `communication_message_events(created)`

### 14.2 创建流程实例并生成首步任务
- 写 `workflow_instances`
- 写 `workflow_step_instances`
- 写 `communication_messages`
- 回填 `delegation_message_id`
- 写 `workflow_instance_events`

### 14.3 完成步骤并推进下一步
- 更新当前 `workflow_step_instances`
- 更新当前 `communication_messages`
- 创建下一步 `workflow_step_instances`
- 创建下一步 `communication_messages`
- 更新 `workflow_instances.current_step_id`
- 写 `workflow_instance_events`

这样可以避免：
- 步骤已完成但下一步未创建
- 流程已推进但任务箱没有任务
- 任务已创建但步骤未关联

---

## 15. 测试用例建议

## 15.1 协作任务
- 创建后状态为 `standby`
- `standby` 可接受
- `accepted` 可开始
- `processing` 可完成
- 终态不可重复流转
- 拒绝后不能再完成

## 15.2 工作流实例
- 创建实例后自动生成首步任务
- 首步完成后生成下一步
- 最后一步完成后实例进入 `completed`
- 步骤拒绝后实例进入 `rejected`
- 暂停后不可继续自动推进

## 15.3 步骤与任务联动
- 任务接受后步骤同步 `accepted`
- 任务完成后步骤同步 `completed`
- 任务拒绝后步骤同步 `rejected`
- 任务超时后步骤同步 `timeout`

## 15.4 配置下发
- 草稿发布后进入 `published`
- 客户端上报成功后 apply record 变为 `success`
- 客户端上报失败后 apply record 变为 `failed`
- 回滚后旧版本不再作为当前有效发布版本

---

## 16. V1 落地建议

V1 建议优先实现以下最小状态机：

### 16.1 协作任务
- `standby -> accepted -> processing -> completed`
- `standby|accepted|processing -> rejected`

### 16.2 工作流实例
- `running -> completed`
- `running -> rejected`
- `running -> paused -> running`
- `running|paused -> cancelled`

### 16.3 工作流步骤
- `standby -> accepted -> processing -> completed`
- `standby|accepted|processing -> rejected`

### 16.4 配置下发
- `draft -> published -> rolled_back`
- `pending -> success|failed`

先把这套最小闭环打通，再补：
- timeout
- skipped
- manual_reassign
- return_previous_step
- 审批分支
- 更细粒度事件投影

---

## 17. 一句话总结

**数字员工中心 V1 的状态机设计应坚持“流程决定下一步、协作任务承载执行、状态变化全程可审计”，并以步骤实例与协作任务的联动作为整套流转机制的核心。**
