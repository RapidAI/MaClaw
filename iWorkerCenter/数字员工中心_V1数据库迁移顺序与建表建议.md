# 数字员工中心：V1 数据库迁移顺序与建表建议

## 1. 目标

本文件用于把《数据库与表结构草案》《事务边界矩阵》《实现切片建议》进一步收敛成可直接执行的 migration 方案。

重点明确：
- 第一批 migration 应按什么顺序落
- 哪些表先建，哪些后建
- 哪些索引和唯一约束第一批必须带上
- 外键该如何控制，避免一开始把运行时链路绑死
- 回滚和测试时要注意什么

V1 原则：
- 先保证主链路一致性
- 先保证可演进
- 不为“理论最完美关系图”牺牲实现节奏

---

## 2. 总体迁移原则

### 2.1 按业务依赖顺序建表
优先顺序不是按文档顺序，而是按运行依赖：
1. 基础主档
2. 低耦合配置表
3. 协作运行态
4. 工作流运行态
5. 安全与审计
6. 配置下发

### 2.2 先建必要索引，不一次上满所有索引
V1 第一批优先建：
- 主键
- 唯一键
- 主链路查询索引
- 状态字段索引

统计分析类索引可后补。

### 2.3 外键策略偏保守
V1 建议：
- 对关键强一致关联，可保留外键
- 对高频运行态链路，不要过度依赖数据库级级联删除
- 尽量避免 `ON DELETE CASCADE` 影响审计追溯

### 2.4 审计与事件表优先保留数据
像：
- `communication_message_events`
- `workflow_instance_events`
- `proxy_request_records`
- `security_policy_hit_records`

不建议依赖级联删除清理。

---

## 3. 推荐 migration 批次总览

建议按 8 批迁移：

1. 基础骨架 migration
2. colleagues
3. capabilities
4. collaboration
5. workflows
6. security + modelrouting + proxy
7. configsync
8. 补充索引与初始化数据

---

## 4. Migration 01：基础骨架

## 4.1 目标
建立 migration 管理基础，先不急着建所有业务表。

## 4.2 本批建议内容
- migration 版本表（若框架未自带）
- 通用时间字段规范
- 通用 ID 类型规范

## 4.3 建议约定
- 主键统一 `varchar/string id`
- 时间字段统一：
  - `created_at`
  - `updated_at`
  - 按需增加 `completed_at` / `published_at` / `rejected_at`
- 状态字段统一 `varchar`

## 4.4 回滚建议
- 基础骨架 migration 一般只允许开发环境回滚
- 一旦进入联调环境，优先新增前向 migration，不频繁改历史版本

---

## 5. Migration 02：colleagues

## 5.1 建表顺序
1. `colleagues`

## 5.2 建议字段重点
- `id`
- `name`
- `code`
- `status`
- `default_model_policy_id`（若首批保留）
- `created_at`
- `updated_at`

## 5.3 第一批必须索引
- PK：`id`
- UNIQUE：`code`
- INDEX：`status`
- 可选 INDEX：`name`

## 5.4 第一批外键建议
- `default_model_policy_id` 若 modelrouting 还未落地，可先不加数据库外键
- 先由 service 做存在性校验

## 5.5 回滚注意
- 若后续表已引用 `colleagues`，不要在共享环境直接回滚此 migration

---

## 6. Migration 03：capabilities

## 6.1 建表顺序
1. `capability_packages`
2. `capability_package_versions`
3. `colleague_capability_bindings`

## 6.2 表关系建议

### capability_packages
主档表，存能力包稳定标识与当前状态。

### capability_package_versions
版本表，存导入版本、来源版本、审核状态、元数据摘要。

### colleague_capability_bindings
员工与能力包绑定关系表。

## 6.3 第一批必须索引

### capability_packages
- PK：`id`
- UNIQUE：`package_code` 或外部唯一标识
- INDEX：`status`

### capability_package_versions
- PK：`id`
- INDEX：`capability_package_id`
- INDEX：`review_status`
- UNIQUE（可选）：`(capability_package_id, version)`

### colleague_capability_bindings
- PK：`id`
- INDEX：`colleague_id`
- INDEX：`capability_package_id`
- UNIQUE：`(colleague_id, capability_package_id)`

## 6.4 外键建议
- `capability_package_versions.capability_package_id` 可加 FK
- `colleague_capability_bindings.colleague_id` 可加 FK -> `colleagues.id`
- `colleague_capability_bindings.capability_package_id` 可加 FK -> `capability_packages.id`
- 不建议级联删除，建议 restrict 或 no action

## 6.5 回滚注意
- 若已经存在绑定数据，不建议直接回滚 package 主表

---

## 7. Migration 04：collaboration

## 7.1 建表顺序
1. `collaboration_permissions`
2. `communication_messages`
3. `communication_message_events`

之所以先建 permission：
- 逻辑上创建任务前先查权限
- 结构上也比较独立

## 7.2 表职责建议

### collaboration_permissions
存 from/to/任务类型/允许策略。

### communication_messages
运行态主表。

### communication_message_events
任务状态变化事件表。

## 7.3 第一批必须索引

### collaboration_permissions
- PK：`id`
- INDEX：`from_colleague_id`
- INDEX：`to_colleague_id`
- UNIQUE 或半唯一：`(from_colleague_id, to_colleague_id, task_type)`

### communication_messages
- PK：`id`
- INDEX：`from_colleague_id`
- INDEX：`to_colleague_id`
- INDEX：`status`
- INDEX：`workflow_instance_id`
- INDEX：`workflow_step_instance_id`
- 组合 INDEX：`(to_colleague_id, status, created_at)` 用于 inbox

### communication_message_events
- PK：`id`
- INDEX：`message_id`
- INDEX：`event_type`
- INDEX：`created_at`

## 7.4 外键建议
- `communication_messages.from_colleague_id` -> `colleagues.id`
- `communication_messages.to_colleague_id` -> `colleagues.id`
- `communication_message_events.message_id` -> `communication_messages.id`

但建议：
- 不要对事件表做级联删除
- 运行态与审计数据优先保留

## 7.5 建模注意点
- `workflow_instance_id` / `workflow_step_instance_id` 初期可先允许为空
- 因为独立协作任务并不一定来自 workflow

## 7.6 回滚注意
- 若 workflow migration 已上线，再回滚 communication_messages 风险很高

---

## 8. Migration 05：workflows

## 8.1 建表顺序
1. `workflow_definitions`
2. `workflow_step_definitions`
3. `workflow_instances`
4. `workflow_step_instances`
5. `workflow_instance_events`

## 8.2 表职责建议

### workflow_definitions
流程模板主档。

### workflow_step_definitions
模板步骤定义。

### workflow_instances
流程运行实例。

### workflow_step_instances
运行时步骤实例。

### workflow_instance_events
实例级事件表。

## 8.3 第一批必须索引

### workflow_definitions
- PK：`id`
- UNIQUE：`code`
- INDEX：`status`

### workflow_step_definitions
- PK：`id`
- INDEX：`workflow_definition_id`
- INDEX：`step_code`
- UNIQUE：`(workflow_definition_id, step_code)`
- INDEX：`step_order`

### workflow_instances
- PK：`id`
- INDEX：`workflow_definition_id`
- INDEX：`status`
- INDEX：`current_step_id`
- INDEX：`business_key`（如有）

### workflow_step_instances
- PK：`id`
- INDEX：`workflow_instance_id`
- INDEX：`step_definition_id`
- INDEX：`status`
- INDEX：`assignee_colleague_id`
- INDEX：`delegation_message_id`
- UNIQUE（可选谨慎）：`delegation_message_id`

### workflow_instance_events
- PK：`id`
- INDEX：`workflow_instance_id`
- INDEX：`event_type`
- INDEX：`created_at`

## 8.4 外键建议
- `workflow_step_definitions.workflow_definition_id` -> `workflow_definitions.id`
- `workflow_instances.workflow_definition_id` -> `workflow_definitions.id`
- `workflow_instances.current_step_id` -> `workflow_step_instances.id`：第一批可先不加 FK，避免建表顺序和循环依赖变复杂
- `workflow_step_instances.workflow_instance_id` -> `workflow_instances.id`
- `workflow_step_instances.step_definition_id` -> `workflow_step_definitions.id`
- `workflow_step_instances.assignee_colleague_id` -> `colleagues.id`
- `workflow_step_instances.delegation_message_id` -> `communication_messages.id`：可加 FK，但不建议做级联删除
- `workflow_instance_events.workflow_instance_id` -> `workflow_instances.id`

## 8.5 关键建议
### 关于 `current_step_id`
V1 第一批建议：
- 保留字段
- 先不做数据库强 FK
- 由 service 负责一致性

原因：
- workflow_instances 与 workflow_step_instances 存在天然环引用趋势
- 强 FK 会增加 migration 与测试复杂度

## 8.6 回滚注意
- workflow 是高耦合运行态表
- 一旦和 collaboration 联动后，不建议在共享环境做回滚删除
- 用补丁 migration 修正更安全

---

## 9. Migration 06：security + modelrouting + proxy

## 9.1 建表顺序
1. `security_policies`
2. `security_policy_hit_records`
3. `model_endpoints`
4. `model_routing_policies`
5. `proxy_request_records`

## 9.2 第一批必须索引

### security_policies
- PK：`id`
- INDEX：`status`
- INDEX：`policy_type`

### security_policy_hit_records
- PK：`id`
- INDEX：`policy_id`
- INDEX：`decision`
- INDEX：`created_at`
- INDEX：`target_type`

### model_endpoints
- PK：`id`
- UNIQUE：`code`
- INDEX：`status`

### model_routing_policies
- PK：`id`
- UNIQUE：`code`
- INDEX：`status`

### proxy_request_records
- PK：`id`
- INDEX：`request_type`
- INDEX：`status`
- INDEX：`requester_colleague_id`
- INDEX：`created_at`
- INDEX：`completed_at`

## 9.3 外键建议
- `security_policy_hit_records.policy_id` -> `security_policies.id`
- `proxy_request_records.requester_colleague_id` -> `colleagues.id` 可选
- `proxy_request_records.model_policy_id` / `endpoint_id` 如有字段，可先不加强 FK

## 9.4 建模注意点
- `proxy_request_records` 建议保留：
  - `status`
  - `status_code`
  - `latency_ms`
  - `error_message`
  - `completed_at`
- 这样失败请求也可完整审计

---

## 10. Migration 07：configsync

## 10.1 建表顺序
1. `config_bundle_versions`
2. `config_bundle_targets`
3. `config_apply_records`

## 10.2 第一批必须索引

### config_bundle_versions
- PK：`id`
- INDEX：`status`
- INDEX：`published_at`
- UNIQUE（可选）：`(bundle_code, version)`

### config_bundle_targets
- PK：`id`
- INDEX：`config_bundle_version_id`
- INDEX：`target_type`
- INDEX：`target_id`

### config_apply_records
- PK：`id`
- INDEX：`config_bundle_version_id`
- INDEX：`client_id`
- INDEX：`status`
- UNIQUE：`(config_bundle_version_id, client_id)`

## 10.3 外键建议
- `config_bundle_targets.config_bundle_version_id` -> `config_bundle_versions.id`
- `config_apply_records.config_bundle_version_id` -> `config_bundle_versions.id`
- `client_id` 第一批可先不加外键，避免和客户端主档设计耦合过深

## 10.4 建模注意点
- `payload_ref` 优先存引用，不直接塞大 JSON
- apply record 保留：
  - `status`
  - `detail`
  - `error_message`
  - `applied_at`

---

## 11. Migration 08：补充索引与初始化数据

## 11.1 适合放在这一批的内容
- 运行后确认的组合索引
- 初始安全策略样例数据
- 初始模型路由策略样例数据
- 初始系统 colleague / admin colleague（若有）
- 常用 workflow 模板种子数据（如项目明确需要）

## 11.2 为什么不建议一开始就塞进前面 migration
因为：
- 主体表结构先稳定更重要
- 初始化数据往往更容易反复调整
- 将“建表”和“样例数据”拆开，回滚和维护更清晰

---

## 12. 推荐的 migration 文件命名方式

建议按序号 + 语义命名，例如：

```text
0001_init_base.sql
0002_create_colleagues.sql
0003_create_capabilities.sql
0004_create_collaboration.sql
0005_create_workflows.sql
0006_create_security_proxy.sql
0007_create_configsync.sql
0008_seed_and_extra_indexes.sql
```

如果使用 Go migration 文件，也建议保持同样语义。

## 13. 外键与删除策略建议总表

| 表 | 是否建议强 FK | 删除策略建议 |
|---|---|---|
| colleagues | 是（被引用侧） | 不建议物理删除，优先状态禁用 |
| capability_package_versions -> capability_packages | 是 | restrict |
| colleague_capability_bindings -> colleagues/capability_packages | 是 | restrict |
| communication_messages -> colleagues | 是 | restrict |
| communication_message_events -> communication_messages | 是 | restrict，不级联删事件 |
| workflow_step_definitions -> workflow_definitions | 是 | restrict |
| workflow_instances -> workflow_definitions | 是 | restrict |
| workflow_step_instances -> workflow_instances | 是 | restrict |
| workflow_step_instances -> communication_messages | 可选强 FK | restrict |
| workflow_instance_events -> workflow_instances | 是 | restrict |
| security_policy_hit_records -> security_policies | 是 | restrict |
| config_bundle_targets -> config_bundle_versions | 是 | restrict |
| config_apply_records -> config_bundle_versions | 是 | restrict |

结论：
- V1 总体偏向 `restrict/no action`
- 少用 `cascade delete`
- 重要运行数据优先逻辑废弃，不做物理清除

---

## 14. 初始化数据建议

第一批若要准备 seed data，建议只放：
- 一个 admin 测试 colleague
- 一个普通执行 colleague
- 一条默认 collaboration permission
- 一条默认 allow 的 security policy（仅开发环境）
- 一个最简单的 workflow definition + 2 step definitions（仅开发环境）

不建议首批就放：
- 大量样例流程
- 大量能力包样例
- 复杂生产策略

---

## 15. 测试库校验清单

每次 migration 后至少检查：
- 表能否成功创建
- 索引是否存在
- 唯一约束是否生效
- FK 是否符合预期
- 样例插入是否成功
- 关键事务链路是否未被 FK/约束错误阻断

尤其检查：
- workflow step 创建后能否正常回填 `delegation_message_id`
- `config_apply_records` 唯一键是否满足幂等要求
- inbox 查询组合索引是否可用

---

## 16. 回滚策略建议

### 16.1 开发早期
可以回滚、重建、反复调整 schema。

### 16.2 联调开始后
不建议通过删除旧 migration 方式修复问题。
建议：
- 新增修正 migration
- 保证前向兼容
- 数据修复单独出 migration

### 16.3 运行态数据表
以下表一旦开始真实联调，不建议轻易做 destructive rollback：
- `communication_messages`
- `communication_message_events`
- `workflow_instances`
- `workflow_step_instances`
- `workflow_instance_events`
- `proxy_request_records`
- `config_apply_records`

---

## 17. 一句话总结

**V1 数据库 migration 应按“主档先行、运行态随后、审计保留优先、外键保守控制、索引先满足主链路”的顺序推进，避免一开始把 schema 设计成难以落地和难以演进的重型关系网。**
