# 数字员工中心：关键数据流与事务边界矩阵 v1

## 1. 目标

本文件用于把数字员工中心 V1 的关键链路进一步收敛成“数据流 + 事务边界 + 失败补偿”矩阵，方便后续直接指导：
- service 编排实现
- 数据库事务设计
- 事件写入实现
- 异常处理设计
- 集成测试编写

本文件重点关注：
- 输入来自哪里
- 调用了哪些模块
- 写了哪些表
- 哪些动作必须同事务
- 哪些失败需要补偿或回滚

---

## 2. 使用原则

### 2.1 先保主链路一致，再考虑异步优化
V1 优先保证：
- 数据不乱
- 状态一致
- 审计可追溯

不要过早把关键链路拆成大量异步步骤。

### 2.2 事务边界只包本地一致性
数据库事务用于保证本地写入一致：
- 主记录
- 状态变更
- 事件记录
- 关联关系回填

外部调用：
- hubcenter
- 外部 LLM / API
- 对外连接器

不应长时间持有数据库事务。

### 2.3 失败后优先显式可见
V1 失败处理原则：
- 不隐藏失败
- 不假装成功
- 要么整体回滚
- 要么明确留下失败状态/失败记录

---

## 3. 链路总览矩阵

| 链路 | 发起方 | 主负责模块 | 关键写表 | 是否强事务 | 是否需补偿 |
|---|---|---|---|---|---|
| 创建数字员工 | 管理端 | colleagues | `colleagues` | 是 | 否 |
| 导入能力包 | 管理端 | capabilities | `capability_packages`, `capability_package_versions` | 是 | 视外部下载而定 |
| 绑定能力包到员工 | 管理端 | capabilities | `colleague_capability_bindings` | 是 | 否 |
| 创建协作任务 | 运行时 | collaboration | `communication_messages`, `communication_message_events` | 是 | 否 |
| 接受/开始/完成协作任务 | 运行时 | collaboration | `communication_messages`, `communication_message_events` | 是 | 否 |
| 创建流程实例并生成首步任务 | 运行时/业务系统 | workflows + collaboration | `workflow_instances`, `workflow_step_instances`, `communication_messages`, `workflow_instance_events` | 是 | 否 |
| 完成步骤并推进下一步 | 运行时 | workflows + collaboration | `workflow_step_instances`, `communication_messages`, `workflow_instances`, `workflow_instance_events` | 是 | 否 |
| 步骤拒绝导致流程结束 | 运行时 | workflows + collaboration | `workflow_step_instances`, `communication_messages`, `workflow_instances`, `workflow_instance_events` | 是 | 否 |
| 协作/流程前规则校验 | collaboration/workflows/proxy | security | `security_policy_hit_records` | 否/小事务 | 否 |
| 代理 LLM/API 请求 | 客户端/运行时 | proxy | `proxy_request_records` | 分段事务 | 需要失败记录 |
| 创建配置包 | 管理端 | configsync | `config_bundle_versions`, `config_bundle_targets` | 是 | 否 |
| 发布配置包 | 管理端 | configsync | `config_bundle_versions`, `config_apply_records` | 是 | 否 |
| 客户端上报应用结果 | DiWorker | configsync | `config_apply_records` | 是 | 否 |

## 4. 链路一：创建数字员工

## 4.1 输入
- 管理端请求 `POST /admin/colleagues`
- DTO：`CreateColleagueRequest`

## 4.2 输出
- 返回 `colleague_id`
- 主档可被管理端与客户端查询

## 4.3 主要调用
```text
ColleagueHandler
  -> ColleagueService
  -> ColleagueRepo
```

## 4.4 写表
- `colleagues`

## 4.5 事务边界
建议单事务：
- 插入 `colleagues`

## 4.6 失败处理
- 参数非法：直接返回错误
- 主键/名称唯一约束冲突：回滚并返回业务错误

## 4.7 实现注意点
- `status=disabled` 的员工创建后不应出现在可分配候选中
- `default_model_policy_id` 若传入，建议先做存在性校验

---

## 5. 链路二：导入能力包

## 5.1 输入
- 管理端请求 `POST /admin/capabilities/import`
- DTO：`ImportCapabilityRequest`

## 5.2 输出
- 返回 `capability_id`
- 本地能力包进入待审核或已安装状态

## 5.3 主要调用
```text
CapabilityImportHandler
  -> CapabilityImportService
  -> 外部 hubcenter client
  -> CapabilityPackageRepo
  -> CapabilityPackageVersionRepo
```

## 5.4 写表
- `capability_packages`
- `capability_package_versions`

## 5.5 事务边界
建议分两段：

### 段 A：事务外
- 调 hubcenter 获取元数据/下载清单

### 段 B：本地事务内
- 插入 `capability_packages`
- 插入 `capability_package_versions`

## 5.6 失败处理
- 外部源读取失败：不写本地记录，直接返回失败
- 本地事务失败：整体回滚，不保留半条能力包记录

## 5.7 实现注意点
- 外部下载完成前不要先写“半初始化状态”记录，除非明确要支持导入中状态
- V1 更简单做法：下载成功后再入库

---

## 6. 链路三：绑定能力包到员工

## 6.1 输入
- 管理端请求 `POST /admin/capabilities/{id}/bind`
- DTO：`BindCapabilityRequest`

## 6.2 输出
- 绑定关系建立
- 客户端后续可通过聚合查询拿到该能力

## 6.3 主要调用
```text
CapabilityBindingHandler
  -> CapabilityBindingService
  -> CapabilityPackageRepo
  -> ColleagueRepo
  -> CapabilityBindingRepo
```

## 6.4 写表
- `colleague_capability_bindings`

## 6.5 事务边界
建议单事务：
- 校验员工存在
- 校验能力包存在/可绑定
- upsert 或插入绑定记录

## 6.6 失败处理
- 员工不存在：回滚
- 能力包不存在或未审核通过：回滚
- 唯一约束冲突：返回“已绑定”或改为幂等成功

## 6.7 实现注意点
- 建议绑定接口做成幂等
- 如果能力包 `status=disabled`，默认不允许新绑定

---

## 7. 链路四：创建协作任务

## 7.1 输入
- 运行时请求 `POST /runtime/collaboration/requests`
- DTO：`CreateCollaborationRequest`

## 7.2 输出
- `CommunicationMessage` 创建成功
- 状态为 `standby`
- 任务进入对方 inbox 可见范围

## 7.3 主要调用
```text
CollaborationHandler
  -> CollaborationService
  -> CollaborationPermissionService
  -> SecurityCheckService
  -> CommunicationMessageRepo
  -> CommunicationMessageEventRepo
```

## 7.4 读对象
- `collaboration_permissions`
- `security_policies`
- `colleagues`

## 7.5 写表
- `communication_messages`
- `communication_message_events`
- 可选：`security_policy_hit_records`

## 7.6 事务边界
建议：

### 事务外
- 权限规则读取
- 安全规则计算

### 本地事务内
- 插入 `communication_messages`
- 插入 `communication_message_events(created)`
- 如需记录命中，可插入 `security_policy_hit_records`

## 7.7 失败处理
- 权限不允许：不写任务主记录
- 安全规则拦截：不写正式任务主记录，必要时只写命中记录
- 数据写入失败：整体回滚

## 7.8 实现注意点
- “任务箱可见”优先通过查询 `communication_messages(status in active)` 实现，不必一开始单独建 inbox 表
- 受托方是 `disabled` 员工时，应直接拒绝创建

---

## 8. 链路五：协作任务状态推进

## 8.1 输入
- `POST /runtime/collaboration/requests/{id}/accept`
- `POST /runtime/collaboration/requests/{id}/start`
- `POST /runtime/collaboration/requests/{id}/complete`
- `POST /runtime/collaboration/requests/{id}/reject`

## 8.2 输出
- 协作任务状态变化
- 事件记录补齐
- 若绑定流程步骤，则步骤状态同步变化

## 8.3 主要调用
```text
CollaborationLifecycleHandler
  -> CollaborationLifecycleService
  -> CommunicationMessageRepo
  -> CommunicationMessageEventRepo
  -> WorkflowStepSyncService(或 workflows service)
```

## 8.4 写表
- `communication_messages`
- `communication_message_events`
- 可联动：`workflow_step_instances`
- 可联动：`workflow_instances`

## 8.5 事务边界

### A. 普通独立协作任务
单事务：
- 更新 `communication_messages`
- 写 `communication_message_events`

### B. 绑定流程步骤的协作任务
单事务内尽量保证：
- 更新 `communication_messages`
- 写 `communication_message_events`
- 更新 `workflow_step_instances`
- 如有必要，更新 `workflow_instances`

## 8.6 失败处理
- 状态不合法：拒绝推进
- 写事件失败：整体回滚
- 步骤同步失败：整体回滚，避免任务态与步骤态不一致

## 8.7 实现注意点
- 协作任务终态建议统一驱动绑定步骤终态
- 若未来支持人工改派，旧任务应显式 `cancelled`

---

## 9. 链路六：创建流程实例并生成首步任务

## 9.1 输入
- `POST /runtime/workflows/instances`
- DTO：`CreateWorkflowInstanceRequest`

## 9.2 输出
- `WorkflowInstance` 创建
- 首个 `WorkflowStepInstance` 创建
- 对应 `CommunicationMessage` 创建
- `delegation_message_id` 回填完成

## 9.3 主要调用
```text
WorkflowRuntimeHandler
  -> WorkflowRuntimeService
  -> WorkflowDefinitionRepo
  -> WorkflowStepDefinitionRepo
  -> CollaborationPermissionService
  -> SecurityCheckService
  -> CommunicationMessageRepo
  -> WorkflowInstanceRepo
  -> WorkflowStepInstanceRepo
  -> WorkflowInstanceEventRepo
```

## 9.4 读对象
- `workflow_definitions`
- `workflow_step_definitions`
- `collaboration_permissions`
- `security_policies`
- `colleagues`

## 9.5 写表
- `workflow_instances`
- `workflow_step_instances`
- `communication_messages`
- `workflow_instance_events`
- 可选：`communication_message_events`

## 9.6 事务边界
建议：

### 事务外
- 读取流程定义
- 计算第一步
- 读取权限与安全规则

### 本地事务内
- 插入 `workflow_instances`
- 插入 `workflow_step_instances`
- 插入 `communication_messages`
- 回填 `workflow_step_instances.delegation_message_id`
- 插入 `workflow_instance_events(created/step_advanced)`
- 可选插入 `communication_message_events(created)`

## 9.7 失败处理
- 模板不存在/未激活：直接失败
- 首步处理人不可分配：直接失败，不创建实例
- 事务内任一步失败：整体回滚

## 9.8 实现注意点
- 不应出现实例创建成功但没有首步任务
- 不应出现步骤记录已创建但 `delegation_message_id` 为空且系统又继续运行
- `current_step_id` 应在首步创建时一并写入

---

## 10. 链路七：完成步骤并推进下一步

## 10.1 输入
- `POST /runtime/workflows/steps/{id}/complete`
- DTO：`CompleteWorkflowStepRequest`

## 10.2 输出
- 当前步骤完成
- 当前协作任务完成
- 若有下一步，则下一步骤与下一任务生成
- 若无下一步，则流程实例完成

## 10.3 主要调用
```text
WorkflowStepLifecycleHandler
  -> WorkflowStepLifecycleService
  -> WorkflowStepInstanceRepo
  -> WorkflowInstanceRepo
  -> WorkflowDefinitionRepo / WorkflowStepDefinitionRepo
  -> CollaborationPermissionService
  -> SecurityCheckService
  -> CommunicationMessageRepo
  -> WorkflowInstanceEventRepo
```

## 10.4 写表
- 更新 `workflow_step_instances`
- 更新 `communication_messages`
- 更新/插入 `workflow_instances`
- 插入新的 `workflow_step_instances`
- 插入新的 `communication_messages`
- 插入 `workflow_instance_events`
- 可选插入 `communication_message_events`

## 10.5 事务边界
建议强事务：
- 更新当前步骤为 `completed`
- 更新当前任务为 `completed`
- 计算下一步结果后：
  - 若存在下一步：插入下一步骤、插入下一任务、回填 `delegation_message_id`、更新实例 `current_step_id`
  - 若不存在下一步：更新实例为 `completed`
- 写事件

## 10.6 失败处理
- 当前步骤状态非法：拒绝操作
- 当前任务无法同步完成：整体回滚
- 下一步创建失败：整体回滚，不能只完成当前步
- 事件写入失败：整体回滚

## 10.7 实现注意点
- “当前步完成”和“下一步生成”必须视为同一业务原子操作
- 若后续做异步消息通知，也应在事务提交后触发，而不是事务中发外部通知

---

## 11. 链路八：步骤拒绝导致流程结束

## 11.1 输入
- `POST /runtime/workflows/steps/{id}/reject`
- DTO：`RejectWorkflowStepRequest`

## 11.2 输出
- 当前步骤变为 `rejected`
- 当前任务变为 `rejected`
- 流程实例根据规则结束为 `rejected` 或进入其他分支

## 11.3 主要调用
```text
WorkflowStepLifecycleHandler
  -> WorkflowStepLifecycleService
  -> WorkflowStepInstanceRepo
  -> CommunicationMessageRepo
  -> WorkflowInstanceRepo
  -> WorkflowInstanceEventRepo
```

## 11.4 写表
- `workflow_step_instances`
- `communication_messages`
- `workflow_instances`
- `workflow_instance_events`
- 可选：`communication_message_events`

## 11.5 事务边界
建议单事务：
- 更新当前步骤状态
- 更新当前任务状态
- 更新流程实例状态
- 写事件

## 11.6 失败处理
- 任一状态更新失败：整体回滚
- `reject_action` 非法：直接返回错误

## 11.7 实现注意点
- V1 最小闭环优先只支持 `terminate_workflow`
- `return_previous_step` / `manual_reassign` 建议先在字段层支持，不急于一次全部实现

---

## 12. 链路九：规则校验

## 12.1 输入
- 协作创建前
- 流程分配前
- 代理请求前
- 显式接口 `POST /runtime/security/check`

## 12.2 输出
- `allowed` / `blocked` / `need_approval`
- 命中规则记录可选写入

## 12.3 主要调用
```text
SecurityCheckService
  -> SecurityPolicyRepo
  -> SecurityPolicyHitRecordRepo
```

## 12.4 写表
- `security_policy_hit_records`（建议）

## 12.5 事务边界
- 规则计算本身无需大事务
- 若记录命中结果，可单独小事务写入 `security_policy_hit_records`

## 12.6 失败处理
- 规则引擎异常：默认按保守策略处理
- V1 建议：
  - 协作/流程关键链路校验失败时默认拒绝
  - 管理端测试接口可返回引擎错误信息

## 12.7 实现注意点
- 不要让每个模块复制规则判断代码
- 规则命中记录可按需采样，但关键拦截建议全量落库

---

## 13. 链路十：代理 LLM / API 请求

## 13.1 输入
- `POST /proxy/llm`
- `POST /proxy/api`

## 13.2 输出
- 返回代理结果或失败信息
- 请求审计记录可追踪

## 13.3 主要调用
```text
ProxyLLMService / ProxyAPIService
  -> SecurityCheckService
  -> ModelRoutingRecommendService
  -> ProxyRequestRecordRepo
  -> 外部 provider client
```

## 13.4 写表
- `proxy_request_records`
- 可选：`security_policy_hit_records`

## 13.5 事务边界
建议分段：

### 段 A：请求开始前小事务
- 插入 `proxy_request_records(status=pending/in_progress)`

### 段 B：事务外
- 调外部模型/API

### 段 C：请求结束后小事务
- 更新 `proxy_request_records(status=success|failed|blocked, status_code, latency_ms, completed_at)`

## 13.6 失败处理
- 安全规则拦截：更新记录为 `blocked`
- 外部调用失败：更新记录为 `failed`
- 外部超时：更新记录为 `timeout` 或 `failed`

## 13.7 实现注意点
- 外部调用绝不能包在数据库长事务里
- 即使外部调用失败，也应尽量保留请求记录，方便审计

---

## 14. 链路十一：创建配置包

## 14.1 输入
- `POST /admin/config-bundles`
- DTO：`CreateConfigBundleRequest`

## 14.2 输出
- 配置包进入 `draft`
- 目标范围已记录

## 14.3 主要调用
```text
ConfigBundleHandler
  -> ConfigBundleService
  -> ConfigBundleRepo
  -> ConfigBundleTargetRepo
```

## 14.4 写表
- `config_bundle_versions`
- `config_bundle_targets`

## 14.5 事务边界
建议单事务：
- 插入 `config_bundle_versions`
- 插入 `config_bundle_targets`

## 14.6 失败处理
- payload 引用无效：拒绝创建
- 任一写入失败：整体回滚

## 14.7 实现注意点

## 15. 链路十二：发布配置包

## 15.1 输入
- `POST /admin/config-bundles/{id}/publish`

## 15.2 输出
- 配置包状态变为 `published`
- 目标客户端 `ConfigApplyRecord` 生成

## 15.3 主要调用
```text
ConfigBundlePublishHandler
  -> ConfigBundleService
  -> ConfigBundleRepo
  -> ConfigApplyRecordRepo
```

## 15.4 写表
- `config_bundle_versions`
- `config_apply_records`

## 15.5 事务边界
建议单事务：
- 更新 `config_bundle_versions.status=published`
- 批量插入 `config_apply_records(status=pending)`

## 15.6 失败处理
- 已发布版本重复发布：幂等返回或拒绝
- apply records 写入失败：整体回滚，不能出现已发布但无应用记录

## 15.7 实现注意点
- 如果目标客户端非常多，后续可改批次生成；V1 先保持逻辑清晰

---

## 16. 链路十三：客户端上报配置应用结果

## 16.1 输入
- `POST /client/config/apply-result`
- DTO：`ConfigApplyResultRequest`

## 16.2 输出
- 对应 `ConfigApplyRecord` 更新为 `success` / `failed` / `skipped`

## 16.3 主要调用
```text
ClientConfigApplyHandler
  -> ClientConfigApplyService
  -> ConfigApplyRecordRepo
```

## 16.4 写表
- `config_apply_records`

## 16.5 事务边界
建议单事务：
- 查询待更新 apply record
- 更新状态、失败原因、detail、applied_at

## 16.6 失败处理
- 找不到记录：返回错误
- 重复上报：可按幂等处理或只允许终态覆盖策略

## 16.7 实现注意点
- 建议用 `(config_bundle_version_id, client_id)` 唯一定位应用记录
- 终态后是否允许再次覆盖，要在 service 里统一控制

---

## 17. 失败补偿策略总表

| 场景 | V1 建议策略 |
|---|---|
| 外部 hubcenter 拉取失败 | 不入库，直接失败 |
| 协作任务创建时权限不通过 | 不创建主记录 |
| 协作任务写事件失败 | 整体回滚 |
| 流程实例创建后首步任务创建失败 | 整体回滚 |
| 步骤完成后下一步创建失败 | 整体回滚 |
| 规则校验服务异常 | 关键链路默认拒绝 |
| 外部代理请求失败 | 保留审计记录并记失败 |
| 配置发布时 apply records 创建失败 | 整体回滚 |
| 客户端重复上报应用结果 | 幂等或拒绝重复，选一种统一实现 |

## 18. 推荐的集成测试矩阵

| 测试名 | 重点验证 |
|---|---|
| 创建协作任务成功 | 主记录 + 事件同时落库 |
| 创建协作任务被规则拦截 | 不生成主记录，命中记录可见 |
| 创建流程实例成功 | 实例 + 首步 + 首个任务 + 事件完整 |
| 步骤完成推进成功 | 当前步完成、下一步生成、实例 current_step 更新 |
| 步骤完成推进失败回滚 | 当前步不应停在 completed 半状态 |
| 步骤拒绝终止流程 | 步骤/任务/实例三者状态一致 |
| 发布配置包成功 | published + pending apply records 同时可见 |
| 代理请求失败仍保留记录 | failed/block 状态和耗时可见 |

## 19. 一句话总结

**数字员工中心 V1 的关键实现，不在于接口数量，而在于把“协作、流程、规则、代理、下发”五条主链路的数据流和事务边界一次定清，确保每条链路都能做到成功时完整落库、失败时状态一致、审计可追踪。**
