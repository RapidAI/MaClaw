# 数字员工中心：V1 错误码与统一返回约定

## 1. 目标

本文件用于统一数字员工中心 V1 的接口返回结构、业务错误码、HTTP 状态映射与典型失败语义。

作用：
- 让 handler 层返回风格一致
- 让前端/客户端能稳定识别错误
- 让 service 层错误语义不再散落
- 让事务失败、状态机失败、权限失败有明确表现

V1 原则：
- 错误要显式
- 失败不要伪装成功
- 业务错误与系统错误分层表达

---

## 2. 统一返回结构

## 2.1 成功返回

建议统一：

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

说明：
- `code=0` 表示成功
- `message` 默认可为 `ok`
- `data` 根据接口类型返回对象、列表或空对象

## 2.2 失败返回

建议统一：

```json
{
  "code": 1001001,
  "message": "colleague not found",
  "data": null,
  "error": {
    "type": "business_error",
    "module": "colleagues",
    "reason": "record_not_found",
    "request_id": "req_xxx"
  }
}
```

## 2.3 字段约定
- `code`：稳定业务码，前后端可依赖
- `message`：面向人类可读信息
- `data`：失败时可为 `null`
- `error.type`：错误类别
- `error.module`：来源模块
- `error.reason`：机器可识别原因
- `error.request_id`：链路追踪 ID

---

## 3. error.type 建议值

建议统一以下类型：

- `validation_error`
- `business_error`
- `forbidden_error`
- `conflict_error`
- `not_found_error`
- `state_error`
- `external_error`
- `internal_error`

说明：
- `validation_error`：参数格式/字段非法
- `business_error`：业务规则不满足
- `forbidden_error`：权限、安全规则、访问被拒绝
- `conflict_error`：唯一约束、重复操作、并发冲突
- `not_found_error`：资源不存在
- `state_error`：状态流转非法
- `external_error`：外部依赖失败
- `internal_error`：未知内部错误

---

## 4. HTTP 状态码映射建议

| 场景 | HTTP 状态 |
|---|---|
| 成功查询/更新 | `200` |
| 成功创建 | `200` 或 `201` |
| 参数错误 | `400` |
| 未认证（如后续有 auth） | `401` |
| 无权限/被规则拒绝 | `403` |
| 资源不存在 | `404` |
| 状态冲突/重复提交/唯一键冲突 | `409` |
| 外部依赖失败 | `502` |
| 超时 | `504` |
| 未知内部错误 | `500` |

V1 建议：
- 业务语义优先靠 `code`
- HTTP 状态用于大类区分
- 不要所有失败都返回 `200`

---

## 5. 错误码编码规则建议

建议用 7 位数字：

```text
A BB CCC D
```

为了简单，V1 可直接理解为：
- 前 2~3 位：模块段
- 后 3~4 位：错误序号

推荐模块段：

| 模块 | 前缀 |
|---|---|
| 通用 common | `100` |
| colleagues | `110` |
| capabilities | `120` |
| collaboration | `130` |
| workflows | `140` |
| security | `150` |
| proxy | `160` |
| configsync | `170` |
| modelrouting | `180` |

例如：
- `1100001`：员工不存在
- `1300004`：协作任务状态非法
- `1400007`：下一步创建失败

## 16. handler 层错误映射建议

建议 handler 层统一做以下映射：

| error.type | HTTP |
|---|---|
| `validation_error` | `400` |
| `not_found_error` | `404` |
| `forbidden_error` | `403` |
| `state_error` | `409` |
| `conflict_error` | `409` |
| `business_error` | `400` 或 `409` |
| `external_error` | `502/504` |
| `internal_error` | `500` |

建议实现一个统一方法：

```go
func WriteError(w http.ResponseWriter, err error)
```

由它完成：
- 业务错误转结构化 JSON
- HTTP 状态选择
- request_id 注入
- 内部日志记录

---

## 17. service 层错误返回建议

service 层不要直接返回 HTTP 错误。
建议返回统一业务错误对象，例如：

```go
type BizError struct {
    Code    int
    Type    string
    Module  string
    Reason  string
    Message string
}
```

这样：
- service 保持协议无关
- handler 负责 HTTP 化
- 后续 RPC/异步任务也可复用同一套错误语义

---

## 18. 前端/客户端使用建议

前端和客户端判断失败时，优先依赖：
1. `code`
2. `error.reason`
3. HTTP 状态

不要只依赖 `message` 文本。

例如：
- `1300004`：提示“当前任务状态不允许该操作”
- `1400005`：提示“流程当前无法分配首步处理人”
- `1700005`：提示“该客户端已上报过结果”

---

## 19. V1 第一批必须稳定的错误码

建议优先保证以下错误码在首批就稳定：
- `1000001` 参数错误
- `1100001` 员工不存在
- `1100004` 员工被禁用
- `1200001` 能力包不存在
- `1200004` 能力已绑定
- `1300002` 协作权限拒绝
- `1300004` 协作状态非法
- `1400001` 流程模板不存在
- `1400005` 首步不可分配
- `1400006` 步骤状态非法
- `1500003` 安全规则阻断
- `1600002` 外部代理失败
- `1700002` 配置包状态非法
- `1700005` 重复上报应用结果

---

## 20. 一句话总结

**V1 的错误处理应统一成“稳定业务码 + 明确错误类型 + 可读 message + 机器可识别 reason”的结构，确保事务失败、状态冲突、权限拒绝、外部依赖异常都能被前端和调用方一致理解。**
