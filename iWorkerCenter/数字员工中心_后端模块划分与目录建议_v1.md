# 数字员工中心：后端模块划分与目录建议 v1

## 1. 目标

本文件用于给数字员工中心 V1 提供一套可直接落地的后端模块划分建议，明确：
- 后端按什么边界拆模块
- 每个模块负责什么
- handler / service / repo 如何分层
- 哪些地方需要事务
- 第一批代码应先落哪几块

本文件默认遵循：
- V1 先单体模块化
- 后续再按边界服务化
- 优先复用 `corelib/`

---

## 2. 总体拆分原则

### 2.1 先按业务域拆，不按技术层先拆
优先按领域分模块：
- colleagues
- capabilities
- collaboration
- workflows
- modelrouting
- security
- configsync
- proxy

而不是先做一个大而全的：
- handlers/
- services/
- repos/

更不建议把所有业务全堆在一个 app service 里。

### 2.2 每个业务域内部再分层
每个模块内部再拆：
- handler
- service
- repo
- domain
- dto

这样 V1 仍是单体，但边界已经清晰。

### 2.3 跨域编排逻辑单独放应用层
像“完成流程步骤后自动生成下一条协作任务”这种逻辑，不应散落在 repo 或 handler 中，应放在应用编排 service 中。

### 2.4 通用基础能力优先复用 corelib
优先评估复用：
- `corelib/memory`
- `corelib/security`
- `corelib/config`
- 现有消息/任务抽象

若现有抽象不足，优先补强 `corelib/`，不要在 iWokerCenter 重新发明一套基础设施。

## 4. 模块职责建议

## 4.1 colleagues 模块

### 负责对象
- `ColleagueProfile`
- 员工基础展示信息
- 偏好配置
- 协作范围配置

### 主要表
- `colleagues`

### 主要接口
- `/admin/colleagues/*`
- `/client/colleagues/*`

### 不负责
- 绑定能力包具体逻辑
- 流程推进逻辑
- 模型代理调用

### 建议服务
- `ColleagueService`
- `ColleagueQueryService`
- `ClientColleagueQueryService`

---

## 4.2 capabilities 模块

### 负责对象
- `CapabilityPackage`
- `CapabilityPackageVersion`
- `ColleagueCapabilityBinding`

### 主要表
- `capability_packages`
- `capability_package_versions`
- `colleague_capability_bindings`

### 主要接口
- `/admin/capabilities/*`
- `/runtime/capabilities`

### 建议服务
- `CapabilityImportService`
- `CapabilityQueryService`
- `CapabilityReviewService`
- `CapabilityBindingService`
- `CapabilityUpgradeService`

### 边界说明
- 从 hubcenter 搜索/导入能力包属于本模块
- 员工详情页中展示“会做的事”时，可由 colleagues 模块调用 capabilities 查询能力摘要

---

## 4.3 collaboration 模块

### 负责对象
- `CommunicationMessage`
- `CommunicationMessageEvent`
- `CollaborationPermission`
- 任务箱查询

### 主要表
- `communication_messages`
- `communication_message_events`
- `collaboration_permissions`

### 主要接口
- `/runtime/collaboration/*`
- `/runtime/tasks/inbox`
- `/admin/communications/*`
- `/admin/collaboration-permissions/*`

### 建议服务
- `CollaborationService`
- `CollaborationLifecycleService`
- `CollaborationQueryService`
- `CollaborationPermissionService`
- `CollaborationPermissionQueryService`
- `InboxQueryService`

### 边界说明
- 点对点协作任务是本模块主责
- 工作流步骤落地后生成协作任务，创建动作可以由 workflows 模块编排调用 collaboration 模块完成
- 不建议 workflows 直接自己写 `communication_messages`

---

## 4.4 workflows 模块

### 负责对象
- `WorkflowDefinition`
- `WorkflowStepDefinition`
- `WorkflowInstance`
- `WorkflowStepInstance`
- `WorkflowInstanceEvent`

### 主要表
- `workflow_definitions`
- `workflow_step_definitions`
- `workflow_instances`
- `workflow_step_instances`
- `workflow_instance_events`

### 主要接口
- `/admin/workflows/*`
- `/runtime/workflows/*`

### 建议服务
- `WorkflowDefinitionService`
- `WorkflowDefinitionQueryService`
- `WorkflowStepDefinitionService`
- `WorkflowInstanceQueryService`
- `WorkflowRuntimeService`
- `WorkflowLifecycleService`
- `WorkflowStepLifecycleService`
- `WorkflowAdminActionService`

### 边界说明
- 负责流程模板管理
- 负责流程实例推进
- 负责“下一步是谁”的计算
- 不直接承载实际任务执行，而是通过 collaboration 模块创建执行任务

## 4.6 proxy 模块

### 边界说明

### 负责对象
- 跨模块审计汇总

### 主要接口
- `/admin/audit/*`

### 建议服务
- `AuditQueryService`
- `AuditExportService`

### 边界说明
- V1 可以先只做查询聚合层
- 不必一开始就做统一总表

## 5. 每个模块内部建议分层

## 5.1 handler
职责：
- HTTP 路由绑定
- 参数接收与解析
- 调用 service
- 返回 DTO / response

不做：
- 复杂状态机判断
- 多表写入事务
- 跨模块编排

## 5.2 service
职责：
- 业务主逻辑
- 状态机控制
- 事务边界控制
- 调用其他模块 service
- 记录事件

建议再细分：
- command service：负责写
- query service：负责读
- lifecycle service：负责状态推进

## 5.3 repo
职责：
- 单表持久化
- 固定查询封装
- 不承载业务分支决策

## 5.4 domain
职责：
- 实体结构
- 枚举常量
- 小型领域规则
- 状态判断辅助方法

## 5.5 dto
职责：
- request / response
- list item / detail view
- admin runtime client 三类返回结构隔离

## 6. 关键跨模块调用关系

## 6.1 工作流启动

```text
WorkflowRuntimeService
  -> WorkflowDefinitionRepo
  -> WorkflowStepDefinitionRepo
  -> CollaborationPermissionService
  -> SecurityCheckService
  -> CollaborationService
  -> WorkflowInstanceRepo / WorkflowStepInstanceRepo
```

说明：
- 流程负责编排
- 协作负责落任务
- 安全与权限负责放行判断

## 6.2 工作流步骤完成

```text
WorkflowStepLifecycleService
  -> WorkflowStepInstanceRepo
  -> CollaborationLifecycleService 或 CollaborationRepo
  -> WorkflowRuntimeService(计算下一步)
  -> CollaborationPermissionService
  -> SecurityCheckService
  -> CollaborationService(创建下一步任务)
  -> WorkflowInstanceRepo
```

## 6.3 代理请求

```text
ProxyLLMService / ProxyAPIService
  -> SecurityCheckService
  -> ModelRoutingRecommendService
  -> 外部 provider client
  -> ProxyRequestRecordRepo
```

## 6.4 配置发布

```text
ConfigBundleService
  -> 各业务模块 Query/Assembler
  -> ConfigBundleRepo
  -> ConfigBundleTargetRepo
  -> ConfigApplyRecordRepo
```

## 7. 事务边界建议

## 7.1 必须事务化的操作

### A. 创建协作任务
同一事务内：
- 写 `communication_messages`
- 写 `communication_message_events`

### B. 创建流程实例并生成首步任务
同一事务内尽量保证：
- 写 `workflow_instances`
- 写 `workflow_step_instances`
- 创建 `communication_messages`
- 回填 `delegation_message_id`
- 写 `workflow_instance_events`

### C. 完成步骤并推进下一步
同一事务内尽量保证：
- 更新当前 `workflow_step_instances`
- 更新当前 `communication_messages`
- 创建下一步 `workflow_step_instances`
- 创建下一步 `communication_messages`
- 更新 `workflow_instances.current_step_id`
- 写 `workflow_instance_events`

### D. 发布配置包
同一事务内：
- 更新 `config_bundle_versions.status=published`
- 写 `config_apply_records`

## 7.2 不建议放大事务的操作
以下动作可事务外处理或异步化：
- 导出报表
- 大批量统计聚合
- 外部 hubcenter 搜索
- 外部 LLM / API 真正调用

## 8. 建议的路由注册方式

建议在 `internal/app/http/` 做统一路由注册，按模块拆分：

```text
internal/app/http/
  router.go
  admin_routes.go
  runtime_routes.go
  client_routes.go
  proxy_routes.go
```

每个模块提供自己的注册函数，例如：
- `RegisterColleagueAdminRoutes(...)`
- `RegisterCapabilityAdminRoutes(...)`
- `RegisterCollaborationRuntimeRoutes(...)`
- `RegisterWorkflowRuntimeRoutes(...)`

这样可以保持：
- 路由层统一
- 模块实现独立
- admin/runtime/client 边界清楚

## 9.1 第一批模块
1. `colleagues`

## 10. 从单体到后续服务化的映射建议

V1 先单体模块化，后续如果拆服务，建议大致沿以下边界演进：

- `colleagues + capabilities` → 员工与能力服务
- `collaboration + workflows` → 协作与流程服务
- `modelrouting + proxy` → 模型网关服务
- `security` → 安全策略服务
- `configsync` → 配置发布服务
- `audit` → 审计与报表服务

这样 V1 的目录边界能自然过渡到 V2 的服务边界。

---

## 11. V1 不建议现在就做的事情

- 不要过早做微服务拆分
- 不要引入过重的 BPM 引擎
- 不要每个模块都做一套自己的规则判断
- 不要把 repo 写成带大量业务逻辑的“万能 service”
- 不要为了未来多租户过度设计当前目录
- 不要先做复杂事件总线再补主链路

V1 优先目标仍然是：
- 主档可管理
- 协作可流转
- 流程可推进
- 规则可治理
- 配置可下发

---

## 12. 一句话总结

**数字员工中心 V1 的后端应采用“单体部署、按领域模块化、模块内再分层、跨域逻辑集中在应用 service”的方式落地，这样既能尽快形成最小闭环，也能为后续服务化演进保留清晰边界。**
