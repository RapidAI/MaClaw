# 缺陷修复需求文档

## 简介

用户在 MaClaw GUI 客户端对八卦帖子评分时，出现"评分失败"错误。根因是 `GossipRateHandler` 中 `HasRated` 重复检查与 `CreateComment` 写入之间存在竞态条件：`HasRated` 从 `readDB` 读取，而 `CreateComment` 通过异步 `writeBatcher` 写入 `writeDB`。在 WAL 模式下，batcher 队列中尚未刷盘的写入对 `readDB` 不可见，导致快速双击时重复评分请求均通过检查。当 batcher 在同一事务中刷盘两条 INSERT 时，若其中一条失败则整个事务回滚，连第一条有效评分也被撤销。此外，`UpdatePostScore` 的错误被 `_ =` 静默忽略，评分记录可能存在但帖子分数/票数未更新。

## 缺陷分析

### 当前行为（缺陷）

1.1 当用户快速连续点击评分（双击）时，两次评分请求的 `HasRated` 检查均在 `readDB` 上执行，由于第一次 `CreateComment` 仍在 `writeBatcher` 队列中尚未刷盘，`readDB` 看不到该写入，因此两次请求均通过重复检查，导致两条评分记录同时进入 batcher 队列。

1.2 当 batcher 在同一批次事务中刷盘包含重复评分的多条写入时，若任一条 INSERT 失败（如触发约束冲突），`flush()` 方法回滚整个事务，导致同批次中所有写入（包括其他用户的有效写入）全部失败，用户看到"评分失败"。

1.3 当 `CreateComment` 成功但 `UpdatePostScore` 失败时，错误被 `_ =` 静默忽略，评分评论已写入但帖子的 `score` 和 `votes` 字段未更新，导致前端显示的分数与实际评分不一致。

1.4 当 `gossip_comments` 表上不存在 `(post_id, machine_id, rating > 0)` 的唯一约束时，即使两条重复评分都成功写入，数据库层面也无法阻止重复数据，`HasRated` 是唯一的防重机制，而该机制在异步写入场景下不可靠。

### 期望行为（正确）

2.1 当用户快速连续点击评分时，系统应确保同一 `(post_id, machine_id)` 的评分操作具有原子性——重复检查与写入应在同一个写连接/事务中完成，使得第二次请求能正确检测到第一次评分并返回 `409 ALREADY_RATED`，而非两次都通过检查。

2.2 当 batcher 刷盘时，单条写入的失败不应导致同批次中其他不相关写入被回滚；或者评分写入应绕过 batcher 直接在写连接上以独立事务执行，避免批量事务的级联失败。

2.3 当 `UpdatePostScore` 执行失败时，系统应将错误传播给调用方，使 handler 能返回适当的错误响应，而非静默忽略导致数据不一致。

2.4 数据库层面应添加唯一约束或等效机制，作为防止重复评分的最终保障，即使应用层检查因竞态而失效，数据库也能拒绝重复插入。

### 不变行为（回归防护）

3.1 当不同用户（不同 `machine_id`）对同一帖子评分时，系统应继续正常接受每个用户的评分并正确更新帖子分数。

3.2 当用户对帖子发表纯评论（`rating = 0`）时，系统应继续正常创建评论，不受评分防重逻辑影响。

3.3 当用户对未锁定的帖子进行首次评分（无重复）时，系统应继续正常创建评分记录、更新帖子分数并返回成功。

3.4 当帖子被管理员锁定时，系统应继续拒绝评分请求并返回 `403 LOCKED`。

3.5 当评分值不在 1-5 范围内时，系统应继续返回 `400 BAD_REQUEST` 验证错误。

3.6 当其他非评分类写入（如发帖、评论）通过 batcher 执行时，系统应继续正常批量写入，不受评分逻辑变更影响。
