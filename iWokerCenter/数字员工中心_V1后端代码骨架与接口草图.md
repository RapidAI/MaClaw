# 数字员工中心：V1 后端代码骨架与接口草图

## 1. 目标

本文件用于把前面的模块划分、DTO、事务边界、开发切片，进一步收敛成接近编码的 Go 后端骨架建议。

重点回答：
- 代码目录第一批该怎么落
- 每个模块第一批该有哪些文件
- handler / service / repo 的核心接口长什么样
- 哪些 service 该暴露给别的模块调用
- 哪些依赖应该反向隔离，避免写着写着又耦合回“大一统 app service”

本文件不是最终代码，而是为了降低正式编码时的结构分歧。

## 3. 基础设施代码骨架

## 3.1 transaction manager

文件建议：
- `internal/app/transaction/manager.go`

```go
package transaction

import "context"

type Manager interface {
    RunInTx(ctx context.Context, fn func(ctx context.Context) error) error
}
```

建议：
- service 层只依赖 `transaction.Manager`
- 不要在 handler 层直接开事务
- `RunInTx` 内部负责把 tx 绑定进 context 或 repo session

## 4. 模块注册建议

## 4.1 bootstrap app

文件建议：
- `internal/app/bootstrap/app.go`
- `internal/app/bootstrap/modules.go`

建议在 `App` 中集中装配：

```go
type App struct {
    TxManager transaction.Manager
    Clock     clock.Clock
    IDGen     idgen.Generator

    ColleaguesModule     *ColleaguesModule
    CapabilitiesModule   *CapabilitiesModule
    CollaborationModule  *CollaborationModule
    WorkflowsModule      *WorkflowsModule
    SecurityModule       *SecurityModule
    ProxyModule          *ProxyModule
    ConfigSyncModule     *ConfigSyncModule
}
```

每个模块再暴露自己的 handler/service 聚合：

```go
type ColleaguesModule struct {
    AdminHandler *handler.AdminHandler
    ClientHandler *handler.ClientHandler
    Service service.ColleagueService
    QueryService service.ColleagueQueryService
}
```

建议：
- app 层负责装配依赖
- 模块间调用尽量通过 service interface
- 不要跨模块直接 new repo 然后随便写对方表

## 12. handler 层统一建议

## 12.1 handler 只做四件事
1. 解析 path/query/body
2. 调用 service
3. 映射错误
4. 输出 response

## 12.2 handler 不做的事
- 不直接开事务
- 不直接操作 repo
- 不直接做状态流转
- 不直接调用外部 provider/hubcenter

## 12.3 handler 辅助函数建议
可在 `internal/app/http/` 提供：

```go
func DecodeJSON(r *http.Request, v interface{}) error
func WriteJSON(w http.ResponseWriter, status int, data interface{})
func WriteError(w http.ResponseWriter, err error)
```

## 13. service 层统一建议

## 13.1 command / query 分离
建议写接口时尽量分开：
- 写操作：command service
- 读操作：query service

这样好处：
- 事务边界清楚
- handler 依赖更稳定
- 跨模块调用更容易收敛

## 13.2 service 入参与出参建议
不要直接把 HTTP DTO 传进 repo。
建议分三层：
- handler 收 HTTP DTO
- service 用 command/query struct
- repo 用 domain struct / query struct

例如：

```go
type CreateColleagueCommand struct {
    Name string
    Code string
    DefaultModelPolicyID string
}
```

---

## 14. repo 层统一建议

## 14.1 repo 只管表，不管业务策略
例如 repo 不做这些：
- “当前状态能不能从 standby 变 accepted”
- “下一步该指派给谁”
- “能力包未审核能否绑定”

这些都应在 service 层。

## 14.2 repo 查询接口尽量稳定
例如：
- `GetByID`
- `Create`
- `Update`
- `List`
- `ListByXXX`
- `UpsertXXX`

不要写成：
- `CompleteAndAdvanceAndWriteEvents()` 这种业务巨型 repo 方法

## 17. 一句话总结

**V1 第一批代码骨架应坚持“底座先稳、模块独立、service 编排、repo 单表、workflow 通过 collaboration 落任务”的结构原则，这样一旦开始编码，就能在不反复推翻目录和接口的前提下持续往前推进。**
