# 数字员工中心：服务划分与接口草案 v1

## 1. 目标

本文件用于定义数字员工中心的服务划分和接口边界，明确：
- 数字员工中心应该拆成哪些核心服务
- 每个服务负责什么
- 与 DiWorker 客户端如何交互
- 与 hubcenter 如何交互
- 数字员工之间的通讯如何建模
- 配置、能力包、规则如何同步下发

本文件是产品方案和后续技术落地之间的桥梁。

---

## 2. 总体定位

数字员工中心是企业内部数字员工的统一入口与中枢服务。

它对上承接：
- hubcenter 等外部能力来源
- 企业内部上传和配置
- 外部 LLM / API 服务提供方

它对下服务：
- DiWorker 客户端
- 数字员工运行时
- 管理端

### 实现原则
- 优先复用同级目录 `corelib/` 中已有公共能力
- 不重复实现 `corelib/` 已覆盖的基础模块
- 如 `corelib/` 现有实现存在问题，应优先修复 `corelib/`，再由上层复用
- 新产生的通用能力优先沉淀回 `corelib/`

### 总体职责
- 管理数字员工资料
- 管理能力包
- 管理经验共享
- 协调员工通讯
- 统一模型调度
- 统一安全规则
- 统一配置下发
- 统一转发外部 API / LLM 请求
- 审计与统计

---

## 3. 建议的服务划分

建议数字员工中心至少拆成以下 8 个逻辑服务。

> 第一版可以单体部署、模块化实现；后续再按模块拆服务。

### 3.1 员工目录服务（Colleague Directory Service）
负责数字员工基础资料和角色设定。

#### 负责内容
- 员工基本信息
- 名字、头像、描述
- 角色设定
- 更擅长什么
- 会做的事的挂接关系
- 状态管理

#### 对外提供
- 员工列表查询
- 员工详情查询
- 员工配置更新
- 员工状态启停

---

### 3.2 能力包服务（Capability Package Service）
负责能力包生命周期管理。

#### 负责内容
- 能力包登记
- hubcenter 搜索 / 下载接入
- 安装
- 审核
- 版本管理
- 绑定到数字员工
- 停用 / 下架

#### 对外提供
- 能力包搜索
- 能力包详情
- 能力包下载导入
- 能力包绑定 / 解绑
- 能力包版本更新

---

### 3.3 经验服务（Experience Service）
负责经验沉淀、共享和引用。

#### 负责内容
- 经验条目录入
- 经验分类
- 经验审核
- 经验共享范围管理
- 经验引用关系记录
- 经验转能力包候选

#### 对外提供
- 经验查询
- 经验发布
- 经验引用
- 经验共享范围变更

---

### 3.4 员工通讯服务（Colleague Communication Service）
负责不同数字员工之间的协作消息，以及与企业 IM 连接器之间的消息交换。

#### 负责内容
- 协作请求收发
- 子任务转交
- 借用能力请求
- 经验参考请求
- 返回结果
- 消息状态流转
- 通讯审计
- 飞书 / 钉钉 / 企业微信连接器消息接入
- 内网场景下的消息桥接

#### 对外提供
- 发起协作请求
- 拉取待处理请求
- 提交处理结果
- 查询通讯记录
- 连接器注册与消息交换

---

### 3.5 模型调度与请求转发服务（Model Routing & Proxy Service）
负责多模型 API 的统一接入、任务路由和请求转发。

#### 负责内容
- 模型接入管理
- 路由策略
- 默认模型 / 备用模型
- 按员工类型路由
- 按任务类型路由
- 外部 API 请求统一转发
- LLM 请求统一转发
- 故障回退
- 成本统计

#### 对外提供
- 查询路由策略
- 计算某任务的推荐模型
- 统一接收客户端 LLM / API 请求
- 将请求转发到目标模型或外部 API
- 记录调用结果

---

### 3.6 安全规则服务（Security Policy Service）
负责规则管理和命中判断。

#### 负责内容
- 协作规则
- 数据共享规则
- 外发控制规则
- 能力包使用规则
- 审批规则
- 生效范围与版本

#### 对外提供
- 规则查询
- 规则命中检查
- 发布规则
- 回滚规则

---

### 3.7 配置下发服务（Config Distribution Service）
负责向 DiWorker 客户端下发配置。

#### 负责内容
- 员工配置下发
- Welcome 页配置下发
- 能力包更新下发
- 模型策略下发
- 安全规则下发
- 下发版本记录
- 下发结果记录

#### 对外提供
- 获取最新配置版本
- 拉取变更包
- 上报客户端应用结果

---

### 3.8 审计与统计服务（Audit & Analytics Service）
负责日志、审计和指标统计。

#### 负责内容
- 员工通讯审计
- 能力包使用统计
- 经验引用统计
- 模型调用统计
- 规则命中统计
- 下发结果统计

#### 对外提供
- 审计查询
- 指标统计
- 报表导出

---

## 4. 外部交互关系

## 4.1 与 DiWorker 客户端的关系

DiWorker 是面向普通用户的客户端。

### 客户端配置原则
DiWorker 客户端只需要配置一项中心地址：
- 数字员工中心的 IP 或域名
- 端口

客户端不再直接配置外部 LLM 提供方地址，也不直接请求外部 API 服务。

### 客户端需要从数字员工中心获取
- 数字员工列表
- 员工头像 / 名字 / 描述
- 员工会做的事
- Welcome 页配置
- 常用任务配置
- 安全策略结果
- 可见能力包结果
- 模型与请求转发入口

### 客户端向数字员工中心发起或上报
- 任务请求
- LLM 请求
- 其他外部 API 请求
- 当前配置版本
- 任务执行结果摘要
- 协作结果摘要
- 客户端应用配置结果
- 使用统计事件

### 交互方式建议
- 配置和元数据：HTTP API
- LLM / API 调用：统一代理转发 API
- 版本同步：HTTP + 增量拉取
- 协作事件 / 任务事件：事件上报 API 或消息队列

---

## 4.2 与 hubcenter 的关系

hubcenter 作为外部能力来源，不直接面向终端用户，而是面向数字员工中心。

### 数字员工中心从 hubcenter 获取
- 能力包搜索结果
- 能力包元信息
- 能力包下载内容
- 版本更新信息

### 建议交互方式
- 搜索：HTTP API
- 下载：HTTP 文件流
- 校验：签名 / 校验和

### 接入原则
- 下载后必须先进入待审核区
- 审核通过后才能绑定给数字员工
- 外部来源必须保留来源标记

---

## 4.3 与飞书 / 钉钉的关系

数字员工中心需要支持飞书 / 钉钉接入，但必须考虑系统可能仅部署于企业内网，无法直接向公网暴露 URL。

### 参考现有 hub 的地方
可以参考 hub 中已有的：
- Feishu 配置管理
- webhook / 插件式消息接入
- IM 消息抽象层
- HMAC / 签名校验

### 与 hub 的关键差异
数字员工中心不能默认采用“公网 webhook 直接打入中心”的部署方式。

### 推荐接入模式
#### 方案 1：企业统一网关转发
- 由企业现有公网网关暴露飞书 / 钉钉回调入口
- 网关反向代理到内网数字员工中心
- 适合已有企业网关体系的部署

#### 方案 2：IM 外部连接器
- 在可联网区域部署飞书 / 钉钉连接器
- 连接器负责接收平台事件
- 连接器与内网数字员工中心建立主动出站连接、长连接或受控轮询
- 消息通过连接器桥接进内网

对于“仅内网部署、不能暴露 URL”的前提，推荐优先采用方案 2。

### 接入原则
- 中心本体不依赖公网暴露
- 飞书 / 钉钉适配器与中心解耦
- IM 接入统一走员工通讯服务的桥接层
- 所有入站 / 出站消息都纳入审计

---

## 5. 数字员工通讯消息模型

数字员工之间的通信，不建议做成自由文本聊天，而应做成结构化协作消息。

## 5.1 基础消息结构
建议消息对象至少包括：

- `message_id`
- `task_id`
- `from_colleague_id`
- `to_colleague_id`
- `message_type`
- `subject`
- `content`
- `attachments`
- `context_summary`
- `status`
- `created_at`
- `updated_at`

---

## 5.2 message_type 建议
- `assist_request`：协助处理请求
- `analysis_request`：分析请求
- `capability_borrow`：借用能力请求
- `experience_reference`：经验参考请求
- `result_return`：结果返回
- `reject_notice`：拒绝处理
- `need_more_context`：需要补充上下文

---

## 5.3 status 建议
- `pending`
- `accepted`
- `processing`
- `completed`
- `rejected`
- `expired`

---

## 5.4 典型流转
### 示例：小迪请求阿宁处理数据子任务
1. 小迪发出 `analysis_request`
2. 通讯服务记录并检查规则
3. 阿宁接受，状态改为 `accepted`
4. 阿宁处理中，状态改为 `processing`
5. 阿宁返回 `result_return`
6. 原消息状态变为 `completed`
7. 结果可被任务主处理者整合

---

## 6. 配置同步模型

配置同步建议采用“版本号 + 增量包”模式。

## 6.1 客户端关注的配置类型
- 数字员工配置
- Welcome 页配置
- 常用任务配置
- 能力包配置
- 模型策略配置
- 安全规则配置

## 6.2 同步建议流程
1. DiWorker 启动时上报当前配置版本
2. 数字员工中心返回是否有更新
3. 若有更新，客户端拉取变更包
4. 客户端应用成功后回传结果
5. 数字员工中心记录下发状态

## 6.3 配置包建议字段
- `config_type`
- `version`
- `change_summary`
- `payload`
- `created_at`
- `created_by`

## 7. 关键接口草案

以下为逻辑级接口草案，不限定最终 REST 或 RPC 形式。

# 7.1 员工目录接口
### 查询员工列表
- `GET /colleagues`

### 查询员工详情
- `GET /colleagues/{id}`

### 更新员工资料
- `PUT /colleagues/{id}`

### 更新员工头像
- `PUT /colleagues/{id}/avatar`

### 绑定能力包
- `POST /colleagues/{id}/capabilities`

### 查询员工会做的事
- `GET /colleagues/{id}/jobs`

---

# 7.2 能力包接口
### 搜索 hubcenter 能力包
- `GET /capabilities/search?source=hubcenter&query=...`

### 导入能力包
- `POST /capabilities/import`

### 查询能力包列表
- `GET /capabilities`

### 查询能力包详情
- `GET /capabilities/{id}`

### 审核能力包
- `POST /capabilities/{id}/review`

### 绑定到员工
- `POST /capabilities/{id}/bind`

---

# 7.3 经验接口
### 查询经验列表
- `GET /experiences`

### 新增经验
- `POST /experiences`

### 发布经验
- `POST /experiences/{id}/publish`

### 引用经验
- `POST /experiences/{id}/reference`

### 转为能力包候选
- `POST /experiences/{id}/to-capability-candidate`

---

# 7.4 员工通讯接口
### 发起协作请求
- `POST /communications`

### 查询通讯列表
- `GET /communications`

### 查询通讯详情
- `GET /communications/{id}`

### 接受请求
- `POST /communications/{id}/accept`

### 提交处理结果
- `POST /communications/{id}/result`

### 拒绝请求
- `POST /communications/{id}/reject`

---

# 7.5 模型调度与统一代理接口
### 查询模型列表
- `GET /models`

### 更新路由策略
- `PUT /model-routing/policies/{id}`

### 查询某任务推荐模型
- `POST /model-routing/recommend`

### 统一代理 LLM 请求
- `POST /proxy/llm`

### 统一代理外部 API 请求
- `POST /proxy/api`

### 上报模型调用结果
- `POST /model-routing/usage`

---

# 7.6 安全规则接口
### 查询规则列表
- `GET /security-policies`

### 发布规则
- `POST /security-policies/{id}/publish`

### 规则命中校验
- `POST /security-policies/check`

### 回滚规则
- `POST /security-policies/{id}/rollback`

---

# 7.7 配置同步接口
### 查询最新版本
- `GET /config/latest`

### 拉取配置变更包
- `GET /config/changes?since_version=...`

### 客户端上报应用结果
- `POST /config/apply-result`

---

## 8. 建议的数据边界

## 客户端应尽量轻
DiWorker 客户端主要负责：
- 展示
- 交互
- 本地任务态
- 结果查看

## 中心应尽量重
数字员工中心负责：
- 通讯协调
- 能力包审核与绑定
- 经验共享
- 模型调度
- 安全控制
- 配置下发
- 审计统计

这样更利于企业级治理。

---

## 9. V1 实施建议

第一版先采用：
- 单体应用
- 模块化代码结构
- 统一数据库
- 明确服务边界

### 第一版优先接口
1. 员工列表 / 详情
2. 能力包搜索 / 导入 / 绑定
3. 员工通讯发起 / 返回
4. 模型策略查询
5. 安全规则检查
6. 配置同步

### 第二版再增强
1. 消息队列化
2. 经验推荐
3. 自动协作路由
4. 多租户隔离
5. 更细粒度审计

---

## 10. 总结

数字员工中心在技术上建议按以下思路建设：

- 先模块化定义边界
- 再逐步服务化
- 客户端轻，中心重
- 通讯结构化，经验可沉淀
- 能力包统一治理，规则统一下发

最终目标不是做一个新的“hub”，而是做一个：

**能让数字员工真正协作、交流、共享和成长的企业中枢。**
