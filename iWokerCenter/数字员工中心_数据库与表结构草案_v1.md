# 数字员工中心：数据库与表结构草案 v1

## 1. 目标

本文件用于把数字员工中心 V1 的核心业务对象进一步收敛为可落地的数据库表结构建议，为后续：
- 存储实现
- ORM 映射
- 查询索引设计
- 接口落地
- 状态流转实现

提供统一基础。

本文件不强绑定具体数据库产品，但默认按关系型数据库思路设计。

---

## 2. 设计原则

### 2.1 先满足 V1 最小闭环
优先支撑：
- 数字员工管理
- 能力包绑定
- 协作委托
- 工作流流转
- 模型路由
- 安全规则
- 配置下发

### 2.2 结构化主表 + 必要 JSON 扩展字段
对于偏好配置、规则内容、上下文摘要等变化快的结构，可使用 JSON 字段；核心关系仍保持显式列。

### 2.3 所有关键对象要可审计
关键表建议统一具备：
- `created_at`
- `updated_at`
- `created_by`
- `updated_by`

### 2.4 状态字段尽量统一
避免每张表都发明一套新状态值。

### 2.5 优先复用 corelib 抽象
如果 `corelib/` 中已有任务、消息、规则、记忆、配置版本相关公共结构，应优先复用其语义和序列化结构。

## 3. 命名约定建议

建议统一采用：
- 表名：复数下划线风格
- 主键：`id`
- 外键：`xxx_id`
- 时间：`created_at` / `updated_at` / `published_at` / `completed_at`
- 状态：`status`
- 版本：`version`

例如：
- `colleagues`
- `capability_packages`
- `workflow_instances`

## 12. 审计与事件总表建议

V1 可以选两种路线：

### 方案 A：各模块独立事件表
例如：
- `communication_message_events`
- `workflow_instance_events`
- `security_policy_hit_records`

优点：
- 领域清晰
- 查询简单

### 方案 B：增加统一审计总表
例如 `audit_events`

建议字段：
- `id`
- `domain_type`
- `domain_id`
- `event_type`
- `operator_type`
- `operator_id`
- `payload_json`
- `created_at`

V1 建议：
- **领域事件表为主**
- 如需统一审计大盘，再补 `audit_events` 聚合表或异步投影表
