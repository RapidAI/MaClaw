# 数字员工中心：V1 后端开发任务拆解清单

## 1. 目标

本清单用于把前面的架构、表结构、状态机、DTO、事务边界设计，收敛成一份可以直接进入开发排期的后端 backlog。

输出目标：
- 明确第一批要落哪些模块
- 明确每个阶段要建哪些表、接口、service、repo、测试
- 明确每项任务的完成标准
- 让实现顺序与事务边界、状态机设计保持一致

默认范围：
- V1 先做单体模块化后端
- 优先打通最小业务闭环
- 不提前做微服务拆分
- 优先复用 `corelib/`

---

## 2. 开发总原则

### 2.1 先打通主链路，再补外围能力
V1 第一优先级不是“功能看起来多”，而是先把以下闭环打通：
1. 员工可创建与查询
2. 能力包可导入与绑定
3. 协作任务可创建与推进
4. 工作流实例可创建、步骤可推进
5. 安全校验可统一接入
6. 配置包可发布、客户端可回报结果

### 2.2 先保证一致性，再考虑异步优化
以下操作优先同步事务实现：
- 创建协作任务
- 创建流程实例并生成首步任务
- 完成步骤并推进下一步
- 发布配置包并生成 apply records

### 2.3 repo 只做持久化，业务编排放 service
- handler：入参、出参、路由
- service：状态机、事务、跨模块编排
- repo：单表 CRUD / 固定查询

### 2.4 先实现最小状态机
V1 第一批只要求打通：
- 协作任务：`standby -> accepted -> processing -> completed`，以及 `-> rejected`
- 流程实例：`running -> completed|rejected`
- 流程步骤：`standby -> accepted -> processing -> completed`，以及 `-> rejected`
- 配置发布：`draft -> published`
- 配置应用：`pending -> success|failed`

---

## 3. 总体实施阶段

建议拆成 8 个阶段：

1. 基础骨架与基础设施
2. colleagues 模块
3. capabilities 模块
4. collaboration 模块
5. workflows 模块
6. security + proxy + modelrouting 基础闭环
7. configsync 模块
8. 集成测试、验收与收尾

## 4. 阶段一：基础骨架与基础设施

## 4.1 目标
建立 iWokerCenter 后端最小可运行骨架，为后续模块接入提供统一约束。

## 4.2 任务拆解

### A. 目录骨架落地
建议创建：

```text
iWokerCenter/
  cmd/server/main.go
  internal/app/bootstrap/
  internal/app/http/
  internal/app/transaction/
  internal/platform/db/
  internal/platform/clock/
  internal/platform/idgen/
  internal/shared/errors/
  internal/shared/response/
  internal/shared/paging/
  internal/shared/validation/
  internal/modules/
```

### B. 应用启动与依赖装配
实现：
- 配置加载
- 数据库连接初始化
- HTTP server 启动
- route 注册入口
- 统一健康检查接口

### C. 统一事务封装
实现：
- `RunInTx(ctx, fn)` 之类事务执行器
- service 层可复用的事务入口
- 统一事务回滚错误包装

### D. 统一响应结构
实现：
- `code/message/data`
- list/paging 响应
- 统一业务错误码映射

### E. 基础平台能力
实现：
- 时钟接口
- ID 生成接口
- 数据库 migration 入口
- 基本日志埋点

## 4.3 交付物
- 可启动 HTTP 服务
- 可连数据库
- 可注册模块路由
- 可通过事务执行 service 写操作

## 4.4 验收标准
- 服务启动成功
- `/health` 可访问
- 数据库连接失败时可显式报错
- 一条 demo 写库事务可成功提交/回滚

## 8. 阶段五：workflows 模块

## 8.1 目标
打通“流程实例 + 步骤实例 + 协作任务承载执行”的核心业务闭环。

## 8.2 表任务
- 建 `workflow_definitions`
- 建 `workflow_step_definitions`
- 建 `workflow_instances`
- 建 `workflow_step_instances`
- 建 `workflow_instance_events`

## 8.3 第一批范围
V1 第一批先做：
- 流程定义基础查询/创建
- 流程实例创建
- 自动生成首步任务
- 步骤完成推动下一步
- 步骤拒绝结束流程

暂缓复杂项：
- 人工改派
- 返回上一步
- 多分支复杂网关
- 超时自动推进

## 8.4 代码任务

### handler
- `POST /admin/workflows`
- `GET /admin/workflows`
- `GET /admin/workflows/{id}`
- `POST /runtime/workflows/instances`
- `GET /runtime/workflows/instances/{id}`
- `POST /runtime/workflows/steps/{id}/accept`
- `POST /runtime/workflows/steps/{id}/start`
- `POST /runtime/workflows/steps/{id}/complete`
- `POST /runtime/workflows/steps/{id}/reject`

### service
- `WorkflowDefinitionService`
- `WorkflowDefinitionQueryService`
- `WorkflowRuntimeService`
- `WorkflowInstanceQueryService`
- `WorkflowStepLifecycleService`

### repo
- `WorkflowDefinitionRepo`
- `WorkflowStepDefinitionRepo`
- `WorkflowInstanceRepo`
- `WorkflowStepInstanceRepo`
- `WorkflowInstanceEventRepo`

### dto
- `CreateWorkflowDefinitionRequest`
- `CreateWorkflowInstanceRequest`
- `CompleteWorkflowStepRequest`
- `RejectWorkflowStepRequest`
- `WorkflowInstanceDetailResponse`
- `WorkflowStepInstanceItem`

## 8.5 编排任务

### A. 创建流程实例
事务外：
- 读流程定义
- 算第一步
- 做权限与安全校验

事务内：
- 插 `workflow_instances`
- 插 `workflow_step_instances`
- 创建首条 `communication_messages`
- 回填 `delegation_message_id`
- 写 `workflow_instance_events`

### B. 完成步骤推进下一步
事务内必须原子：
- 当前步骤置 `completed`
- 当前任务置 `completed`
- 计算下一步
- 若有下一步：创建下一步骤、下一任务、更新 `current_step_id`
- 若无下一步：实例置 `completed`
- 写事件

### C. 步骤拒绝终止流程
事务内：
- 当前步骤置 `rejected`
- 当前任务置 `rejected`
- 实例置 `rejected`
- 写事件

## 8.6 测试任务
- 创建实例成功时首步任务同步创建
- 首步不可分配时实例不落库
- 步骤完成后生成下一步
- 最后一步完成后实例进入 `completed`
- 步骤拒绝后实例进入 `rejected`
- 下一步创建失败时整体回滚
- 任务态与步骤态联动正确

## 8.7 验收标准
- 流程实例不能出现“只有实例、没有首步任务”
- 步骤推进与任务推进状态一致
- `delegation_message_id` 始终可追踪
- 主链路事务一致性符合设计矩阵

- 安全规则拒绝时返回 blocked

- proxy 调用失败时保留失败记录
- proxy 调用成功时状态与耗时写入正确

## 9.6 验收标准
- 各业务模块不再重复实现自己的规则判断
- 代理请求无论成功失败都可审计
- model routing 可给出基础推荐结果

## 14. 每阶段完成后的检查清单

每完成一个阶段，都应检查：

- 是否已经有对应 migration
- 是否已经有 request/response DTO
- 是否已经有 handler/service/repo 基本骨架
- 是否已经有状态机测试
- 是否已经有事务回滚测试
- 是否已经有错误码与业务错误映射
- 是否已经符合前述事务边界文档

---

## 15. 不建议在 V1 第一批就做的内容

以下任务建议明确延后：
- 微服务拆分
- 复杂 BPM 引擎接入
- 大规模异步事件总线
- 超复杂审批流
- 多分支/并行网关全量能力
- 高级模型路由策略优化
- 完整统一审计总表
- 大规模批处理发布优化

---

## 16. 建议的 Definition of Done

每个业务任务完成，至少满足：

1. 对应表结构已落地
2. handler/service/repo 已完整接通
3. DTO 已稳定
4. 成功路径可测
5. 关键失败路径可测
6. 状态流转符合状态机文档
7. 事务边界符合事务矩阵文档
8. 返回错误可被前端/调用方稳定识别

---

## 17. 一句话总结

**V1 后端开发不应按“想到哪个接口就做哪个接口”推进，而应按“基础骨架 → 员工/能力 → 协作 → 流程 → 规则/代理 → 配置下发 → 集成验收”的顺序收敛成可执行 backlog，优先打通主链路原子性与状态一致性。**
