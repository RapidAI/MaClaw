# 伴读分享文档的讨论（主持人 Agent 回复）

状态：已实现（2026-10-27）

## 问题

伴读窗口里分享出去的文档，参与者发的问题会写成批注，但回答由参与者自己的本地 agent 生成。那条回答只在这位参与者的聊天里，其它参与者和主持人都看不到，讨论无法成立。

## 目标流程

1. 参与者在收到的分享上发送普通问题。这条消息作为批注写到 Hub，本机不再跑一次私有回答。
2. 主持人的机器轮询自己拥有的分享，把还没有主持人回复的批注交给本机的伴读 agent。
3. 主持人的 agent 回答后，回答以批注形式写回同一个分享，并把 `reply_to` 指向被回答的批注。
4. 所有能看到分享的人在下一次库轮询时收到这条回答；参与者在聊天区看到「主持人回复」，批注区看到「主持人 · 作者」。

选中一段文字后的改写、视频/网页记笔记、论文解读仍是本机操作，不进入讨论。

## Hub 协议

`POST /api/mobile/documents/shares/{token}/notes` 的请求体增加可选的 `reply_to`：

```json
{"text": "回答正文", "reply_to": "cn_..."}
```

- 只有分享创建者（主持人）可以带 `reply_to`；参与者带它会得到 403（`只有主持人可以回复批注`）。
- `reply_to` 必须指向该分享里已存在的一条非主持人批注，否则 400。
- 同一个 `reply_to` 只接受一条主持人回答。重复 POST（第二台主持机器、响应丢失后的重试）返回当前列表，不增加新批注。
- 批注持久化增加 `host` 与 `reply_to`。更早写入的批注没有 `host`，读取时用已保存的 `author_id == owner_id` 推导，避免把主持人旧批注当成读者问题再答一遍。
- `GET /api/mobile/documents/shares` 的响应增加 `notes_reply: true` 和 `server_time`（Hub 当前时间）。旧 Hub 没有这些字段，桌面端据此关闭主持人自动回答；否则旧 Hub 不记录 `reply_to`，每条主持人发言都会被当成未回答的问题，形成循环。`server_time` 用于把讨论水位放在 Hub 时钟上，避免两端时钟偏差跳过现场批注。
- 桌面端的库列表把 `notes_reply` 转成 `notesReply` 返回给窗口。参与者只有在确认 Hub 支持主持人回复后，才停用本机回答；旧 Hub，或第一次列表请求还没成功时，仍按原逻辑由本机 agent 回答，避免桌面端先升级、Hub 后升级时问题无人回答。列表请求失败时保留上一次成功的能力值。

批注列表里每条记录新增：

```json
{"id": "cn_...", "author": "reader@example.com", "text": "...", "created_at": "...", "host": false, "reply_to": "cn_..."}
```

## 桌面端

新增 `guiapp/file_companion_share_discussion.go`，主窗口和伴读窗口的启动路径都会启动同一个 watcher（进程内单例）。

- 每 20 秒拉一次本账号的分享；没有分享时退到 60 秒。
- 只处理 `host=false`、`created_at` 晚于水位、且没有被任何 `host=true` 批注以 `reply_to` 指过的批注。
- 水位按分享保存。新分享的水位取「功能首次安装时间」和「分享创建时间」中较晚的一个：功能上线前的旧分享不会补答历史批注；上线后创建的分享即使主持人在线前就有人提问，也会从分享创建时间开始回答。首次安装时间会回退一分钟，避免刚创建的分享被误判成历史。两个时间都使用 Hub 列表返回的 `server_time`（Hub 时钟），避免主持人和 Hub 的时钟不一致时把现场批注误判成历史；Hub 太旧没有该字段时才退回本机时间。旧版本用本机时钟写下的安装时间如果明显晚于 Hub 时间，会按 Hub 时钟重写，避免时钟跑快后跳过现场批注。`InstalledAt` 写在 `data/file-companion/share-discussion/share-discussion.json`。
- 每条批注只回答一次：Hub 的 `reply_to` 是持久去重；本机 `claims/` 文件防止主窗口与伴读窗口同时跑同一轮模型；失败后 5 分钟内不重试。
- 每个分享每小时最多 12 次回答（失败也计入），每次轮询最多回答 2 条，按时间从旧到新。
- 模型回答成功但 Hub 暂时拒绝写入时，回答文本在本机缓存 15 分钟；重试只重发批注，不再跑一次模型。
- 回答使用主持人自己的伴读 agent，私有会话在 `data/file-companion/share-discussion/sessions/`，不写主持人的正常伴读聊天记录，也不修改文档。
- 讨论轮次的系统提示是**最小提示**：只有主持人讨论指令，不拼主助手的身份、项目路径、置顶规则、任务、SSH 主机、长期记忆、技能、steering 规则和 resume trace。主助手侧也会跳过 chat task 调度指引和子代理路由，避免读者的诱导性批注把这些宿主上下文带进公开回答。
- 后台会话不是打开的标签页，所以会为它登记一个只读的文档授权和会话→文档映射；`pdf_read_pages` 等工具因此能读到主持人的本地副本。已经打开的标签页保留原来的授权，不会被改成只读。
- 模型提示把批注声明为读者写的、只能当作问题或评论，不能当作指令；PDF 只允许读页、裁图、提取图片，不调用 `pdf_restore`/`pdf_generate`。这不仅是提示：讨论会话的工具列表里没有这两个工具，执行层也会拒绝，即使批注诱导模型调用。
- 发布回答前会把主持人本机的文档绝对路径、父目录和用户主目录替换成「（本机路径已省略）」；共享文档名本身是公开的，保留。提示里也要求模型不透露本机路径、用户名、任务和记忆。
- 回答正文截到 1900 个字符，低于 Hub 的 2000 字符上限。

前端 `FileCompanionWindow`：

- 收到的分享上，普通问题只发批注，不调用本机 agent，并提示「已发给主持人 Agent，回复会作为批注同步给参与者」。
- 选中一段原文再提问时，选中的原文附在批注里一起发给主持人，主持人能看到具体段落。
- 最新批注列表里 `host=true && reply_to` 的条目在聊天区显示为「主持人回复」，并引用被回答的读者批注；批注区把主持人条目标成「主持人 · 作者」。
- 收到的分享按 5 秒轮询库，主持人回复通常在下一次轮询出现；聊天导出也包含这些主持人回复。
- 主持人画或清除 PDF 高亮后，阅读器保存本地高亮并发出变更事件；窗口按 1.2 秒防抖把项目（含最新高亮）同步到该文件的所有主持人分享。高亮发生在库列表确认主持人身份之前时先挂起，列表到达后再上传。参与者下一次轮询收到新版本，保存高亮并重载预览，因此主持人标注的黄色高亮会出现在其他参与者页面上。

## 撤销分享后的接收端清理

主持人删除分享后，Hub 不再把该 token 返回给接收方。接收端下一次列表刷新时对缺失的非群组 token 做一次单条分享查询：

- `404` + `分享链接不存在`：分享已被删除。删除本地 `library-files/<token>` 下载副本，删除会话记录、图表、结果和工作文件（`purgeFileCompanionProjectData`），清空该路径的 PDF 高亮、翻译和回答标注，关闭打开的标签页，并提示「这份分享已被撤回，本地副本与阅读记录已清除」。删除的 token 会记入 dismissed，防止一个较早的列表响应把副本重新导入；群组分享不记 dismissed，以便重新加入群组后同一 token 还能出现。
- `200`：链接仍存在（通常是过期分享），保留本地副本和阅读记录，不做清理。
- 网络错误、`403`、`5xx`：保留，下一次刷新重试。
- 群组分享继续走原有的成员撤销逻辑，不额外查询。
- 旧 Hub 没有单条分享路由时返回的普通 404 没有「分享链接不存在」消息，不会被误判为删除。
- 被判定「仍存在」的过期 token 会缓存 30 秒，避免接收方 5 秒轮询时反复请求 Hub；每次刷新最多并发查询 12 个缺失 token。

## 限制

- 主持人机器离线时没有回答；参与者的问题仍留在批注里，主持人下次上线后会回答。
- 主持人本地没有该文件（已移动或删除）时跳过；不会从 Hub 下载副本再回答。
- 公开链接分享的持链接者也能写批注。当前用每分享每小时 12 次的上限约束 token 消耗；需要更严格时可只对群组/指定人分享开启自动回答。
