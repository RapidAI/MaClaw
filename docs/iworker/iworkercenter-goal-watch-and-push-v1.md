# iWorkerCenter 目标守护与 Push 机制

## 为什么需要 Goal Watch

AI Native 组织不能假设一次 LLM 调用一定会持续工作到任务完成。

现实中，LLM 可能因为上下文丢失、工具调用失败、网络异常、服务限流、推理中断、模型幻觉或单纯“忘了继续”而停止推进任务。如果 iWorkerCenter 只负责分派任务，而不负责持续检测目标进展，组织运行就会退回到“人盯人”的状态。

因此，iWorkerCenter 需要一套目标检测与 push 机制，像组织心跳一样定期检查目标、任务、协商会话和流程状态，发现停滞后主动推动对应 iWorker 继续执行。

## 它不是老板控制中心

Goal Watch 不代表老板/董事会变成公司控制中心。

它属于组织自动运行机制，负责把已经确定的目标持续推向执行：

- 老板/董事会定义方向、约束和重大决策。
- iWorkerCenter 负责把目标拆成可执行状态，并持续检查是否停滞。
- iWorker 负责执行、反馈、协商和沉淀经验。
- 真人员工作为高价值 skill/tool/judgement node，在需要时被调用。

也就是说，Goal Watch 推动的是“已进入执行网络的目标”，不是替老板做战略控制。

## 第一阶段机制

当前第一版 `goalwatch` 模块先覆盖协作任务停滞检测：

- 定期扫描非终态任务：`pending`、`accepted`、`in_progress`。
- 如果任务 `updated_at` 超过停滞阈值，则判断为需要推动。
- 如果冷却期内已经 push 过，则不重复刷屏。
- 写入 `goal_push` 任务事件，作为可审计的组织推动记录。
- 提供手动检查接口，便于调试、前端驾驶舱和后续 IM 集成。

第一版默认参数：

- 停滞阈值：5 分钟。
- Push 冷却期：10 分钟。
- 后台检查周期：1 分钟。

## 后续演进方向

Goal Watch 应逐步从“任务停滞检测”演进为“组织目标守护系统”：

- 任务级：发现任务未接受、未开始、执行中长时间无反馈。
- Workflow 级：发现流程步骤超时、前后步骤断裂、责任人不可用。
- A2A 级：发现协商会话长期 open、方案无人 review、决策未形成。
- 目标级：发现经营目标偏离、关键指标恶化、行动项未闭环。
- 能力域级：发现某个虚拟组织单元持续积压、质量下降或经验未沉淀。

## Push 的目标对象

Push 不应该只是一条日志，最终要进入 iWorker 的工作界面和 IM/语音协作入口。

推荐路径：

- iWorkerCenter 写入 `goal_push` 事件。
- iWorker 客户端拉取或订阅自己的待处理 push。
- IM bot 将 push 转成自然语言提醒。
- iWorker 收到 push 后恢复上下文，继续执行或说明阻塞原因。
- 如果多次 push 后仍无进展，则升级为 A2A 协商或异常升级。

## 一句话总结

Goal Watch 是 AI Native 组织的执行心跳：它不替人做重大决策，但防止目标在 LLM 中断、工具失败或协作停滞中悄悄死亡。
