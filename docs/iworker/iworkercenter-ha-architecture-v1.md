# iWorkerCenter 高可用与多机热备架构

## 一句话定义

`iWorkerCenter` 是 AI Native 组织的中枢，因此必须具备多机热备与高可用能力，不能被视为单机后台服务。

## 一、为什么 iWorkerCenter 必须高可用

`iWorkerCenter` 承担的不是普通管理后台职责，而是企业组织运行的核心中枢：

- 组织记忆
- 角色能力
- 工作流状态
- 协作关系
- 审计轨迹
- 经营视图
- Executive Skills

如果它不可用，企业不仅是“后台打不开”，而是：

- 数字员工的组织协调会退化
- 关键记忆无法统一写入与读取
- 工作流推进会中断
- 管理与经营视图会失真
- 组织能力沉淀会暂停

因此，`iWorkerCenter` 必须具备类似 `hubcenter` 的高可用能力。

## 二、目标能力

第一阶段高可用目标应包括：

- 多节点部署
- 主备热备
- 节点故障自动或半自动切换
- 配置同步
- 状态数据持久化
- 故障恢复后继续服务

后续阶段再扩展：

- 多活读能力
- 更细粒度的同步策略
- 跨机房容灾
- 跨中心云侧灾备

## 三、推荐分层

### 1. 接入层

负责：

- 对外提供统一入口
- 将 `iWorker`、IM 网关、管理台流量转发到可用节点
- 在节点故障时切走失效实例

### 2. Center 服务层

由多个 `iWorkerCenter` 节点组成。

每个节点都可运行：

- 管理 API
- 组织记忆读写接口
- 工作流编排接口
- Executive Skills 服务
- 管理台 Web 服务

### 3. 状态与存储层

负责保存：

- 组织级记忆
- 任务与工作流状态
- 角色与能力数据
- 审计记录
- 同步事件日志
- 高可用配置状态

这里必须保证：

- 主节点写入可靠
- 备节点可追平
- 切换后状态连续

### 4. 云侧支撑层

由 `iWorkerCloud` 提供：

- 远程备份
- 授权
- 平台级发现与运维支持
- 灾备恢复辅助

## 四、核心设计原则

### 1. 真源仍在 iWorkerCenter 集群，而不是本地设备

即使有多机热备，组织级真源仍属于 `iWorkerCenter` 集群，不属于单个 `iWorker` 本地设备。

### 2. 事件优先于最终状态复制

高可用同步应优先考虑事件日志和状态演进，而不是只复制最终对象快照。

这样更利于：

- 故障恢复
- 幂等回放
- 冲突识别
- 审计追踪

### 3. 节点切换对 iWorker 尽量透明

`iWorker` 本地应尽量只感知“当前中心可用”，而不是深度感知复杂 HA 细节。

本地需要具备：

- 当前活跃节点发现
- 主节点切换后重连
- 待同步事件幂等重放
- 暂时不可用时进入离线缓冲模式

### 4. 高可用与组织一致性一起设计

不能只做服务存活层面的 HA，还要确保：

- 记忆一致性
- 工作流连续性
- 审计连续性
- Executive Skills 的输入上下文一致

## 五、对 iWorker 的直接影响

本地 `iWorker` 在接入 `iWorkerCenter` 时，建议按“中心集群”而非“单节点”建模。

需要支持：

- 多地址配置或发现
- 节点健康探测
- 首选节点与回退节点
- 切换后的请求重试
- 同步请求的幂等键

## 六、对记忆系统的直接影响

记忆系统必须兼容中心切换。

这意味着：

- 记忆写入要具备版本和事件标识
- 记忆回传不能依赖单节点会话状态
- 离线队列恢复时要能在新主节点继续提交
- 冲突判断要基于中心版本而不是本地猜测

## 七、与 hubcenter 的关系

`iWorkerCenter` 不是 `hubcenter` 的别名，也不是简单兼容层。

但在基础设施能力上，完全可以借鉴并吸收 `hubcenter` 已经验证过的高可用经验，例如：

- 多机热备部署方式
- 同步器设计
- 配置状态同步
- 故障切换机制
- 管理与运维手册

也就是说：

- 产品线独立
- 架构经验可复用
- 基础设施能力应继承成熟经验

## 八、最终结论

`iWorkerCenter` 一旦被定义为 AI Native 组织中枢，它就天然需要像基础设施一样高可用。

所以，多机热备不是可选增强项，而是 `iWorkerCenter` 成为企业级产品后的基本能力之一。
