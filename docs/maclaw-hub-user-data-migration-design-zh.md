# maclaw GUI 迁出与迁入设计

## 目标

在 maclaw GUI 的设置中提供 `迁出与迁入` 模块，让用户可以把当前机器上的 maclaw 个人数据和完整系统配置迁出到当前登录的 Hub，再在新安装或另一台已注册的 maclaw 客户端上迁入。迁入完成后，目标机器应尽可能恢复源机器上的完整 MaClaw 使用环境，同时保留目标机器自己的 Hub 身份和设备属性。

迁移范围：

- 当前用户的 maclaw 记忆数据。
- 当前用户的本地知识库数据与相关知识库文件、图片、附件资产。
- 全局设置中所有可迁移的系统配置，包括通用设置、代理设置、UI 配置、编程工具、宠物、搜索引擎、大模型、缓存服务、AI 模型、服务兑换、数字员工、IM、MIS 数据、安全策略及后续新增的用户可编辑设置。
- LLM 提供商的完整配置，包括 API Key、Base URL、接口类型、模型名称、自定义请求头、认证字段、路由、优先级、回退模型和推理参数。API Key 必须按原值完整迁移，不允许脱敏、截断、置空或要求用户重新填写。
- 其它系统配置中由用户保存的访问密钥、Token、密码和自定义请求头；只要它们属于可迁移的业务配置，就应随加密迁移包完整迁移。
- 恢复时写入当前机器 maclaw 使用的系统配置、记忆库、知识库数据库、知识库文件目录及其它被纳入清单的本地数据。

以下设备身份和临时运行状态不迁移：

- Hub 启用状态、Hub 登录会话、当前机器注册身份、`machine_id`、机器 token、viewer token、Hub 集中安全策略标记及其它用于标识或治理当前设备、当前登录会话的字段。
- 日志、缓存文件、临时文件、运行中任务、锁文件和纯运行时状态。
- 无法跨机器直接复用的绝对路径、端口占用状态及操作系统生成的设备标识。项目列表与当前项目、本地扩展技能目录、音频设备 ID、麦克风校准值、本地 Needle 模型路径和 VE 授权目录均保留目标机器现值；其它此类字段应在迁入预检中标记，并按目标机器环境重写或保留目标值。

配置迁移采用“默认包含、显式排除”的原则：所有持久化、用户可编辑且影响 MaClaw 行为的系统配置默认进入迁移包；只有设备身份、会话、临时状态或被明确列入排除表的字段可以不迁移。新增配置字段必须显式判定其迁移策略，不能因未加入手工白名单而静默丢失。

完整覆盖还包括源配置中的空值、空数组、`false` 和 `null`：这些值必须进入配置快照，用于清除目标机器已有但源机器已删除或关闭的配置。迁入方必须拒绝当前 schema 未声明的顶层配置字段，避免未知字段被静默忽略后形成“部分迁入”。

本设计只依赖当前 maclaw GUI 登录或注册到的 Hub，以及 Hub 上的租户、用户、客户端实例身份。它不涉及 hubcenter、skillmarket、能力市场或其它 Hub 管理模块。

## 身份与实例模型

Hub 侧以如下边界隔离迁移数据：

```text
hub + tenant_id + user_id + instance_id
```

同一个 Hub、同一个租户、同一个用户下可以存在多台电脑。每台电脑是一个 maclaw 客户端实例。

实例信息至少包含：

- `instance_id`
- `machine_name`
- `instance_name`
- `os`
- `maclaw_version`
- `last_seen_at`
- `has_export`
- `export_status`
- `export_updated_at`
- `export_size`

GUI 在迁入选择源实例时必须显示机器名。用户依靠机器名确认要从哪台电脑迁入数据。

## Hub 职责边界

Hub 只做加密迁移包的临时中转：

- 保存当前用户当前租户下唯一一份迁移包。
- 保存迁移包元信息、分片状态、hash 和迁移状态机。
- 支持分片上传、分片下载和断点续传。
- 校验分片 hash 与整体 hash。
- 在迁入完全成功后删除服务器上的迁移包。

Hub 不做以下事情：

- 不解析记忆、知识库、系统配置、LLM API Key 或其它密钥明文。
- 不参与知识库检索。
- 不把迁移包同步到 hubcenter。
- 不长期备份用户数据。
- 不在不同租户或不同用户之间共享迁移数据。

## 迁出覆盖规则

同一个 Hub、同一个租户、同一个用户下只允许保留一份待迁移数据。

用户点击迁出前，GUI 必须提示：

```text
Hub 上同一账号只能保留一份迁出数据。新的迁出会覆盖旧的迁出数据。请确认旧数据已经不再需要。
```

迁出时用户必须输入两次迁移口令。两次口令只用于确认本次迁出使用的加密口令是否一致，不用于验证旧迁出包。

服务端规则：

- 如果已有 `uploading` 或 `ready` 迁移包，新建迁出会创建新 `export_id` 并覆盖旧迁移包。
- 覆盖必须先让旧迁移包进入 `replaced` 或 `deleting` 状态，再清理旧分片。
- 覆盖不允许影响已经被目标机器 `claim` 且仍在有效 lease 内的 `importing` 迁移包，除非旧 lease 过期。
- 任一用户在同一租户下最终只有一份可见的 `ready` 迁移包。
- 新迁出覆盖旧迁出时，不要求本次口令与旧迁出包口令一致。旧迁出包会被替换，新迁移包使用本次输入的新口令加密。

## 迁移大小上限

迁移包大小按压缩后的数据包计算，默认不超过 `100M`。Hub 需要在创建迁出记录和完成上传校验时都执行该限制，避免客户端绕过前置检查。

租户管理员可以在 Hub 的系统设置中调整本租户迁移包上限：

- 默认值：`100M`。
- 最小值：`100M`。
- 最大值：`1G`。
- 设置项建议保存为 `migration_max_compressed_bytes`。
- GUI 在迁出前应展示当前租户上限；压缩后超过上限时停止上传，并提示用户清理知识库或调高租户上限。

## 数据包格式

本地先构建明文迁移目录，再压缩、加密、分片上传。

目录建议：

```text
manifest.json
memory/
  entries.jsonl
  metadata.json
knowledge/
  export.jsonl
  assets/
config/
  app_config.json
  migration_policy.json
  secret_inventory.json
```

`manifest.json` 包含：

- `format_version`
- `tenant_id`
- `user_id`
- `source_instance_id`
- `source_machine_name`
- `created_at`
- `maclaw_version`
- `memory_entry_count`
- `knowledge_source_count`
- `asset_count`
- `config_schema_version`
- `config_section_count`
- `secret_count`
- `excluded_config_paths[]`
- `plain_size`
- `plain_sha256`
- `encrypted_size`
- `encrypted_sha256`
- `chunk_size`
- `chunks[]`

每个 chunk 记录：

- `index`
- `offset`
- `size`
- `sha256`

`config/app_config.json` 保存完整的可迁移系统配置。其 LLM API Key 和其它业务密钥均保留原值，但该文件只能存在于迁移包的明文工作目录中，并必须在整体加密完成后立即安全清理。

`config/migration_policy.json` 记录配置字段的处理方式，至少区分：

- `restore`：按迁移包值恢复。
- `preserve_target`：保留目标机器现值，如 Hub 身份和机器身份。
- `rewrite_for_target`：根据目标机器环境重写，如本地目录。
- `skip_runtime`：跳过临时或运行时状态。

`config/secret_inventory.json` 只记录密钥所属配置路径、类型和是否已包含，不记录密钥值、摘要、前后缀或其它可用于推断密钥的信息。GUI 和日志只能显示“已包含密钥”的数量和类别。

`rewrite_for_target` 字段不得直接写入源机器值。当前版本对 `data_dir`、`working_directory` 采用“保留目标机器现值”的安全重写结果，避免把源机器绝对路径写入目标；未来若引入可验证的路径映射器，可在预检阶段生成目标路径后再恢复。

## 加密与完整性

口令只在本地使用，不上传到 Hub。

系统配置中包含 LLM API Key 等高敏感信息，因此还必须满足：

- Hub 始终只接触整体加密后的字节流，不得接收或生成配置明文预览。
- API Key 不得出现在 manifest、分片元信息、进度文本、日志、错误信息、遥测、崩溃报告或 GUI 预览中。
- Hub 接收 manifest 时按公开字段 schema 拒绝未知字段；密钥清单只存在于整体加密的正文中，不能通过扩展字段上传到 Hub。
- 解密后的配置只允许存在于受限临时目录或进程内存中；临时文件权限应限制为当前用户可读写，并在成功、失败、取消和进程恢复清理流程中删除。
- 在支持 Unix 权限位的平台上，迁移明文工作目录、解压目录及其配置子目录使用 `0700`，其中的配置文件使用 `0600`；创建子目录不得放宽组用户或其他用户的访问权限。
- 迁移口令不得持久化。密钥派生参数和 salt 可以写入加密包头，但不得降低既有加密强度。
- 迁出前要求用户设置满足产品密码策略的迁移口令，并明确提示迁移包包含 API Key 等敏感配置。

建议实现：

- 压缩：`zstd` 或 `gzip`。
- 密钥派生：`Argon2id`，随机 salt。
- 加密：`AES-256-GCM`。
- 明文包 hash：`plain_sha256`。
- 加密包 hash：`encrypted_sha256`。
- 分片 hash：每片独立 `sha256`。

迁出校验：

1. 本地生成明文包并计算 `plain_sha256`。
2. 压缩加密后计算 `encrypted_sha256`。
3. 分片上传，每片带 `sha256`。
4. Hub 校验每片 hash。
5. Hub 合并后校验 `encrypted_sha256`。
6. 校验通过后迁移包进入 `ready`。

迁入校验：

1. 分片下载并在本地合并。
2. 本地合并后校验 `encrypted_sha256`。
3. 使用用户口令解密。
4. 校验 `plain_sha256`。
5. 校验 manifest 中各数据文件 hash。
6. 对 v2 包校验配置 schema、配置段数量、记忆条目数量、迁移策略及密钥路径清单与正文一致；计数不符、策略不兼容或清单不一致时在写入前终止。
7. manifest 使用独立读取上限，避免文件数量较多时通过超大 manifest 造成额外内存压力。
8. manifest 文件路径必须是唯一、规范的相对 slash 路径；所有平台都按不区分大小写的可移植路径标识拒绝反斜杠别名、绝对路径、`.`/`..`、盘符冒号、Windows 保留设备名、尾随点或空格、控制字符、大小写碰撞、重复 ZIP 条目及文件/目录碰撞，避免在源机器可接受但迁入 Windows 后发生覆盖或清单绕过。Hub 接收公开 manifest 时执行同样的路径与非负统计校验，在上传正文前尽早拒绝异常包。
9. 导入端不信任 Hub 返回的分片元数据：分片数、分片大小和加密包大小必须是正整数并满足算术关系，SHA-256 必须为 64 位十六进制，且总大小与分片数均受上限约束。
10. `knowledge_bytes` 必须等于知识快照文件大小，`asset_bytes` 必须等于全部知识资产文件大小之和；v2 配置、策略和密钥清单文件必须完整存在。
11. 客户端生成的公开 manifest 上限为 16 MiB；Hub 创建迁出请求的 HTTP body 上限预留为 18 MiB，覆盖 manifest 与固定元数据开销。
12. 解包后的 JSON 不因整体 4 GiB 上限而无限制读入内存：manifest、策略和密钥清单各受 16 MiB 上限约束，完整配置受 64 MiB 上限约束，记忆条目受 256 MiB 上限约束；超限时在 JSON 解码和业务写入前终止。
13. 所有迁移正文 JSON 在反序列化前执行结构预检：按 Go JSON 字段匹配语义不区分大小写地递归拒绝同一对象中的重复字段，并拒绝顶层值后的附加 JSON。由此避免重复或大小写变体的 `api_key`、策略字段、公开 manifest 字段因解析器“后值覆盖前值”产生歧义；Hub 在保存公开 manifest 前执行同样校验。
14. JSON 结构预检限制最大嵌套深度为 128 层，防止小体积但极深的恶意配置或密钥对象消耗过多调用栈与解析时间。
15. 在任何配置、记忆或资产写入前，客户端先导出目标知识库的未脱敏本地回滚快照。知识导入返回错误或失败统计时，按知识库、资产、记忆、配置的顺序恢复目标状态，确保包括 LLM API Key 在内的系统配置不会因知识导入晚期失败而停留在半迁入状态。
16. 导入端把 Hub 返回的 `compressed_size` 作为必需的正整数元数据，同时复核 `encrypted_size <= compressed_size + 1 MiB + chunk_count × 64` 的加密开销上限；并在流式解密期间限制累计明文字节数，结束时要求解密输出精确等于声明大小，从而在 ZIP 解析前拒绝异常膨胀、异常加密开销或大小不一致的正文。
17. 每个下载分片按该分片的精确预期大小执行 HTTP 响应读取上限（额外读取 1 字节用于超限检测），不再由通用 32 MiB 缓冲兜底；响应读取错误、少字节或多字节均立即终止，避免恶意 Hub 响应造成不必要的内存占用。
18. 客户端对 Hub 的所有 JSON 响应复用迁移正文的严格结构校验：拒绝大小写变体的重复字段、尾随第二个 JSON 值、过深嵌套以及非对象顶层值。认领状态、分片元数据和清理状态不能通过影子字段改变解析结果。
19. 加密包头也使用同一严格 JSON 解析规则，再执行版本、KDF、盐、nonce 和 Argon2 参数范围校验；大小写变体的 `version`、`kdf`、`memory_kb` 等影子字段不能改变密钥派生或兼容性判断。
20. 密钥清单除标准 `api_key`、`token`、`password`、`secret` 外，还识别自定义 Header 或扩展配置中的 `authorization`、`credential`、`cookie`、`bearer`、私钥和访问密钥命名，并兼容 `apiKey`、`accessToken`、`refreshToken`、`privateKey` 等 camelCase 写法；这些值仍只存在于整体加密正文中，公开 manifest 只携带数量，不携带路径和值。
21. Hub 创建迁出记录的外层 JSON 信封同样执行严格结构校验和字段白名单：拒绝大小写变体重复字段、未知字段及尾随第二个顶层值，避免利用影子 `compressed_size`、`manifest` 或额外密钥字段绕过校验或进入服务端存储。
22. Hub 不信任公开 manifest 中客户端声明的租户、用户和机器身份；字段存在时必须与本次请求已认证的上传机器一致，防止伪造来源身份污染实例列表和迁入预检。为兼容旧包，缺省身份字段可以接受，但 Hub 仍以认证主体和数据库记录作为授权依据。
23. GUI 不得把 Hub 非成功响应正文原样拼接到错误信息、任务状态或日志中；只提取严格 JSON 中受控的 `message`/`code` 并限制长度，非 JSON 或结构异常响应使用通用错误，防止上游调试正文中的 API Key、Token 或请求元数据被二次回显。
24. LLM 连通性验证属于迁入后的诊断步骤，不得推翻已经成功提交的本地恢复。验证实现发生 panic 或自身不可用时，结果记为 `validation_unavailable`，不回显 panic 或上游请求详情，并继续执行 Hub 完成与清理；本地恢复成功标记必须在进入验证前设置。
25. 校验通过后导入当前机器本地 maclaw 数据目录。

## 迁出流程

旧机器执行：

1. 用户打开 GUI 设置中的 `迁出与迁入`。
2. GUI 显示当前 Hub、租户、用户、当前机器名。
3. GUI 显示覆盖提醒。
4. 用户输入迁移加密口令并二次确认；两次口令必须一致。
5. MaClawSrv 创建迁移 job。
6. 读取当前用户记忆、本地知识库和完整系统配置；应用迁移策略排除设备身份与运行时字段，并完整保留 LLM API Key 等业务密钥。
7. 构建 manifest、配置迁移策略、无值密钥清单与迁移目录。
8. 压缩、使用本次输入的口令加密、计算 hash。
9. 向 Hub 创建迁出记录。
10. 分片上传，支持失败重试和断点续传。
11. Hub 完成整体校验后返回 `ready`。
12. GUI 显示迁出完成。

迁出进度阶段：

```text
scanning -> packing -> compressing -> encrypting -> uploading -> verifying -> ready
```

## 迁入流程

新机器或目标机器执行：

1. maclaw 客户端注册或登录到同一个 Hub。
2. GUI 打开 `迁出与迁入`。
3. 拉取同 Hub、同租户、同用户下有迁移包的实例列表。
4. 实例列表显示机器名、更新时间、大小、状态。
5. 用户选择源机器实例。
6. 用户输入迁移加密口令。
7. 目标机器向 Hub claim 迁移包。
8. 分片下载；失败时释放 claim，Hub 数据保留，用户可重新迁入。
9. 本地校验加密包 hash。
10. 解密、解压、校验明文包 hash。
11. 执行迁入预检，展示配置范围、覆盖项、需重写项、兼容性问题和密钥数量，但不展示任何密钥值。
12. 备份目标机器当前配置、记忆和知识库，然后以事务式流程恢复完整系统配置、记忆库、知识库数据库与知识库文件目录。LLM API Key 必须按原值恢复。
13. 恢复后重新加载配置，并对 LLM 提供商等外部服务执行不泄露凭据的连通性验证；验证失败应进入结果摘要，不得回显密钥。
14. 本地导入完全成功后，客户端调用 Hub `complete`。
15. Hub 标记迁入成功并删除服务器上的迁移数据。
16. Hub 删除完成后返回完成。
17. GUI 显示迁入结果摘要，包括已恢复的配置分类、记忆和知识库数量、密钥数量、被保留或重写的字段，以及需要用户处理的连接验证失败项。

迁入进度阶段：

```text
claiming -> downloading -> verifying -> decrypting -> unpacking -> importing -> completing -> cleaning -> done
```

## 一次性迁入与清理

迁移包只能成功迁入一次。

状态机：

```text
uploading -> ready -> importing -> imported -> deleting -> deleted
                    -> failed
                    -> expired
                    -> replaced
```

规则：

- `ready` 可以被目标实例 claim。
- claim 后进入 `importing`，并设置 lease。
- 目标实例崩溃或断网时，lease 过期后可回到 `ready`。
- 本地导入未完全成功时，不允许调用成功 complete。
- Hub 只有收到目标实例的 complete 后才进入 `imported`。
- 进入 `imported` 后不允许再次下载或再次 claim。
- Hub 清理完成后进入 `deleted`。
- 清理失败时保持 `deleting` 并后台重试，但不允许再次迁入。

## API 草案

以下 API 属于当前登录 Hub，不属于 hubcenter。

```text
GET  /api/v1/migration/instances
POST /api/v1/migration/exports
GET  /api/v1/migration/exports/current
PUT  /api/v1/migration/exports/{export_id}/chunks/{index}
GET  /api/v1/migration/exports/{export_id}/chunks/{index}/status
POST /api/v1/migration/exports/{export_id}/complete-upload

POST /api/v1/migration/imports/{export_id}/claim
GET  /api/v1/migration/imports/{export_id}/chunks/{index}
POST /api/v1/migration/imports/{export_id}/complete
POST /api/v1/migration/imports/{export_id}/abort
```

所有 API 都必须从 Hub 登录态或机器 token 解析：

- `tenant_id`
- `user_id`
- `instance_id`
- `machine_name`

客户端不能通过请求体伪造这些身份字段。

## 本地导入策略

记忆导入：

- 写入当前机器当前用户的本地记忆库。
- 保留内容、分类、标签、时间、来源元数据。
- 将 owner 归属映射为当前 Hub 用户。
- 按原记忆 ID upsert，重复迁入或重试保持幂等。
- 受保护记忆会随快照恢复到当前用户 owner。

知识库导入：

- 写入当前机器当前用户的本地知识库数据库。
- 恢复 sources、nodes、cards、facts、labels、source links、import batches。
- 恢复图片与附件资产到当前机器知识库资产目录。
- 将 tenant/user 归属映射为当前登录 Hub 的 `tenant_id + user_id`。
- 使用现有知识库 `ImportSnapshot` 的 overwrite 与冲突处理能力恢复快照。
- 导入失败时不调用 Hub `complete`，并释放 claim，用户可修复后重新迁入。

配置恢复：

- 恢复全局设置中全部可迁移系统配置，采用“迁移包值覆盖目标值”的默认策略。
- LLM 配置必须完整恢复，包含 API Key、Base URL、接口类型、模型、路由、回退策略、自定义请求头和认证字段。API Key 不得脱敏或省略；验收标准是迁入后原有 LLM 提供商无需重新填写 API Key 即可继续调用。
- 代理密码、搜索服务密钥、缓存服务凭据、IM 或其它服务集成密钥等业务凭据同样完整恢复，除非该凭据本身与目标设备身份绑定且已被明确列入排除表。
- 不覆盖目标机器的 Hub 登录态、机器实例 ID、机器 token、viewer token 及其它设备身份凭据。
- 目标机器特有路径按迁移策略重写；无法安全重写的字段保留目标值，并在结果摘要中说明。
- 配置格式必须携带 schema 版本。迁入方对旧版本执行升级转换；对不支持的新版本在写入前终止，不得部分恢复。
- 写入前备份当前配置；配置、记忆、知识库和资产作为一个逻辑事务处理。任一关键步骤失败时回滚到迁入前状态，不得留下半迁入环境。
- 恢复后重新加载依赖配置的服务，并执行无密钥回显的连接验证。验证失败不删除已恢复密钥，但必须清晰提示用户检查网络、额度、服务状态或密钥有效性。

## 失败与断点续传

上传断点：

- 客户端可查询 chunk 状态。
- 已上传且 hash 匹配的 chunk 不重复上传。
- hash 不匹配的 chunk 重新上传。

下载失败恢复：

- 客户端按分片下载并在本地校验整体 `encrypted_sha256`。
- 下载、解密、校验或本地导入失败时释放 claim，Hub 数据保留。
- 用户可修复网络或口令后重新选择同一迁移包迁入。

失败恢复：

- 打包、加密失败只影响本地 job。
- 上传失败可重试。
- Hub 合并校验失败进入 `failed`，需重新迁出。
- 迁入导入失败不清理 Hub 数据。
- 配置、记忆、知识库或资产任一步骤失败时回滚目标机器已写入的数据，并保留迁入前备份用于恢复。
- 回滚失败属于高优先级错误，必须保留 Hub 迁移包并向用户显示可操作的恢复说明。
- complete 请求失败时客户端可重试；服务端 complete 必须幂等。

## 测试要点

- GUI 设置页出现 `迁出与迁入` tab。
- 迁出前显示“新迁出会覆盖旧迁出”的提醒。
- 迁出时必须输入两次口令，且两次口令不一致时不能开始迁出。
- 新迁出覆盖旧迁出时，口令可以与旧迁出不同，新迁移包必须使用本次输入口令加密。
- 实例列表显示机器名。
- 只能列出同 Hub、同租户、同用户的实例。
- 同用户只能有一份 `ready` 迁移包。
- 新迁出覆盖旧迁出。
- 上传分片 hash 错误会被拒绝。
- 合并后整体 hash 错误会被拒绝。
- 下载后 encrypted hash 与 plain hash 都必须校验。
- 口令错误不能导入。
- 本地导入失败不会删除 Hub 数据。
- 本地导入成功后才清理 Hub 数据。
- 迁移包成功迁入一次后不能再次迁入。
- 迁入落点是当前机器 maclaw 的本地配置、记忆库、知识库文件。
- 迁出包包含全局设置中全部可迁移配置，新增配置字段不会因未加入手工白名单而静默丢失。
- LLM 提供商配置中的 API Key、Base URL、模型、路由、回退策略、自定义请求头和认证字段按原值完整迁移。
- 迁入完成后，原有 LLM 提供商无需重新填写 API Key 即可发起调用。
- API Key 和其它密钥不会出现在 manifest、日志、错误信息、进度文案、GUI 预览或测试快照中。
- Hub 登录态、机器实例 ID、机器 token 和 viewer token 不会被源机器数据覆盖。
- 迁入前能够预览配置分类、覆盖项、保留项、重写项和密钥数量，但不能查看密钥值。
- 配置格式版本不兼容时在写入前失败，不产生部分迁入。
- 配置恢复中途失败会完整回滚到迁入前状态，Hub 迁移包保持可重试。
- 迁入完成摘要准确列出已恢复配置分类、密钥数量、被保留或重写的项目和连接验证结果。
