# HubCenter 路由模型与脏数据治理

## 一句话原则

用户归属、Hub 的默认租户，以及未注册用户的公共入口是三个不同概念，不能互相推导或互相覆盖。

同一邮箱还可能具有不同身份角色：普通用户、Hub 租户管理员、Hub owner，以及 HubCenter 管理员显式维护的路由。角色必须随库存和路由一起保存；租户管理员不能因被上报而伪装成普通用户。

## 身份角色与路由标志

Hub 上报的能力分为两组，禁止混用：

| 能力 | 含义 | 写入的链接 | 普通 `/api/entry/resolve` | 管理员路由查询 |
| --- | --- | --- | --- | --- |
| `tenant_user_emails` | 已确认的普通产品用户 | `hul_user_...` | 参与精确路由 | `route_kind=user` |
| `tenant_admin_emails` | 租户管理员身份库存 | `hul_hub_admin_...` | 不参与 | `route_kind=hub_admin` |

其他已有标志也会以 `route_kind` 返回：`hub_owner`、`admin_override`、`admin_migration`、`domain`、`public_fallback` 与 `invitation`。其中仅普通用户链接、HubCenter 的管理员显式路由以及迁移锁可影响普通用户的既有身份路由；Hub 自报的管理员库存和 owner 链接仅用于管理诊断，绝不抢占普通 onboarding 的公共兜底租户。

`EmailHasHubTenantLink` 是产品用户授权校验，不是“任意身份存在”校验：它只接受普通用户链接及 HubCenter 显式维护的路由，不接受 `hub_admin` 或 `hub_owner`。普通用户同步、邀请 `replace_all` 也不得删除 `hul_hub_admin_...`，这样同一邮箱同时是用户和管理员时，两种身份库存仍彼此独立。

兼容与自动修复：Hub 升级后下一次 register/heartbeat 会将同一 Hub + Tenant 下、已不在 `tenant_user_emails` 而出现在 `tenant_admin_emails` 的历史 `hul_user_...` 链接替换为 `hul_hub_admin_...`。若邮箱同时是真实用户和管理员，则保留普通用户链接，避免误删真实账户路由。

滚动升级期间，缺失 `tenant_admin_emails` 字段表示“旧 Hub 未提供管理员库存”，HubCenter 只保留现有管理员记录而不作删除；只有字段已明确上报（包括空对象）时才以该库存执行清理。这避免先升级 HubCenter 时，旧 Hub 的普通心跳误删已经分离的管理员身份。

```text
已注册用户的精确路由 → 企业邮箱域路由 → 显式公共兜底租户 → 无可用路由
```

上图描述的是未携带邀请码时的常规邮箱路由。有效邀请码优先定位到签发它的 Hub + Tenant；已消费的邀请码不会继续为其他身份保留该优先级。

## 概念与边界

| 概念 | 含义 | 不能代表什么 |
| --- | --- | --- |
| 精确用户路由 (`HubUserLink`) | 一个已知身份位于某个 Hub + Tenant | 不是公共注册策略 |
| Hub 默认租户 | 此 Hub 内部未显式选择租户时使用的租户 | 不是 HubCenter 公共兜底 |
| `HubUserLink.IsDefault` | 同一身份存在多个普通默认租户路由时的首选 Hub | 不代表该 Hub 对所有新用户兜底 |
| 公共兜底 (`IsPublicFallback`) | 未命中精确路由和域路由时，允许公开注册的明确入口 | 不接管已注册用户 |
| 企业邮箱域路由 | 针对某企业域名导向指定 Hub + Tenant | 不覆盖已注册用户的精确归属 |

特别地，某 Hub 拥有默认租户并不表示它是公共兜底。只有官方 Hub 的租户同时满足以下条件，才能进入公共兜底候选：

1. Hub 来源为 `official`；
2. 租户配置 `is_public_fallback=true`；
3. 该租户的有效注册范围为 `public`；
4. Hub 在线且未禁用。

历史兼容：没有迁移到租户注册策略的旧记录仍可能使用 Hub 级
`accept_public_signup` 作为旧默认租户入口。该兼容路径不应用于新配置；新建或已迁移的配置一律以上述显式租户策略为准。

## 常规解析顺序

1. 检查 IP 和身份是否被封禁。
2. 如果邀请码有效且尚未使用，路由至邀请码所属的 Hub + Tenant。
3. 对已知手机号或邮箱，查询精确用户路由。
   - 同一邮箱的默认租户普通链接可标记一个首选 Hub。
   - 管理员维护的用户路由优先于普通同步路由。
   - 只要存在可用的非私有精确用户路由，就不再退回域名或公共入口。
4. 若没有适用的精确路由，匹配企业邮箱域路由。
5. 若没有域路由命中，使用显式公共兜底租户。
6. 无任何候选则返回无可用路由，而不是任意猜测一个 Hub。

因此，已注册用户的邮件验证和登录必须先到其精确路由目标；邮件服务由该目标 Hub 的配置负责。前端不能把失败请求强行回退到某个固定 Hub，否则会跨租户并掩盖真实路由问题。

## 路由写入者

| 写入者 | 可做的事 | 不可做的事 |
| --- | --- | --- |
| 正常 Hub 用户同步 | 为本 Hub 已确认用户刷新对应 Hub + Tenant 的普通路由 | 用全量重放抢占其他 Hub 的历史归属 |
| Hub 用户清单/心跳 | 更新本 Hub 的已知成员清单 | 根据本地恢复数据判定全局归属 |
| 邀请和迁移流程 | 将被邀请或已迁移用户定向到指定 Hub + Tenant | 把邀请码当作所有后续用户的永久默认路由 |
| 管理员迁移 | 显式调整真实归属，并写入可抗来源重同步的维护路由 | 让系统猜测多条有效路由中哪一条正确 |

全量地让每个 Hub 重放其所有邮箱用户是危险的：同一邮箱在多个 Hub 的备份、迁移窗口或历史数据中存在时，会退化为“最后写入者获胜”。HubCenter 不使用这种方式修复路由。

## 自动清理策略

HubCenter 通过集中式 `ReconcileStaleUserRoutes` 巡检历史脏数据：启动两分钟后执行一次，随后每六小时执行一次。管理员也可调用：

```http
POST /api/admin/routing/reconcile-stale-routes
Authorization: Bearer <admin-token>
```

巡检对每条普通用户路由查询目标 Hub 的 `/api/center/user-exists`，并遵循以下规则：

1. 仅当目标 Hub 明确返回该 `Hub + Tenant + Email` 不存在时删除。
2. 删除严格限定在同一个 Hub、同一个租户、同一个身份；不波及同邮箱的其他租户路由。
3. Hub 离线、超时、接口不支持或鉴权失败时保留路由，并记录失败计数。
4. 管理员维护路由和 Hub owner 路由不参与自动删除。
5. 多条路由都有效时，系统不猜测哪条“正确”；必须通过管理员迁移明确处理。

在 HA 中各节点可安全重叠执行：删除是严格范围限定且幂等的。重叠仅可能产生额外的探测请求，不会扩大删除范围。

## 运维手册

### 诊断单个身份

1. 使用 `POST /api/entry/resolve` 或管理员路由查询确认当前候选、默认 Hub 和 Tenant。
2. 使用 `POST /api/admin/routing/verify-email-route` 对该身份逐条验证。该接口仅在远端明确不存在时清理对应精确路由。
3. 若路由不存在而用户确实存在，用 `restore-email-route` 恢复精确路由。

### 批量清理历史脏数据

1. 部署 HubCenter 版本后，调用 `reconcile-stale-routes` 立即执行一次。
2. 检查返回的 `checked`、`cleaned`、`skipped`、`failed`。
3. 对 `failed` 保留数据，待 Hub 恢复、接口升级或密钥同步后再重试；绝不以离线为由删除。

### 修复“多条都有效但归属错误”的情况

自动清理不处理这种情况，因为两端都声称用户存在时无法可靠推断真实归属。使用管理员用户迁移接口，指定来源 Hub + Tenant 和目标 Hub + Tenant。迁移会写入“身份级归属锁”（每个目标租户一条迁移链接）：该邮箱只返回迁移目标，任何 Hub 的普通单用户同步或用户清单同步都不能再以不同租户把它抢回。迁移链接的 ID 包含目标租户，因此一次保留多个目标租户时不会互相覆盖。需要改变该邮箱的归属时，必须再次执行管理员迁移，而不是依赖旧 Hub 重同步。

### Hub 恢复或数据库还原后

Hub 恢复后可正常同步其当前已确认用户。若恢复数据含有历史用户，不能通过全量同步重写全局归属。先运行路由诊断；确需转移的用户使用管理员迁移。自动巡检仅会删除远端明确已不存在的陈旧链接。
