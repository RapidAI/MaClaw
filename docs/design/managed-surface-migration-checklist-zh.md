# 受管表面迁移评估检查表

日期：2026-09-18
上游计划：`docs/design/ssh-availability-incident-review-and-improvement-plan-zh.md` §B1/B2
强制力：**legacy 工具迁往语义受管表面前，本表四个问题必须全部有书面答案；任一无答案即不准迁移。**

## 为什么有这张表

2026-09-18 的 ssh 事件链（见上游计划 §1）根源是：迁移把"恒可用 legacy 工具"换成受管表面时，可用性被悄悄耦合到分类器健康度、宿主状态、预算与跨请求状态四个新依赖上，而旧表面被撤除。一天内连续暴露 7 个故障。这张表把教训变成迁移前的强制闸门。

## 四个必答问题

### ① 分类器降级时，该能力从哪条路径可达？

UIC 的 tree 通道会超时/502（生产已多次发生）。降级（Degraded）或亚地板（conf < 0.78）回合中，逐项确认：

- 该标签是否被 `leftoverKeeps*` 保留在回露面？（当前仅 ssh 有保留，且要求 !Degraded）
- 该能力是否享受地板豁免？（当前仅 ssh，属安全评审例外，不可默认套用）
- 降级回合模型直接点名该工具时，petition 是否可达？（有托管表面 → 扩展重规划；无表面 → legacy overlay，仅当有 legacy 等价物）
- 如果以上皆非：**答案就是"降级时不可用"——必须显式接受并写入工具描述，不准留成隐含行为**

### ② 宿主状态缺席时，provider 是否仍能发布？

受管 adapter 常依赖宿主绑定（会话/活动文档/profile/桌面运行时）。逐项确认宿主缺席场景：

- 无存活会话 / 无活动文档 / 无 profile / 桌面运行时不存在——provider 是"不发布"还是"发布降级形态"（如 ssh 的 connect 模式）？
- "不发布"的情况下，能力是否还有任何可达路径？（ssh 曾因全部回答"不"而整回合失联）
- 多实例歧义（2+ 会话）时行为是什么？

### ③ 跨请求状态挂在哪？重建时谁重放？

petition 授予的 overlay、每回合预算计数等状态挂在回调结构体的哪个字段？`BuildToolsForModelRequest` 每次从策略面重建工具表时**谁负责重放**？（ssh 的 overlay 曾挂在 `c.tools` 上被重建静默抹除——修复是重建改道 `setVisibleToolDefinitions`。新迁移若引入同类状态，必须指名重放点。）

### ④ 每回合预算是多少？耗尽时模型看到什么？

- 规则表（IM 与 reviewed 两张，parity 测试钉住）声明 `MaxInvocations` 了吗？默认值是 1。
- 该数字与任务的迭代性质匹配吗？（服务器管理一回合 8 条命令 vs 默认 1）
- 耗尽时的提示文本是能力中立的吗？（`RepeatFamilySpentBudgetNote` 曾因 office 专属文案误导 ssh 回合）

## 不变量测试先行（问题①的强制执行手段）

迁移提交**必须**包含该能力的四场景可用性矩阵测试，范式：`guiapp/semantic_ssh_connect_test.go` 的 `TestSSHAvailabilityIndependentOfClassifierAndSession`：

1. 自信分类（conf ≥ 0.78，非降级）→ 受管表面直接渲染
2. 降级分类但带该能力信号 → 有豁免则渲染，无豁免则确认 leftover/petition 可达
3. 降级分类且无该能力信号（无托管表面）→ 模型点名时 petition 救援可达（**无 legacy 等价物的能力此场景标 N/A**）
4. 路由 miss 且保留分类 → leftover 渲染 builtin 工具（**无 builtin 残留的家族此场景标 N/A**）

矩阵中每个场景必须明确标注"适用并通过 / 适用但失败（=阻塞项）/ N/A（附理由）"。

## 评审例外登记

凡答案涉及以下机制的，属安全姿态例外，须单独评审并在 `semantic_schema_gate_test.go` 基线登记：

- 降级地板豁免（变更型家族在降级回合规划）
- legacy overlay 授予（在受管回合挂 legacy 工具定义）
- 新 schema 字段穿越参数闭包（location 类 / 凭据类）

## 批次收尾（迁移后同样强制）

- 每个批次落地后**同步所属计划的变更集附录**（追加文件、更新计数、标注共用文件）——2026-09-18 的实践中，附录漂移三次成为 review 的主要剩余产出源，且提交清单与现实不一致本身就是"乱"（宁慢勿乱原则的文档面）。
- 批次的新行为必须有观测事件（如 `[ssh-availability]`），否则无法验证验收标准。
