# HubCenter AI 专家市场后台改进需求

> 修订说明（2026-08-15）：本文已按现有实现复核。当前专家数据仅稳定保存 `owner_user_id` 和 `owner_email`；用户资料表没有用户名、昵称、手机号字段；管理员账户也没有审核员/超级管理员角色字段。以下方案以“先补齐身份数据与权限能力，再开放操作”为前提，避免前端做出后端无法正确支持的承诺。

## 0. 评审结论与关键决策

原始需求的业务方向成立，但不能直接按“私有 → 已上架”与“按手机号选用户”实现。推荐采用以下可实施方案：

| 议题 | 结论 |
| --- | --- |
| `公开`的含义 | 默认是“公开并提交审核”：`private/private → public/pending_review`；审核通过后沿用现有“通过并上架”：`pending_review → listed`。只有新增了 `expert_market.publish_direct` 能力时，才允许“公开并上架”。 |
| 转属主范围 | v1 仅限 `visibility=private AND status=private`，不触碰已经公开、已售卖或处于审核中的专家。 |
| 私有专家删除 | 管理员可删除私有专家，但必须使用“逻辑删除 → 可选彻底清除”的两阶段流程，保留审计记录；不能复用发布者当前的物理删除接口。 |
| 用户选择数据源 | 以 HubCenter 的统一用户身份目录为唯一来源；在该目录尚未提供用户名/昵称/手机号前，v1 只支持按用户 ID 和 Email 搜索与展示，不伪造手机号能力。 |
| 权限 | 不再假设已有“审核员/超级管理员”角色；新增可分配的细粒度能力，最低包括 `expert_market.view_contact`、`expert_market.publish`、`expert_market.transfer_owner`。 |
| 审计 | 现有事件表只有 `actor/action/reason`，不足以表达属主变更前后值。新增结构化审计字段或独立审计表，并记录管理员 ID、变更前后值和请求追踪 ID。 |
| 搜索性能 | `%关键字%` 不能依靠普通 B-tree 索引优化；SQLite 场景采用 FTS5 搜索索引（或限定为前缀匹配），不要只写“加索引”。 |
| 高可用 | 专家市场表目前不在 SkillMarket HA 快照同步清单中。若部署 HA，本次新增的属主/可见性变更必须纳入同步或明确仅支持单主写入。 |

### 0.1 推荐交付边界

第一期先交付“管理员运营私有专家”最小闭环：显示发布者 Email、后台关键字检索、转属主、公开并提交审核、结构化审计。用户名、昵称和手机号仅在统一身份目录提供这些受权限保护字段后启用；直接公开上架作为第二期的独立授权能力。

## 1. 背景与目标

当前 HubCenter 的 AI 专家市场后台已经支持审核、上架、下架和删除。运营管理员还需要处置未公开的私有专家：识别发布者、按发布者信息检索、转移专家属主，并在满足发布条件后将其公开发布。

本次改进目标：

- 让管理员能快速定位专家及其发布者；
- 让管理员能安全、可追溯地把私有专家转交给另一位用户；
- 让管理员能把符合条件的私有专家公开发布；
- 不向非管理员暴露发布者的完整联系方式。

本需求仅覆盖 HubCenter 管理后台，不改变面向普通用户的 AI 专家市场浏览、购买和安装流程。

## 2. 角色与权限

| 操作 | HubCenter 审核员 | HubCenter 超级管理员 | 普通用户/专家作者 |
| --- | --- | --- | --- |
| 查看发布者联系方式 | 允许，完整显示 | 允许，完整显示 | 不允许 |
| 按发布者信息检索 | 允许 | 允许 | 不允许 |
| 转移私有专家属主 | 不允许 | 允许 | 不允许 |
| 将私有专家公开发布 | 可按现有审核权限执行 | 允许 | 不允许 |
| 查看操作审计记录 | 允许 | 允许 | 不允许 |

后端必须独立鉴权，不能仅依赖前端按钮隐藏。无权限调用返回稳定的 `FORBIDDEN` 业务错误。

### 2.1 权限模型调整

当前管理员认证只区分“已登录管理员”和“非管理员”，管理员表没有角色字段。因此上表是目标权限，而不是现状。建议将功能权限作为管理员权限集合保存，采用最小权限原则：

| 能力码 | 用途 |
| --- | --- |
| `expert_market.read` | 查看后台专家列表和基础发布者摘要 |
| `expert_market.view_contact` | 查看、搜索完整 Email/手机号 |
| `expert_market.review` | 审核通过、驳回、下架 |
| `expert_market.publish` | 将私有专家公开并提交审核 |
| `expert_market.publish_direct` | 在满足发布条件时直接公开上架；默认不授予 |
| `expert_market.transfer_owner` | 转移私有专家属主 |
| `expert_market.delete_private` | 逻辑删除私有专家 |
| `expert_market.purge_private` | 彻底清除已删除私有专家的包文件；默认不授予 |
| `expert_market.audit.read` | 查看完整专家运营审计 |

在角色能力迁移完成前，只有显式配置为平台超级管理员的账户能执行转属主；其余管理员只能继续使用现有审核功能。所有权限判断必须在路由处理器内完成，`RequireAdmin` 只解决身份认证，不能替代授权。

## 3. 专家卡片信息改进

### 3.1 发布者信息

在后台专家卡片的“发布者”字段显示：

1. 发布者显示名/用户名（身份目录具备时）；
2. Email；
3. 手机号（身份目录具备、且操作者拥有 `expert_market.view_contact` 时）。

当前实现仅保存 `owner_email`，没有用户名、昵称和手机号。因此一期卡片展示 `发布者：Email`；统一身份目录完成后展示 `用户名 · Email`，手机号只作兜底。鼠标悬停可展示完整值；窄屏时允许截断。

发布者 Email 和手机号属于个人信息：仅管理后台拥有相应权限的角色可见完整值。任何普通用户市场、公开 API、导出文件和错误日志不得返回完整联系方式；若确有展示需求，必须使用脱敏值。

### 3.2 私有状态与操作区

私有专家应有清晰的 `私有` 状态标识，不能只显示英文 `private`。其操作区增加：

- `修改属主`：仅超级管理员可见；
- `公开`：拥有审核/上架权限的管理员可见。
- `删除`：仅对私有专家显示给拥有 `expert_market.delete_private` 能力的管理员。

操作进行中需禁用同卡片全部操作按钮，并显示提交中状态，防止重复请求。成功后刷新当前列表和卡片数据；失败时保留输入内容并提示明确错误。

`私有`不是独立的审核状态，而是当前数据模型中的组合状态 `visibility=private AND status=private`。前端应基于两字段组合判断，不能仅凭卡片文案或单个 `status` 字段显示操作。

## 4. 列表筛选与搜索

### 4.1 搜索入口

在现有“状态”筛选旁增加关键字搜索框，支持回车搜索、清除和刷新后保留当前筛选条件。列表 API 新增可选参数：

```text
GET /api/v1/admin/expert-market/experts?status={status}&keyword={keyword}&page={page}
```

### 4.2 匹配范围

`keyword` 采用不区分大小写的模糊匹配，至少覆盖：

- 专家名称；
- 专家简介；
- 专家 ID；
- 发布者用户名、昵称；
- 发布者 Email；
- 发布者手机号。

在统一身份目录尚未补齐前，一期实际覆盖专家名称、简介、专家 ID、发布者 Email、发布者 ID；接口响应必须明确支持范围，不能声称支持不存在的昵称/手机号。

搜索在服务端执行并与状态筛选取交集，返回结果仍按既有分页规则分页。关键字需 `trim`，限制最大长度（建议 100 个字符），使用参数化查询，并对 `%`、`_` 和 `\\` 做 LIKE 转义。

需要明确索引策略：普通索引只能优化精确匹配/前缀匹配，无法优化 `LIKE '%keyword%'`。建议为专家名、简介和发布者可搜索字段维护 SQLite FTS5 虚表；若暂不引入 FTS5，则产品交互须改为前缀匹配且限制搜索字段，不能预期大数据量下的模糊搜索性能。

无搜索结果时应明确提示“没有匹配的专家”，而非显示加载失败。

## 5. 修改属主

### 5.1 交互流程

1. 管理员点击私有专家卡片的 `修改属主`。
2. 弹出“选择新属主”对话框，显示当前属主信息。
3. 管理员输入关键字筛选用户；目标是支持用户名、昵称、Email、手机号的模糊匹配。
4. 结果以分页列表展示用户 ID、用户名/昵称（如有）和联系方式；当前属主、禁用用户、已删除用户不可选并说明原因。
5. 选择新属主后，确认区展示“专家名称、原属主、新属主”。
6. 点击确认时进行二次确认，文案明确该操作会转移后续管理权限。
7. 成功后关闭对话框、刷新专家卡片并给出成功提示。

对话框必须具备加载态、空结果、请求失败重试、键盘焦点管理和关闭按钮。用户列表不得一次加载全部用户，必须分页或按关键字查询。

当前 `sm_users` 仅有 ID、Email 与验证状态，且没有“禁用/删除”语义；因此用户选择不能直接建立在它之上并声称支持手机号或禁用过滤。需先明确统一身份目录的权威表、字段与生命周期，最低字段为 `user_id`、`username`、`nickname`、`email`、`phone_normalized`、`status`、`updated_at`。一期若无法接入该目录，则仅从 `sm_users` 查询“已验证用户”，展示 ID 和 Email，并在文案中明确限制。

### 5.2 接口建议

```text
GET  /api/v1/admin/identity-users?keyword={keyword}&page={page}&page_size={page_size}
POST /api/v1/admin/expert-market/experts/{expert_id}/transfer-owner
```

转属主请求体：

```json
{
  "target_user_id": "u_123",
  "reason": "运营归属调整",
  "expected_owner_id": "u_456"
}
```

`expected_owner_id` 用于乐观并发校验。若专家已被其他管理员转移，后端返回 HTTP `409` 与 `OWNER_CHANGED`，前端提示刷新后重试，不能覆盖新属主。对用户目录搜索接口还应设置最小关键词长度（建议 2）与返回上限，防止管理员令牌泄漏后被用来枚举全量联系人。

### 5.3 服务端规则

- 仅允许具备 `expert_market.transfer_owner` 能力的管理员执行；
- 仅允许转移私有专家；如未来支持公开专家转移，必须另行评审；
- 目标用户必须存在、启用且未删除；
- 目标用户是当前属主时拒绝请求，返回 `OWNER_UNCHANGED`；
- 请求必须在事务中更新 `owner_user_id` 与同步冗余的 `owner_email`，写入结构化审计事件并返回更新后的发布者摘要；只更新 ID 会造成现有后台卡片显示旧 Email；
- 专家包、版本、审核记录、下载统计和历史订单保持关联，不得复制或丢失；
- 历史订单、Credits 流水和已授予权益的归属不随属主转移而改写。后续收益规则若存在，应单独定义结算切点；
- 转移前后均需保留版本、操作者和时间，避免原发布者再继续编辑该专家。

由于当前专家市场购买记录不保存卖家 ID，且专家市场没有收益分成入账逻辑，不能在本需求中承诺“收益切点”。应在实施前先决定专家市场是否支持作者收益；若支持，订单必须持久化 `seller_user_id_at_purchase`，转属主只影响转移后的新订单。

## 5.4 管理员删除私有专家

### 删除语义

管理员删除私有专家采用逻辑删除：

```text
private/private → private/deleted
```

此状态的专家不再被原属主下载、编辑、重新公开或转属主，但仍保留列表墓碑和完整审计记录。管理员需填写删除原因并进行二次确认；确认框应显示专家名称、当前属主和“删除后原属主将失去访问权限”。

只有具备 `expert_market.purge_private` 能力的管理员才可对 `private/deleted` 执行“彻底清除”。彻底清除仅移除专家包文件，数据库墓碑、审计事件和必要的统计记录必须保留。若发现任何有效购买/授权记录（包括异常历史数据），彻底清除必须返回冲突，交由人工处置。

### 服务端规则与接口

```text
DELETE /api/v1/admin/expert-market/experts/{expert_id}/private
DELETE /api/v1/admin/expert-market/experts/{expert_id}/private/purge
```

两个接口均要求 JSON 请求体中的非空 `reason`。逻辑删除使用单一事务完成：校验权限与当前状态、更新状态和更新时间、写入结构化审计。`DELETE` 的幂等性须明确：重复请求返回当前 `deleted` 状态（建议 HTTP 200），而非误报“找不到”。

实现时必须修正下载授权条件：当前私有专家若仅按 `visibility=private AND owner_user_id` 判断，逻辑删除后原属主仍可能下载包。下载、账户列表和用户侧公开/编辑入口均应限制私有可操作状态为 `visibility='private' AND status='private'`；管理员审计列表则保留 `private/deleted` 可见。

发布者现有“删除私有专家”接口是物理删除并清理相关事件，不能供管理员调用，因为这会破坏运营审计。若产品希望统一行为，后续可把发布者删除也迁移为逻辑删除，但这是独立的数据保留策略变更。

## 6. 公开发布私有专家

### 6.1 交互流程

点击 `公开` 后弹出二次确认，说明“公开后将提交审核；审核通过后才会在市场展示并允许获取/购买”。确认成功后状态变更为 `visibility=public, status=pending_review`，按钮切换为当前审核流程所需的操作。

这是与现有生命周期一致的行为：用户侧已有私有专家 `publish` 接口，实际执行的是 `private/private → public/pending_review`，而管理员的 `approve` 才执行 `pending_review → listed`。原方案中“点击公开即已上架”会绕过审核，与当前安全边界冲突。

如业务确需直接公开上架，必须使用另一颗显式按钮 `公开并上架`，仅对拥有 `expert_market.publish_direct` 的管理员显示；服务端必须在一次事务内执行全部校验、状态更新和审计，且不可复用用户侧 `publish` 端点。

### 6.2 发布前校验

公开不是绕过质量与安全检查。后端必须校验：

- 专家及当前版本存在且未删除；
- 名称、简介、图标、版本及市场展示所需字段完整；
- 专家包签名、内容 hash、依赖和安全扫描均有效；
- 审核状态已通过，或由有权管理员在同一事务中完成审批与发布；
- 专家未处于封禁、归档、风险拦截等不可发布状态。

校验失败时返回具体业务错误，例如 `EXPERT_NOT_APPROVED`、`EXPERT_PACKAGE_INVALID`、`EXPERT_PUBLISH_BLOCKED`。前端显示可理解的失败原因，不应把私有专家直接标记为已上架。

### 6.3 接口建议

推荐复用现有审核语义，避免引入第二套状态：

```text
POST /api/v1/admin/expert-market/experts/{expert_id}/publish
```

请求体可包含必填的操作原因：

```json
{
  "reason": "管理员公开发布"
}
```

默认状态变更采用 `private/private -> public/pending_review`。审核通过后已有接口变更为 `public/listed`，而普通市场查询继续严格限定 `visibility='public' AND status='listed'`。

为避免 API 语义与用户侧 `/publish` 混淆，管理员接口建议命名为：

```text
POST /api/v1/admin/expert-market/experts/{expert_id}/submit-publication
POST /api/v1/admin/expert-market/experts/{expert_id}/publish-direct   # 仅显式直发能力
```

## 7. 审计、隐私与安全

所有转属主和公开发布操作写入不可变的 `expert_moderation_events`（或等价审计表），至少记录：

- 专家 ID、专家名称和版本；
- 操作类型：`transfer_owner`、`publish`；
- 操作管理员 ID；
- 原值与新值（属主 ID、可见性、上架状态）；
- 操作原因；
- 请求时间、完成时间、请求追踪 ID；
- 操作结果和失败错误码。

审计记录中的个人联系方式应仅保存必要的用户 ID 或当时的脱敏快照，避免在日志中扩散完整 Email/手机号。接口响应和管理页面应遵循最小必要披露原则。

现有 `sm_expert_market_events` 只有 `id, listing_id, actor, action, reason, created_at`，且 `actor` 为用户名/Email 字符串，不能满足上述可追溯要求。建议新建 `sm_expert_market_audit_events`，不要修改旧事件语义：

```text
id, listing_id, actor_admin_id, action, reason,
before_json, after_json, request_id, created_at
```

`before_json` / `after_json` 仅记录专家字段与用户 ID，例如 `owner_user_id`、`visibility`、`status`；不得记录完整手机号或 Email。旧事件表可以继续为现有审核页面提供兼容记录，但关键写操作以新审计表为事实来源。

## 8. 数据与性能建议

- 专家列表查询应关联发布者基础信息，避免逐卡片请求用户资料造成 N+1 问题；
- 为专家名称、ID、状态、`owner_id` 建立合适索引；发布者 Email/手机号搜索应使用受控索引或搜索字段，避免全表扫描；
- 手机号搜索应统一规范化（去空格、短横线和国家区号展示差异），Email 搜索统一小写；
- 列表只返回后台显示所需的发布者摘要，不返回密码、认证状态详情等敏感资料；
- API 对搜索和转属主接口实施后台管理员限流，并记录异常频率。

另外补充两项实现约束：

- 每次转属主/公开发布均使用写库和单一事务完成“状态读取（含预期属主）—更新—审计写入”；不要让读副本参与并发校验。
- 当前 SkillMarket 的 HA 快照清单未包含专家市场各表。启用 HA 的环境必须先将 `sm_expert_market_listings`、购买记录、事件和新增审计表加入复制范围，或将这些写接口限制到唯一主节点；否则故障切换后会丢失属主和发布状态。

## 9. 验收标准

1. 拥有 `expert_market.view_contact` 的管理员可看到发布者 Email，统一身份目录接入后可按权限看到手机号；普通用户接口不返回完整联系方式。
2. 管理员可用专家名称、简介、专家 ID、发布者 Email、发布者 ID 检索，并可与状态筛选组合；统一身份目录接入后再验收用户名、昵称、手机号匹配。
3. 拥有 `expert_market.transfer_owner` 的管理员仅可对 `private/private` 专家打开用户选择对话框；结果分页且不允许选择当前属主或非有效用户。
4. 服务端拒绝无权限、目标用户不存在/无效、非私有专家、目标属主未变和过期属主版本的请求，并返回稳定错误码。
5. 转属主成功后，`owner_user_id` 和 `owner_email` 同时更新；专家版本、审核记录、统计和历史订单均保持完整。
6. 并发转属主时，过期请求返回 HTTP 409 / `OWNER_CHANGED`，不会覆盖最新属主。
7. 拥有 `expert_market.publish` 的管理员可将通过提交校验的私有专家转为 `public/pending_review`；只有审核通过后，普通市场才可发现该专家。
8. 仅拥有 `expert_market.publish_direct` 的管理员可以直接上架，且该接口覆盖完整的发布校验、二次确认和审计。
9. 每次转属主和公开发布都有二次确认、加载状态、成功/失败提示、结构化审计记录和请求追踪 ID。
10. 专家市场表和新增审计表在 HA 部署中可正确复制，或系统明确禁止从非主节点写入；现有审核、上架、下架、删除流程及已购买用户权益均通过回归测试。
11. 拥有 `expert_market.delete_private` 的管理员可将且仅可将 `private/private` 专家逻辑删除为 `private/deleted`；操作必须填写原因、二次确认并产生结构化审计。
12. 已逻辑删除的私有专家不能被原属主下载、编辑、重新公开或转属主；仅有 `expert_market.purge_private` 的管理员可在无有效权益时彻底清除包文件。

## 10. 实施顺序

1. 确认并接入统一身份目录；定义用户状态、手机号规范化和联系方式访问权限。若无法接入，冻结一期范围为用户 ID + Email。
2. 引入管理员细粒度能力与结构化专家市场审计表；补齐 HA 同步或主节点写入策略。
3. 实现专家列表发布者摘要、FTS 搜索和后端/隐私测试。
4. 实现用户选择接口及“修改属主”对话框，并覆盖并发冲突测试。
5. 实现私有专家的管理员逻辑删除、下载保护和受控彻底清除，并覆盖幂等与历史权益测试。
6. 实现“公开并提交审核”、现有审批衔接和发布前校验；直发上架能力另行评审。
7. 完成端到端、权限、隐私、HA 故障切换和审计查询验证。
