# 数字员工计划 — 开发计划 v1

## 一、项目全景

数字员工计划由两个独立但紧密协作的产品组成：

| 产品 | 目录 | 定位 | 技术栈 |
|------|------|------|--------|
| DiWorker | `DiWorker/` | 面向终端用户的数字化同事客户端 | Wails v2 + Go + React/TS |
| iWorkerCenter | `iWorkerCenter/` | 企业级数字员工中枢（本身也是一个"超级数字员工"） | Wails v2 + Go + React/TS |

两者共享 `corelib/` 公共能力层，新增通用能力优先沉淀到 `corelib/`。

---

## 二、核心设计理念（新增）

### iWorkerCenter 不只是管理后台，它本身是一个"超级数字员工"

传统理解中，iWorkerCenter 是一个配置管理中心。但在新设计中，它的定位升级为：

1. **它了解企业** — 拥有企业级共享记忆（公司业务、组织结构、术语、制度），是企业认知的唯一权威来源
2. **它推送记忆** — 将共同记忆按层级（企业→角色→团队）注入到每个数字员工，让所有员工"懂公司"
3. **它拥有流程系统** — 管理员可以设计流程，也可以让 iWorkerCenter 自己基于企业理解来设计流程
4. **它基于角色驱动流程** — 每个数字员工有明确角色（办公、数据、生产、质量等），流程按角色分配步骤，模拟真实企业业务流转

### 数字员工 = 有角色的执行者

每个 DiWorker 中的数字员工不是通用 AI，而是：
- 有固定名字、头像、人格
- 有明确角色定位（办公同事、数据同事、生产同事、质量同事）
- 有角色对应的共享记忆（角色知识）
- 通过角色参与流程（流程步骤按角色分配）
- 角色之间的协作模拟真实企业分工

### 流程 = 企业业务流转的数字化映射

流程不是简单的审批链，而是：
- 基于角色的任务流转（"质量问题 → 质量同事分析 → 生产同事整改 → 办公同事归档"）
- iWorkerCenter 作为调度中枢，决定每一步由哪个角色/员工处理
- 流程步骤落地为协作任务，进入对应员工的任务列表
- 全过程可审计、可追溯

## 四、V1 开发计划

### 总体策略

按 **9 个切片（Slice）** 连续交付，每个切片可独立验证。

优先打通核心业务链路：**员工主档 → 协作任务 → 流程启动 → 流程推进**，再补齐治理和下发。

### 里程碑总览

```
M0  准备阶段          ─── Slice A
M1  基础主档就绪      ─── Slice B + C
M2  协作与流程打通    ─── Slice D + E + F
M3  治理与下发闭环    ─── Slice G + H + I
M4  DiWorker 联调     ─── 客户端切换到中心数据源
```

---

### Slice A — 应用骨架与统一基础设施

**目标**：搭建所有模块共享的底座，后续业务模块只填自己的 handler/service/repo。

**工作内容**：

| 项目 | 内容 |
|------|------|
| 入口 | `iWorkerCenter/cmd/server/main.go` |
| 配置加载 | 统一配置结构，支持文件 + 环境变量 |
| 数据库 | SQLite 初始化、`RunInTx` 事务封装 |
| 路由 | 统一 router 注册（admin/runtime/client/proxy 四组） |
| 响应 | 统一 response/error 结构、错误码体系 |
| Migration | 执行入口 + 空表验证 |
| 健康检查 | `/health` 增强（含 DB 状态） |

**目录结构**：

```
iWorkerCenter/
  cmd/server/main.go
  internal/
    app/bootstrap/        # 应用装配
    app/http/             # 路由注册
    app/transaction/      # 事务封装
    platform/db/          # SQLite 初始化
    platform/idgen/       # ID 生成
    shared/errors/        # 统一错误
    shared/response/      # 统一返回
    shared/paging/        # 分页
```

**验收标准**：服务可启动、`/health` 正常、migration 可执行、事务提交/回滚测试通过。

**预估工作量**：2-3 天

### Slice B — 数字员工主档闭环

**目标**：让"数字员工"这个核心对象可管理、可下发。后续所有模块都依赖它。

**工作内容**：

| 层 | 内容 |
|----|------|
| 表 | `colleagues`（含角色、头像、名字、描述、擅长、状态等） |
| Repo | `ColleagueRepo` |
| Service | `ColleagueService`、`ColleagueQueryService` |
| Handler | `POST/GET/PUT /admin/colleagues`、`POST /admin/colleagues/{id}/status` |
| DTO | 创建/更新/列表/详情 |
| 客户端接口 | `GET /client/colleagues` — DiWorker 拉取员工列表 |

**关键字段**（体现角色设计）：

```go
type Colleague struct {
    ID          string   // 唯一标识
    Name        string   // 名字（小迪、阿宁、老陈、小周）
    Avatar      string   // 头像
    Role        string   // 角色定位（办公同事、数据同事、生产同事、质量同事）
    RoleType    string   // 角色类型枚举（office/data/production/quality/general）
    Description string   // 一句话描述
    Strengths   []string // 更擅长什么
    Tasks       []string // 会做的事
    Status      string   // active/disabled
}
```

**验收标准**：管理端可 CRUD 员工，DiWorker 可通过 `/client/colleagues` 拉取列表。

**预估工作量**：2-3 天

### Slice D — 协作委托任务闭环

**目标**：实现数字员工之间的点对点协作，这是流程系统的执行基础。

**工作内容**：

| 层 | 内容 |
|----|------|
| 表 | `communication_messages`、`communication_message_events`、`collaboration_permissions` |
| Service | `CollaborationService`、`CollaborationLifecycleService`、`CollaborationPermissionService`、`InboxQueryService` |
| Handler | `/runtime/collaboration/*`、`/runtime/tasks/inbox` |
| 状态机 | 待命 → 正在执行 → 完成 / 拒绝 |

**关键规则**：
- 主记录与 created 事件同事务

**验收标准**：两个员工之间可发起协作、接受/拒绝/完成，事件表完整记录状态变化。

**预估工作量**：3-4 天

### Slice E — 工作流定义与实例启动闭环

**目标**：实现基于角色的流程定义和实例创建。这是"iWorkerCenter 作为超级数字员工驱动流程"的核心。

**工作内容**：

| 层 | 内容 |
|----|------|
| 表 | `workflow_definitions`、`workflow_step_definitions`、`workflow_instances`、`workflow_step_instances`、`workflow_instance_events` |
| Service | `WorkflowDefinitionService`、`WorkflowRuntimeService`、`WorkflowInstanceQueryService` |
| Handler | `/admin/workflows/*`、`/runtime/workflows/instances` |

**关键设计（基于角色）**：

```go
type WorkflowStepDefinition struct {
    StepCode        string // 步骤编码
    StepName        string // 步骤名称
    StepType        string // processing/review/notification/archive
    AssigneeMode    string // fixed_colleague/by_role_type/by_permission
    AssigneeRoleType string // office/data/production/quality — 按角色分配
    AssigneeColleagueID string // 固定分配时使用
    TimeoutRule     string
    RejectRule      string // end_process/return_initiator
    SortOrder       int
}
```

**流程示例**（质量问题闭环）：

```
步骤1: 质量同事(quality) → 问题分析与归类
步骤2: 生产同事(production) → 整改方案制定
步骤3: 质量同事(quality) → 整改效果审核
步骤4: 办公同事(office) → 归档与通知
```

**关键规则**：
- 创建实例时必须同步创建首步与首条协作任务
- 首步不可分配时整个实例不创建
- 步骤按角色类型匹配可用员工

**验收标准**：可创建流程模板、基于模板创建实例、实例创建后立即有首步任务。

**预估工作量**：4-5 天

### Slice F — 工作流步骤推进闭环

**目标**：实现流程步骤的连续推进，这是整个 V1 最关键的事务一致性挑战。

**工作内容**：

| 层 | 内容 |
|----|------|
| Service | `WorkflowStepLifecycleService` |
| Handler | `/runtime/workflows/steps/{id}/accept|start|complete|reject` |
| 联动 | workflow ↔ collaboration 状态同步 |

**完成步骤时的原子操作**（同一事务）：
1. 当前步骤标记完成
2. 当前协作任务标记完成
3. 计算下一步（按角色匹配员工）
4. 创建下一步骤实例 + 下一协作任务
5. 更新流程实例 `current_step_id`
6. 写事件记录
7. 若无下一步 → 流程完成

**拒绝步骤时的原子操作**（同一事务）：
1. 当前步骤 rejected
2. 当前协作任务 rejected
3. 流程实例 rejected
4. 写事件记录

**验收标准**：多步流程可连续推进、最后一步可结束流程、拒绝可终止流程、不出现半推进状态。

**预估工作量**：3-4 天

### Slice G — 共享记忆 + 安全规则最小闭环

**目标**：实现 iWorkerCenter 作为"了解企业的超级数字员工"的记忆管理能力，以及统一安全规则。

**工作内容**：

| 模块 | 内容 |
|------|------|
| 共享记忆 | `shared_memories` 表、企业级/角色级记忆 CRUD、记忆下发接口 |
| 安全规则 | `security_policies`、`security_policy_hit_records` 表、规则检查服务 |
| 模型路由 | `model_endpoints`、`model_routing_policies` 表 |
| 代理审计 | `proxy_request_records` 表 |

**共享记忆关键设计**：

```go
type SharedMemory struct {
    ID          string   // 记忆 ID
    Title       string   // 标题
    Content     string   // 内容正文
    Level       string   // enterprise/role/team
    Scope       string   // all/office/data/production/quality/team_x
    Tags        []string // 标签
    Version     int      // 版本号
    Status      string   // draft/active/disabled
}
```

**注入顺序**：企业共享记忆 → 角色共享记忆 → 团队共享记忆 → 员工私有设定 → 当前任务上下文

**验收标准**：
- 可创建/编辑/发布共享记忆
- 按角色类型查询适用记忆
- collaboration/workflow 可接入统一安全判断
- proxy 调用无论成功失败都留审计记录

**预估工作量**：4-5 天

## 八、技术决策摘要

| 决策 | 选择 | 理由 |
|------|------|------|
| 数据库 | SQLite | 单体部署、零运维、与现有 hub 一致 |
| 架构 | 单体模块化 | V1 先跑通，模块边界清晰可后续拆服务 |
| 流程引擎 | 自建轻量串行引擎 | V1 不需要通用 BPM，优先简单可控 |
| 前后端通信 | Wails binding + HTTP API | 管理端用 binding，DiWorker 用 HTTP |
| 公共能力 | 优先复用 `corelib/` | 不重复造轮子，缺什么补什么 |
| 协议 | OpenAI 兼容 | 代理层统一转换，Anthropic 自动适配 |

## 九、V1 成功标准

### 对管理员
- ✅ 能创建和维护数字员工（含角色配置）
- ✅ 能给数字员工装配能力包
- ✅ 能设计基于角色的工作流
- ✅ 能管理企业共享记忆
- ✅ 能查看员工之间的协作记录
- ✅ 能统一配置模型和安全规则
- ✅ 能把配置下发给客户端

### 对终端用户
- ✅ 能在 Welcome 页看到不同名字和角色的同事
- ✅ 能根据同事的"会做的事"选择帮助者
- ✅ 数字员工"懂公司"（共享记忆生效）
- ✅ 能在历史任务里看到是谁帮自己处理过工作
- ✅ 流程任务能自动流转到对应角色的员工

### 对系统
- ✅ iWorkerCenter 作为超级数字员工，统一调度所有流程和协作
- ✅ 所有 LLM 请求通过中心代理，可审计可控制
- ✅ 角色驱动的流程可模拟真实企业业务流转
