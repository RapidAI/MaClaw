# Maclaw 数字员工本地欢迎介绍设计

## 背景

用户第一次在当前本地客户端连接某个数字员工时，希望数字员工先做一次自我介绍，包括名字、角色、擅长事项和常见可协助任务。

本需求更关注当前本地体验，而不是账号生命周期内的全局“首次连接”审计语义。用户可能已经在别处见过该数字员工，但如果当前本地客户端没有任何相关历史会话，仍然适合先做一次轻量介绍，帮助用户快速想起该数字员工是谁、能做什么。

## 最终结论

采用本地判定、本地展示方案：

- 以“当前本地是否存在该数字员工的历史会话”为准。
- 如果本地不存在该数字员工的历史会话，则客户端直接展示一条本地欢迎介绍。
- 这条欢迎介绍不发给数字员工，不进入 LLM 上下文，不伪造用户消息。
- 如果本地历史会话后来被删除，再次连接时允许再次展示欢迎介绍。

## 不采用的方案

不采用“悄悄替用户发一句 `你是谁` 再触发数字员工回复”的方案，原因如下：

- 会污染真实消息历史。
- 会把假消息带入后续模型上下文。
- 会干扰总结、记忆、检索、导出和审计。
- 用户看到原始会话时语义别扭。

也不采用服务端全局首连状态方案，原因如下：

- 当前需求重点是本地唤醒和引导，不是全局审计。
- 本地历史删除后需要再次介绍，而全局首连状态会阻止这一行为。
- 多端全局状态会让“本机没有历史但不介绍”变得不符合用户直觉。

## 判定规则

连接某个数字员工时，客户端执行以下逻辑：

1. 读取当前本地与该数字员工相关的历史会话。
2. 只统计本地用户主动连接过该数字员工的可见历史会话。
3. 如果没有历史会话，则显示欢迎介绍。
4. 如果存在历史会话，则不自动显示欢迎介绍。

建议至少满足以下过滤条件后，才算“已有本地历史会话”：

- `employee_id` 等于当前数字员工。
- 会话属于当前本地用户主动发起或主动打开的正常会话。
- 会话不是只读审计会话。
- 会话不是其他人邀请该数字员工参与的受邀会话。
- 会话未被本地隐藏或已被本地彻底删除时，不算存在。

## 展示方式

优先采用“本地欢迎卡片”或“本地系统消息”。

推荐顺序如下：

- 首选：欢迎卡片。显示在聊天区顶部，不进入真实消息流。
- 次选：本地系统消息。显示在消息列表里，但带有明确的本地标记。

无论哪种形式，都必须满足：

- 不发送到服务端执行链路。
- 不触发数字员工实际回复。
- 不作为用户消息保存。
- 不进入后续 LLM 请求上下文。
- 不计入真实消息数、token 统计和运行记录。

## 数据来源

欢迎介绍文案直接由本地已有数字员工资料拼装，不依赖 LLM 生成。

建议使用以下字段：

- 名字
- 角色
- `description`
- `strengths`
- `tasks`

如果部分字段缺失，允许降级展示：

- 只有名字和角色时，也可展示简版介绍。
- `strengths` 或 `tasks` 为空时，可省略对应段落。

## 文案要求

欢迎介绍应为轻量引导，不应写成长篇普通回复。

建议内容结构：

- 我是谁
- 我擅长什么
- 你可以直接让我做什么

示例：

> 你好，我是小张，运营数字员工。  
> 我擅长日报整理、异常汇总和交接说明。  
> 你可以直接让我帮你写周报、整理材料或总结问题。

如果使用卡片，可拆成：

- 标题：`我是 {name}`
- 副标题：`{role}`
- 简介：`description`
- 擅长：`strengths`
- 可帮你做：`tasks`

## 本地消息元数据建议

如果采用“本地系统消息”而不是卡片，建议带以下元数据：

- `source=local_system`
- `message_kind=employee_intro`
- `employee_id={id}`
- `exclude_from_llm_context=true`
- `persist=false`

如果现有消息模型不支持 `persist=false`，则至少保证：

- 该消息只存在于本地 UI 状态层。
- 后续组装历史消息给模型时主动过滤掉。

## 删除历史后的行为

当用户删除当前本地与该数字员工相关的历史会话后：

- 下次再次连接该数字员工时，允许重新展示欢迎介绍。
- 这种行为不是“全局第一次连接”，而是“当前本地重新认识该数字员工”。

这是预期行为，不视为重复介绍 bug。

## 适用范围

本规则适用于：

- GUI 数字员工面板首次打开某员工会话。
- 本地客户端中从员工卡片进入聊天。

默认不适用于：

- 只读历史会话恢复。
- 审计查看场景。
- 其他人发起并邀请该数字员工参与的群聊审查场景。

如果未来需要对群聊场景做介绍，应单独设计短版群聊介绍，不复用本方案。

## 伪代码

```text
onOpenEmployeeChat(employeeID):
    sessions = listLocalSessions(employeeID)
    visibleOwnedSessions = filterNormalOwnedSessions(sessions)

    if visibleOwnedSessions is empty:
        showLocalEmployeeIntro(employeeID)

    openChatTab(employeeID)
```

如果采用本地系统消息：

```text
showLocalEmployeeIntro(employeeID):
    profile = loadEmployeeProfile(employeeID)
    intro = buildIntroFromProfile(profile)
    appendLocalSyntheticMessage({
        role: "assistant",
        source: "local_system",
        message_kind: "employee_intro",
        employee_id: employeeID,
        exclude_from_llm_context: true,
        persist: false,
        content: intro,
    })
```

## 实现建议

为尽量减少改动，建议分两步实施：

第一步：

- 先做欢迎卡片或本地系统消息。
- 判定只依赖现有本地历史会话。
- 不改服务端接口，不改数字员工执行链路。

第二步：

- 如果后续需要更精细体验，再增加“查看员工介绍”入口。
- 如果后续需要跨端一致行为，再另行设计服务端状态，不覆盖本方案。

## 当前实现状态

当前代码已按“本地系统消息”路径落地，行为如下：

- 数字员工列表打开 1:1 会话时，会把 `skill_description` 一并透传到会话 tab。
- 当前实现只对 1:1 数字员工会话生效，不对 live group 会话自动插入欢迎介绍。
- `VEConversationView` 在新会话建立后，会先等待当前 session 的本地历史加载完成。
- 仅当以下条件同时满足时，才插入一条本地 synthetic assistant 消息：
  - 当前不是恢复既有 `existingSessionId` 的历史会话。
  - 当前不是群聊会话。
  - `initialMessages` 为空。
  - 当前 session 从本地历史里没有加载出任何消息。
- 本地欢迎消息仅存在于前端会话状态中，带：
  - `localOnly: true`
  - `messageKind: "employee_intro"`
- 该消息不会发往后端，也不会参与数字员工实际回复。
- 清空当前本地会话后，组件会重置 session/history 门闩；若随后创建 fresh session 且本地仍无历史，会再次显示欢迎介绍。

当前实现更接近“本地系统消息”而非“欢迎卡片”。如果后续想升级成卡片展示，可继续复用现有本地判定逻辑，只替换渲染层。

## 验收标准

- 当前本地从未与某数字员工有历史会话时，首次打开聊天会显示欢迎介绍。
- 欢迎介绍不会触发数字员工实际回复。
- 欢迎介绍不会进入后续模型上下文。
- 当前本地已存在该数字员工历史会话时，不再自动显示欢迎介绍。
- 本地删除该数字员工历史会话后，再次打开聊天会重新显示欢迎介绍。
- 只读审计或受邀会话不会错误地阻止欢迎介绍，也不会错误触发欢迎介绍。
